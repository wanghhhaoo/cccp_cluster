## 术语

“主节点”在本系统里有三种不同的含义，所以本文**从不单独写“主节点”**，一律用下表中的全称。

| 术语 | 含义 | 代码中的名字 |
|---|---|---|
| **集群主节点** | 通过选主选出的节点，负责调度、对账和任务表（第 5 章） | `leader` |
| **任期** | 每选出一次新的集群主节点就加 1 | `term` |
| **任务主节点** | 执行某个任务、并负责协调辅助节点的节点 | `primary` |
| **辅助节点** | 协同任务中由任务主节点调用的其他节点 | `helper` |
| **副本** | 同一个任务在某一个节点上的一份执行实例。协同任务正常情况下有“1 + 辅助节点数”份副本；迁移残留、短暂双主会产生多余的副本，由对账停掉 | — |
| **主视角** | PKCT 协同跟踪时由算法选举（`ElectPrimary`）选出的那架无人机，属于算法层的概念，与调度无关 | `primary_drone_id` |
| **执行代次** | `(epoch, assign_term)`，按字典序比较。`epoch` 在任务每次（重新）调度时加 1；`assign_term` 是做这次调度的集群主节点的任期。用来区分新旧执行会话（第 3.8 节） | `epoch`、`assign_term` |
| **任务表** | 集群主节点内存中的任务清单：应该有哪些任务、由谁执行（第 3.3 节） | `TaskTable` |
| **墓碑** | 执行器因“销毁”而停止某个任务后保留的记录，防止任务在换主后复活（第 4.5 节） | `Tombstone` |
| **节点编号** | 部署时为每个节点配置的 1 字节编号（1～254，0 表示“无”），控制面消息里用它代替节点名 | `node_id` |
| **控制面** | 决定“哪个任务、在哪些节点上、以哪个执行代次运行”，并保证这个决定被执行。每个节点的控制进程都运行其中一部分（心跳、集群视图、选主、网关路由），集群主节点再额外运行任务表、调度、对账（第 2.7 节） | — |
| **数据面** | 按控制面的决定把任务跑起来：取帧、推理、发布结果、节点之间协同 | — |
| **接入层** | 对外入口：UE HTTP 接口、事件流、`TaskStatus`。本版不修订 | — |
| **PKCI / PKCT** | 平台目前支持的两种推理任务：逐帧图像分类 / 目标跟踪 | — |
| **UE** | 运行 AirSim 的 Unreal Engine 仿真端，也是平台的调用方：通过 HTTP 创建、查询、销毁任务，接收结果（第 4.7 节） | — |

## 本版变更（0.2 → 0.3）

0.3 的出发点有两个：**无线网络可能较差、带宽有限，控制面流量要尽量小**；以及评审 0.2 时发现的几处逻辑漏洞。

| # | 变更 | 原因 | 章节 |
|---|---|---|---|
| 1 | `NodeStatus` 拆成每秒发布的精简心跳（< 1 KB，只带任务摘要）和变化时发布的 `TaskList`（完整 `TaskState`、墓碑） | 0.2 的心跳每条 1～4 KB，要拆成多个链路层帧；BEST_EFFORT 下任何一帧丢失，整条就丢了，丢包被放大 | 3.2、附录 C |
| 2 | 心跳压缩：节点编号代替名字、链路质量量化、二进制 `task_id`、资源和链路每 5 条心跳附带一次；去掉 `stamp` 和 CPU/GPU 型号字符串 | 同上 | 3.2、8.4 |
| 3 | 跨节点的 Service 全部改为 topic：`/cluster/command`、`/cluster/exec_event`、`/cluster/request`、`/cluster/reply`；只有集群主节点在当选时创建对应端点 | 端点数从数百降到约 110；没有 Service 的发现竞态；下发天然并行 | 2.5、D9 |
| 4 | `TaskReport` 升级为 `ExecEvent`：状态变化通知 + 命令回执 | 取代 Service 的回复 | 3.5 |
| 5 | 执行代次改为 `(epoch, assign_term)` | 两个集群主节点短暂并存时，0.2 的 epoch 可能重复 | 3.8、D17 |
| 6 | 执行器“没有出声”不再当作“没有任务”：心跳带 `executor_alive`，保留最后已知的任务列表，等 `executor_stall_grace_s` 后再迁移 | 数据面进程被饿死几秒很常见，0.2 会引发无谓的迁移和重复执行 | 2.4、4.9、6.4 |
| 7 | 每个节点缓存所有节点的 `TaskList`，离线节点的条目保留 5 分钟；新集群主节点据此救回离线节点（包括旧集群主节点自己）上的任务 | 0.2 中集群主节点自己执行的任务会随它丢失 | 3.6、6.2 |
| 8 | 销毁改为“当前代次的在线参与者都确认停止才算成功”，执行器留墓碑 | 0.2 中销毁后立即换主，任务会复活 | 4.5、D18 |
| 9 | 大面积离线保护：短时间内超过 1/3 的节点同时离线，暂停迁移 | 集群主节点自己的链路变差时，0.2 会把大量任务误迁移 | 4.9 |
| 10 | 执行器自己做准入检查（`BUSY`） | 调度器看到的任务数可能是错的 | 3.8 |
| 11 | 选主候选按“看得见的节点数”优先，再按编号 | 让连通性最好的节点当集群主节点 | 5.3、D21 |
| 12 | Submit 后在下一个控制周期就调度，不等每秒的对账 | 创建延迟从约 1 秒降到约 0.1～0.3 秒（估算） | 4.1 |
| 13 | 任务规格预留 `priority`、`preemption_policy`，当前只透传，待调度队列按优先级排序 | 以后启用优先级时不用改接口 | 3.3、D20 |
| 14 | 网络假设定为单个广播域 | 选主依赖“所有节点互相可见” | 1.3 |
| 15 | 明确控制面的边界、职责和流量预算；记录带宽措施 | — | 2.7、2.8 |
| 16 | 链式任务走发布订阅，平台不做结果存储 | — | 1.5、D19 |
| 17 | 运行中没有输入帧时，任务主节点报告 `FAILED`（`NOT_READY`），集群主节点换节点重试，累计 3 个节点都没有输入才判定失败 | 0.2 中输入停了任务仍显示 Running（原 10.1 第 13 条）；讨论纪要把“没帧检测”列为待讨论，实现先行，待团队确认 | 3.3、4.3、6.1 |

本版**没有**定下来的问题见第 10.5 节。

## 0 一页纸概览

**是什么**：12 架无人机机载板卡组成的协同推理平台。没有中心后端，所有节点对等；任何时刻由其中一个节点充当**集群主节点**，负责调度和任务管理；所有节点（包括集群主节点）都执行推理任务。

**核心机制**，一共五条：

1. **广播选主**。每个节点每秒广播一条精简的 `NodeStatus` 心跳（< 1 KB），里面带着“我认谁当集群主节点、任期多少”。按（支持者数量，任期，编号更小）的规则，所有节点收敛到同一个集群主节点。不需要 Raft，不需要成员名单（第 5 章）。
2. **执行者是事实来源**。每个节点在心跳里上报自己正在运行的任务摘要，在 `TaskList` 里（变化时可靠发布）上报完整规格。“集群里实际在跑什么”只由执行者说了算（第 3 章）。
3. **任务表只在集群主节点的内存里**。它记录“应该跑什么、由谁跑”。换主后，新集群主节点根据各节点的 `TaskList` 重建任务表，包括离线节点最后一份 `TaskList` 里的任务（第 3.3、4.9 节）。
4. **对账**。集群主节点每秒比较一次“应该”和“实际”，补发、重新调度、接收、停掉多余的副本（第 4.9 节）。
5. **栅栏和墓碑**。执行器拒绝来自旧任期（`term`）的命令；执行器、任务表和汇总方拒绝旧执行代次（`(epoch, assign_term)`）。执行器为被销毁的任务留墓碑，任务不会在换主后复活。即使短时间出现两个集群主节点，重复执行也会在几秒内被清理（第 5.6 节）。

节点之间只通过 6 个 topic 交互（另有 1 个只在本机传输的 `<ns>/exec/status`），没有跨节点的 Service（第 2.5 节）；控制面稳态流量的目标是约 50～100 kbps，与帧率无关（第 2.8 节）。

**换来的性质**（完整版见第 1.4 节）：

- 正在运行的任务不受集群主节点故障影响，新集群主节点原样接收。集群主节点自己执行的任务会被重新调度（从头开始）。
- 任务主节点掉线，任务约 5 秒后迁移到其他节点。
- 创建任务返回成功时，任务一定已经跑起来了；销毁返回成功时，任务一定已经停了。否则调用方重试同一个请求（创建沿用同一个幂等键），不会重复。
- 代价：故障期间可能短暂重复执行；集群主节点挂掉时，还没跑起来的任务和历史记录会丢失。

**关键时间**（由参数推算，尚未在真实自组网上实测）：

| 事件 | 时间 |
|---|---|
| 冷启动到选出第一个集群主节点 | 约 5 秒（`startup_grace_s`） |
| 集群主节点故障 → 选出新的集群主节点 | 约 5～6 秒 |
| 集群主节点故障 → 新集群主节点开始接受请求 | 约 10～11 秒（再加 5 秒预热） |
| 任务主节点故障 → 任务在别处重新启动 | 约 5～6 秒 |
| 执行器卡住 → 任务迁移 | 约 13 秒（3 秒判定 + 10 秒宽限） |
| 创建一个任务（正常情况） | 约 0.1～0.3 秒（下一个控制周期就调度） |

## 1 目标与约束

### 1.1 背景：为什么不用中心后端

一个协同推理平台除了在各节点上做推理，还需要三项管理职责：

- **节点管理**：知道有哪些节点、各自的资源和链路状况；
- **调度**：为每个任务选出执行节点；
- **任务管理**：记录有哪些任务、处于什么状态，节点故障时迁移任务。

最直接的做法是放一台中心后端来承担这三项职责，各无人机节点只负责执行。但后端是单点：它挂了，整个系统就无法创建、查询、迁移任务。而且后端需要一台不在无人机上的机器，部署场景里不一定有。

### 1.2 目标

做一个**完全分布式**的平台：网络只由无人机节点组成，没有后端。具体来说：

1. 节点管理、调度、任务管理由节点自己承担。
2. 任何一个节点故障，包括承担管理职责的节点，系统都能自动恢复。
3. UE 可以连接任意一个节点，得到同样的服务。
4. 支持 PKCI、PKCT 两种推理任务和三种协同模式（第 4.4 节），UE 通过 HTTP 使用（第 4.7 节）。

### 1.3 约束

| 约束 | 对设计的影响 |
|---|---|
| 12 个节点，自组网；**目前假设是单个广播域**，所有节点互相直接可见 | 选主依赖“所有节点互相可见”（第 5.3 节）；状态同步只走 DDS。如果以后改成多跳网络，需要重新评估选主和 DDS 发现（第 10.5 节） |
| **无线网络可能较差，带宽有限** | 控制面流量必须有上界，只和节点数、任务数有关，和帧率无关；每秒发送的消息要能装进一个链路层帧（第 2.8 节） |
| 允许动态选主，“一段时间内由一个节点充当集群主节点” | 采用单一集群主节点的控制面，而不是完全无主（第 9 章 D1） |
| 集群主节点**也要承担推理** | 每个节点都有两种身份；控制面必须轻，不能和推理抢 CPU（第 2.4 节） |
| 除冗余协同外，**不允许两个节点做同一个任务** | 重复执行必须被检测和清理（第 5.6、6 章） |
| MVP 阶段**不考虑网络分区** | 分区时不保证正确性，但分区恢复后必须自动收敛（第 6.6 节） |
| 以 AirSim 仿真为主，但**不能影响真实部署** | 任务输入用地址描述，仿真和真机走同一套机制（第 7 章） |
| 先用 Python 实现，以后转 C++ | 业务逻辑不依赖 ROS，可以逐个模块翻译（第 2.3 节） |
| 平台组 3 个人 | 越简单越好；不引入需要专人维护的组件（第 9 章 D2） |
| ROS 2 Humble，节点是 Jetson Orin 和 x86 | 接口不支持类型演进，改接口必须全体升级（第 5.7 节）；以后可能用到的字段现在就预留（第 9 章 D20） |

### 1.4 系统的承诺

这是整个设计的出发点。下表列出系统对使用者的全部承诺，以及每一条背后的取舍。

| 方面 | 保证 | 不保证 | 为什么这样取舍 |
|---|---|---|---|
| 重复执行 | 同一任务的重复执行只会短暂存在，几秒内被自动清理 | 不保证任何时刻都不重复 | 要做到“永不重复”，需要在下发前达成多数派共识，并且执行器在每次处理前都确认自己仍持有租约。代价是 Raft 级别的复杂度，而 Raft 本身也不能完全消除执行层的重复（第 9 章 D2） |
| 正在运行的任务 | 集群主节点挂掉不影响它们；新集群主节点原样接收，执行代次不变，不重启 | 集群主节点自己执行的任务会被重新调度，**从头开始** | 执行者是事实来源。集群主节点自己的执行者也一起挂了，但它最后一份 `TaskList` 还缓存在其他节点上，新集群主节点能据此重新调度（第 6.2 节） |
| 还没跑起来的任务 | 对调用方的回复如实反映结果：返回成功时任务一定已经在跑 | 集群主节点挂掉时，排队中或下发途中的任务会丢失，调用方需要重试 | 这些任务只存在于集群主节点的内存里。如实回复 + 幂等重试，比复制它们简单得多 |
| 销毁 | 返回成功时，当前代次所有在线参与者上的副本都已停止，换主后也不会复活 | 销毁时离线的参与者，要等它回来后才被停掉；所有参与者都离线时，换主后任务可能被重新接收（第 10.1 节） | 和创建用同一个标准：执行者确认了才算成功。“这个任务已被销毁”记在执行器的墓碑里，不随集群主节点消失 |
| 历史记录 | 集群主节点在任期内保留终态任务 1 小时 | 换主后历史丢失 | 历史是给人看的，UE 或前端可以自己保存 |

一句话：**正在跑的任务很稳，没跑起来的任务靠调用方重试，销毁以执行者确认为准，历史不保证。**

### 1.5 不做的事情

- **模型并行**（把一个模型切分到多个节点上执行）：暂不支持，需要时新增协同模式。
- **拜占庭容错、鉴权**：节点之间互相信任；UE 接口没有认证。
- **持久化**：节点重启后不恢复任何控制面状态。全集群重启等于从零开始。
- **推理结果的存储**：平台只负责把结果按时送到，不负责把结果留住。PKCI/PKCT 是持续的逐帧任务，结果的价值随时间快速衰减，由消费者（UE、前端、子任务）自己保存它关心的结果。出现“有终态的任务”或“事后才读结果的读者”时再考虑，可以先从节点本地录制做起（第 10.3 节，第 9 章 D19）。
- **网络分区期间的正确性**：分区两侧可能各自选出集群主节点并各自执行任务，恢复后收敛（第 6.6 节）。是否接受分区期间短暂双主，尚未决定（第 10.5 节）。
- **外部观察者**：控制面的设计只考虑系统内部的交互。给 UE 生成事件流的 `TaskStatus` 属于接入层，本版不修订（第 2.7 节）。
- **跨节点时钟同步作为正确性前提**：所有超时只用本地单调时钟（`time.monotonic()`）计算；控制面消息里不再带时间戳，日志用本地收到消息的时间。各节点仍然应该部署 chrony，但那只是为了方便对照日志。

## 2 整体架构

### 2.1 职责由谁承担

| 职责 | 由谁承担 | 代码 |
|---|---|---|
| 节点管理 | 每个节点都广播 `NodeStatus` 心跳和 `TaskList`，每个节点都维护一份集群视图（含离线节点保留的条目） | `core/cluster_view.py`、`monitor/` |
| 选主 | 每个节点都运行，只有一个节点胜出 | `core/election.py` |
| 调度 | 集群主节点上的调度器 | `core/scheduler.py` |
| 任务管理 | 集群主节点内存中的任务表 + 对账器 | `core/task_table.py`、`core/reconciler.py`、`control/controller.py` |
| 对 UE 的接口 | **每个节点**都提供同样的 HTTP 接口，请求通过 `/cluster/request` 交给集群主节点 | `ue_api.py`、`control/ue_backend.py`、`control/gateway.py` |
| 资源监测 | 每个节点的控制进程：资源采集和链路测量 | `monitor/probes.py`、`core/link_estimator.py` |
| 任务执行 | 每个节点的执行器：接收命令、检查 term 和执行代次、准入检查、上报状态、留墓碑 | `cccp_task_executor/executor_node.py`、`core/execution_guard.py` |
| 推理 | PKCI/PKCT 引擎，与执行器在同一进程内直接调用 | `collab_inference_ros/engines.py`、`cccp_task_executor/inference.py` |
| 节点之间的协同 | 协同载荷放在 `TaskResult` 中通过 topic 传输（第 4.4 节） | — |

### 2.2 每个节点的两种身份

```
                       UE / 前端（HTTP，可以连任意节点，连不上就换一个）
                                           │
 ┌─────────────────────────────────────────┼─────────────────────────────────────────┐
 │ 自组网：同一个 ROS domain，DDS 自动发现，不需要成员名单                              │
 │                                                                                   │
 │  ┌──────── edge-01（当前的集群主节点）──────────┐   ┌──── edge-02 … edge-12 ──────┐  │
 │  │ 控制进程                                     │   │ 控制进程                      │  │
 │  │   选主 · 网关 · UE HTTP · 资源/链路测量        │   │   选主 · 网关 · UE HTTP · 测量 │  │
 │  │   ★ 任务表 · 调度 · 对账                       │   │   （任务表、调度、对账不启用）    │  │
 │  │ 数据面进程                                   │   │ 数据面进程                    │  │
 │  │   执行器 ─直接调用→ PKCI / PKCT 引擎           │   │   执行器 → PKCI / PKCT        │  │
 │  │ 取图进程（airsim_camera）                     │   │ 取图进程                      │  │
 │  └──────────────────────────────────────────────┘   └───────────────────────────────┘  │
 └───────────────────────────────────────────────────────────────────────────────────┘
```

- **所有节点**都是执行者：运行数据面，接收任务、做推理、发布结果。
- **一个节点**同时是集群主节点：它的控制进程额外启用任务表、调度和对账，并创建只有集群主节点才需要的端点（第 2.5 节）。其他节点的这部分代码也在，只是不工作；一旦当选就开始工作。心跳、集群视图、选主、网关路由这部分控制面在所有节点上都运行（第 2.7 节）。
- **所有节点**都运行网关：UE 可以连任意节点。不是集群主节点的网关通过 `/cluster/request` 把请求交给集群主节点。

集群主节点的身份是**临时的**：它只在当选期间持有任务表，卸任或挂掉时任务表随之消失。这是有意为之（第 9 章 D3）。

### 2.3 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层   ue_api.py (HTTP)        ros/control_node.py (ROS 服务) │
├──────────────────────────────────────────────────────────────┤
│ 控制层   control/  网关 · 集群主节点控制器 · 任务表存储 · UE 后端  │  不依赖 ROS
├──────────────────────────────────────────────────────────────┤
│ 核心层   core/     选主 · 任务表 · 调度 · 对账 · 执行栅栏 ·       │  纯逻辑
│                    链路估计 · 集群视图 · 任务规格 · 数据源地址     │  禁止 import ROS
├──────────────────────────────────────────────────────────────┤
│ 适配层   ros/      dispatcher · forwarder · convert · qos         │  ROS 消息 ↔ 核心对象
├──────────────────────────────────────────────────────────────┤
│ 数据面   cccp_task_executor/  执行器 · 推理后端 · AirSim 取图 ·    │  每个节点都运行
│          压缩转发    collab_inference/  PKCI/PKCT 引擎             │
└──────────────────────────────────────────────────────────────┘
```

为什么核心层禁止 import ROS（`test_core_is_ros_free.py` 会检查）：

1. **测试**：选主、任务表、对账这些最容易出错的逻辑，可以在没有 ROS 的机器上用 pytest 跑完，包括随机历史测试和多节点仿真。
2. **转 C++**：核心层的每个模块都是“输入一份视图，输出一组动作”，可以逐个对照翻译，并用同一组测试用例验证。
3. **时间可注入**：所有时钟都由调用方传入，测试可以精确模拟“5 秒后”。

控制层也不依赖 ROS：下发（`Dispatcher`）和转发（`Forwarder`）都是注入的接口。`test_controller.py` 用一个模拟的集群（`_sim.py`）驱动控制器，可以模拟丢消息、节点离线、两个集群主节点并存等情况。

### 2.4 进程和线程

每个节点运行 3 个进程：

| 进程 | 入口 | 内容 | 为什么单独一个进程 |
|---|---|---|---|
| 控制进程 | `ros2 run cccp_node control_node` | 选主、网关、UE HTTP、资源采集、链路测量；当选后启用任务表、调度、对账 | 必须保持轻量。如果被推理拖慢，`NodeStatus` 发不出去，节点会被判定离线，甚至引发换主 |
| 数据面进程 | `ros2 run cccp_task_executor data_plane` | 执行器 + PKCI + PKCT，用一个 `MultiThreadedExecutor` 运行 | 推理和图像处理很耗 CPU，受 GIL 影响，不能和控制进程放在一起 |
| 取图进程 | `airsim_camera` | 从 AirSim 取本机无人机的相机画面，发布到 `<ns>/camera/image` | 独立的取图程序，和平台其他部分只通过这个 topic 交互 |

执行器、PKCI、PKCT 如果各占一个进程，每块板卡就是 5 个进程；合并成一个数据面进程后是 3 个，全集群的 DDS 参与者从 60 个降到 36 个。DDS 发现流量和参与者数量的平方相关，在无线网络上这一点很重要。是否把取图进程也并入数据面进程（参与者降到 24 个），等抓包结果再定（第 2.8 节）。

**控制进程内部的线程**：

| 线程 | 做什么 | 注意 |
|---|---|---|
| ROS 执行器（8 线程） | 收发 `NodeStatus`、`TaskList`，收 `ExecutorStatus`、`Reply`，发 `Request`；当选后还收 `ExecEvent`、`Request`，发 `Command`、`Reply` | `NodeStatus` 的收发和选主在一个互斥回调组里，保证选主的输入一致；这个组里不做阻塞调用。资源采样（会调用 `nvidia-smi`）在单独的互斥回调组，每 5 个心跳周期一次，心跳只读最近一次的结果 |
| 控制器线程 | 10 Hz 循环：处理 `ExecEvent` 和 `Request`；为新的 Pending 任务调度；每秒对账一次 | 只在当选且预热结束后真正工作 |
| UE HTTP 线程 | 每个请求一个线程 | 创建、销毁请求最多阻塞 15 秒（`request_timeout_s`），等集群主节点的 `Reply` |
| 出站队列（50 ms 定时器） | 把其他线程产生的 ROS 动作（发布消息、订阅结果）交给 ROS 线程执行 | ROS 实体只在执行器线程里创建 |
| 事件日志写盘线程 | 把事件日志的行写到本机磁盘（第 2.9 节） | 记录事件的线程只把行放进队列，不等磁盘 |

控制面**没有跨节点的阻塞调用**：下发是发布一条 `Command`，回执通过 `ExecEvent` 异步回来；网关转发是发布一条 `Request`，在本地等对应的 `Reply`。集群主节点也不需要为每个等待中的请求占一个线程：它记下请求的标识，结果出来时再发布 `Reply`。

**数据面进程和控制进程之间**只有一个 topic：`<ns>/exec/status`（`ExecutorStatus`，1 Hz）。控制进程用它生成心跳里的任务摘要和本节点的 `TaskList`。

- 执行器里，发布 `ExecutorStatus` 的定时器放在**独立的回调组**，不和推理回调共用线程，降低它被饿死的概率。
- 超过 3 秒（`executor_timeout_s`）没收到 `ExecutorStatus`，控制进程把心跳的 `executor_alive` 和 `inference_ready` 置为 false，**任务列表和墓碑保持最后一次已知的值**。调度器不再往这个节点派新任务；集群主节点对它已有的任务等 `executor_stall_grace_s`（10 秒）后再迁移（第 4.9 节）。
- 只有执行器明确说“任务没了”（新的 `ExecutorStatus` 里没有这个任务，包括执行器重启后 `incarnation` 变了），才说明任务真的没了，按第 6.4 节处理。执行器没有出声，只说明暂时不知道。

### 2.5 通信方式

先讲选择的逻辑：

| 通信方式 | 用在哪里 | 原因 |
|---|---|---|
| **Topic 广播（不可靠）** | `/cluster/node_status`（所有节点 ↔ 所有节点，1 Hz） | 一对多、周期性、只有最新值有用；丢一条下一秒就补上 |
| **Topic（可靠，保留最后一条）** | `/cluster/task_list`（所有节点 → 所有节点，变化时） | 内容大、变化少；新订阅者一订阅就能拿到每个节点的最新一份 |
| **Topic（可靠，带目标地址）** | `/cluster/command`、`/cluster/exec_event`、`/cluster/request`、`/cluster/reply` | 低频的命令、回执、请求、回复。命令都是幂等的，丢了由对账重发，不需要 Service 的“一问一答”（第 9 章 D9） |
| **Topic（逐帧）** | `<ns>/task/result`、`<ns>/input/...`、`.../compressed` | 高频数据流；可以多个订阅者；丢帧没关系 |
| **进程内函数调用** | 执行器 → PKCI/PKCT 引擎 | 同一进程，省掉序列化和 DDS 往返 |
| **本机 Service** | `<ns>/api/task/*`（接入层入口）、`<ns>/algorithms/*` | 只在本机调用 |
| **HTTP** | 只用于 UE ↔ 节点 | UE 只需要知道任意一个节点的地址；节点之间禁止使用 HTTP |

整个系统**没有**独立的一致性协议，**没有**跨节点的 Service，**没有**节点之间两两建立的 TCP 连接，对网络唯一的要求是 DDS 能正常发现和通信。

**控制面的 7 个 topic**（6 个跨节点，`<ns>/exec/status` 只在本机；字段定义见附录 C）：

| Topic | 消息 | 发布端 | 订阅端 | QoS | 频率 / 大小 |
|---|---|---|---|---|---|
| `/cluster/node_status` | `NodeStatus` | 所有节点 | 所有节点 | BEST_EFFORT, VOLATILE；发布端 KEEP_LAST(1)，订阅端 KEEP_LAST(32) | 1 Hz；平均约 250 B（第 3.2 节） |
| `/cluster/task_list` | `TaskList` | 所有节点 | 所有节点 | RELIABLE, TRANSIENT_LOCAL；发布端 KEEP_LAST(1)，订阅端 KEEP_LAST(32) | 本节点任务或墓碑变化时 |
| `<ns>/exec/status` | `ExecutorStatus` | 本机执行器 | 本机控制进程 | BEST_EFFORT, KEEP_LAST(1), VOLATILE | 1 Hz，只在本机 |
| `/cluster/command` | `Command` | **集群主节点**（当选时创建） | 所有执行器 | RELIABLE, KEEP_LAST(32), VOLATILE | 调度、对账时 |
| `/cluster/exec_event` | `ExecEvent` | 所有执行器 | **集群主节点**（当选时创建） | RELIABLE, KEEP_LAST(32), VOLATILE | 执行状态变化、命令回执 |
| `/cluster/request` | `Request` | 所有网关 | **集群主节点**（当选时创建） | RELIABLE, KEEP_LAST(32), VOLATILE | 有请求时 |
| `/cluster/reply` | `Reply` | **集群主节点**（当选时创建） | 所有网关 | RELIABLE, KEEP_LAST(32), VOLATILE | 有请求时 |

全集群的控制面 DDS 端点：每个节点固定约 9 个，集群主节点再多 4 个，合计约 110 个。

**接入层和数据面的端点**（本版只改了和控制面相关的部分）：

| 名称 | 类型 | 方向 | QoS | 说明 |
|---|---|---|---|---|
| `/cluster/task_status` | `TaskStatus` topic | 集群主节点 → 所有网关 | RELIABLE, KEEP_LAST(100) | **接入层**：任务表变化，供网关生成 UE 事件流（第 4.6 节）。控制面不读它 |
| `<ns>/api/task/create\|destroy\|query` | `CreateTask` 等 srv | 本机调用方（UE 后端、链式触发）→ 本节点网关 | — | 接入层入口；网关校验后本地处理，或通过 `/cluster/request` 交给集群主节点 |
| `<ns>/algorithms/pkci/*`、`pkct/*` | srv | 执行器 → 推理引擎 | — | 只在 `INFERENCE_BACKEND=ros` 时使用（第 4.3 节） |
| `<ns>/camera/image` | `sensor_msgs/Image` | 取图进程 → 本节点执行器 | sensor data | 本机无人机的默认相机 |
| `<ns>/input/airsim/<vehicle>/cam_<camera>` | `sensor_msgs/Image` | 按需取图 → 本节点执行器 | sensor data | 有任务使用 `airsim://` 输入时才存在（第 7.4 节） |
| `<ns>/<topic>/compressed` | `sensor_msgs/CompressedImage` | 数据所在节点 → 其他参与节点 | sensor data | JPEG；只在有订阅者时才编码（第 7.5 节） |
| `<ns>/task/result`、`result_image` | `TaskResult` / `Image` | 执行节点 → 汇总方、网关 | RELIABLE, KEEP_LAST(10) | 逐帧结果和结果叠加图；`TaskResult` 增加 `assign_term` 字段（第 3.8 节） |
| `http://<节点>:18090/api/ue/*` | HTTP/JSON | UE → 任意节点 | — | UE 接口（第 4.7 节） |

QoS 集中定义在 `cccp_node/ros/qos.py`，端点名集中定义在 `cccp_node/names.py`。`<ns>` 是由节点名推导出的命名空间：非 `[A-Za-z0-9_]` 字符替换为 `_`，例如 `edge-01` 对应 `/edge_01`。

几条要点：

- **按角色创建端点**。`Command` 和 `Reply` 的发布端、`ExecEvent` 和 `Request` 的订阅端，只有集群主节点在当选时创建、卸任时销毁。其他节点平时不订阅这些 topic，也就不承担它们的可靠传输开销（心跳和确认）。DDS 匹配这些新端点的时间被 5 秒预热期吸收；预热期间丢失的消息，由对账和请求方的重试兜底。
- **目标地址代替“服务名唯一”**。0.2 把服务放在各节点的命名空间下，是为了避免同名服务有多个服务端时请求被执行多次。换成 topic 后，同一条消息会被所有订阅者收到，所以每条命令和请求都带目标：`Command.targets` 写明发给哪些执行器，`Request.target_leader` 写明由哪个集群主节点处理，收到不是发给自己的就忽略。短暂出现两个集群主节点时，一个请求也只会被一个集群主节点处理。
- **转发只转一次**。网关自己不是集群主节点时，向它跟随的集群主节点发布 `Request`；集群主节点只在本地处理，自己已经不是集群主节点就立即回复 `NOT_LEADER`，不再转发。即使各节点对“谁是集群主节点”的看法暂时不一致，请求也不会在节点之间来回转。
- **TRANSIENT_LOCAL 的两端都要声明**。`TaskList` 的订阅端也必须声明 TRANSIENT_LOCAL，否则收不到历史消息。订阅端的 KEEP_LAST 必须开大（32）：ROS 2 的消息没有 key，订阅端的历史槽位是所有发布者共用的，新订阅者一次收到 12 个节点的 `TaskList` 时，深度为 1 会互相覆盖。
- **多个节点发布的 topic，订阅端深度不小于节点数**，原因同上。心跳 `NodeStatus` 也是这样（订阅端 KEEP_LAST(32)）：两个节点的心跳相隔只有几毫秒时，后到的一条会在订阅端取走前一条之前把它覆盖；而各节点 1 Hz 定时器的相位由启动时刻决定、运行期间不变，于是每秒都撞，先到的那个节点在所有接收方那里长期“丢心跳”（第 10.1 节第 25 条）。QoS 统一在 `qos.py` 里定义，避免两端不一致导致静默连不上。
- 除 `TaskList` 外，所有 topic 的 Durability 都是 VOLATILE：新加入的订阅者不会收到历史消息，需要的状态都由周期性的心跳或 `TaskList` 补上。

### 2.7 控制面的边界与职责

**边界**：控制面负责决定“哪个任务、在哪些节点上、以哪个执行代次运行”，并保证这个决定被执行。

```
            UE / 前端（HTTP）
                  │
        ┌─────────▼─────────┐   /cluster/request   ┌──────────────────────┐
        │ 接入层：任意节点网关 │ ───────────────────► │ 控制面：集群主节点      │
        └───────────────────┘ ◄── /cluster/reply ── │ 任务表·调度·对账·下发   │
                                                     └───────────┬──────────┘
                                                                 │ /cluster/command
                                                                 ▼
  ┌──────────────────────────────┐  ExecutorStatus   ┌──────────────────────┐
  │ 控制面：每个节点的控制进程     │ ◄──（本机）─────── │ 执行器（两个面的接口）  │
  │ 心跳·集群视图·选主·链路测量    │                   │ 栅栏·准入·上报·墓碑    │
  └──────────────┬───────────────┘                   └─────┬────────────────┘
                 │ NodeStatus（1 Hz）、TaskList（变化时）       │ /cluster/exec_event → 集群主节点
                 ▼ 所有节点 ↔ 所有节点                         ▼ TaskResult、图像（数据面）
```

边界上有三条规则：

1. **控制面不传帧、不传结果、不传协同载荷。** 所以控制面的流量有上界，只和节点数、任务数有关，和帧率无关。
2. **数据面不做放置决策。** 唯一的越界点是链式触发：父任务通过本机网关的创建接口创建子任务，和 UE 走同一条路。
3. **执行器是两个面之间唯一的接口。** 对控制面，它是“接收命令、上报状态”的端点；对数据面，它负责管理会话。

**职责**：

| # | 职责 | 在哪里运行 | 输入 → 输出 |
|---|---|---|---|
| C1 | 心跳与成员管理：维护集群视图；离线节点的条目保留 `offline_retain_s`（5 分钟） | 每个节点的控制进程 | 收到的 `NodeStatus`、`TaskList` → 集群视图 |
| C2 | 链路测量 | 同上 | 对端心跳的 seq 和回显字段 → 本节点心跳的 `links[]` |
| C3 | 选主：候选按看得见的节点数、再按编号排序 | 同上 | 集群视图 → 本节点心跳的选主字段 |
| C4 | 汇总本节点执行状态：区分“执行器说没有任务”和“执行器没有出声” | 同上 | 本机 `ExecutorStatus` → 心跳的任务摘要和 `executor_alive`；本节点的 `TaskList` |
| C5 | 网关路由：本地处理、转发一次，或者报错 | 同上 | 本机的创建/销毁/查询调用 → `Request` |
| L1 | 任务表（期望状态），唯一写入口 `apply(command)` | 只在集群主节点（当选并预热结束后） | — |
| L2 | 创建与幂等：Submit，按幂等键去重 | 同上 | `Request` → 任务表 |
| L3 | 调度：Submit 后在下一个控制周期就调度 | 同上 | 任务表、集群视图 → `Assign` |
| L4 | 下发与停止：先写任务表，再发布 `Command`；一条 START 同时发给所有参与者；Cancel 后立即发 STOP | 同上 | 任务表 → `Command` |
| L5 | 对账：每秒一次 | 同上 | 任务表、集群视图 → 动作（第 4.9 节） |
| L6 | 回复请求 | 同上 | 任务表变化、`ExecEvent` → `Reply` |
| L7 | 定时触发 | 同上 | 未实现 |
| E1 | 执行栅栏：检查目标、term、执行代次 | 每个执行器 | `Command` → 接受 / 拒绝 |
| E2 | 准入检查：自己实际运行的任务数达到上限就拒绝（`BUSY`） | 同上 | 同上 |
| E3 | 状态上报：每秒发 `ExecutorStatus`；状态变化时和收到命令时发 `ExecEvent` | 同上 | — |
| E4 | 墓碑：因销毁而停止任务时留墓碑，保留 `tombstone_ttl_s`（10 分钟） | 同上 | — |
| E5 | 链式触发：父任务的任务主节点调用本机网关的创建接口 | 同上 | 未实现 |

**不属于控制面的**：推理、取图、压缩转发、发布 `TaskResult`、协同结果汇总，以及接入层的 UE HTTP、事件缓存、`TaskStatus`。

控制面的状态模型可以用一句话概括：**每份状态只有一个写者；所有通知（`ExecEvent`）只是为了加快速度，丢了都能由下一轮对账从心跳和 `TaskList` 补回来。** 详细见第 3 章。

### 2.8 控制面流量预算与带宽措施

**预算**（估算，需要抓包实测）：

| 来源 | 稳态流量 | 说明 |
|---|---|---|
| `NodeStatus` | 组播时约 25 kbps | 12 个节点 × 平均约 250 B（含协议头）× 1 Hz。如果 rmw 用单播发出，要再乘 11（每个订阅者一份） |
| `TaskList`、`Command`、`ExecEvent`、`Request`、`Reply` | 平时接近 0 | 事件驱动；换主或批量创建时有短暂的峰值 |
| 可靠传输的心跳和确认 | 与可靠 topic 的数量、收发关系数成正比 | 可靠发布者的历史缓存里有数据时，会周期性地向每个订阅者发 HEARTBEAT，订阅者回 ACKNACK，即使没有新数据也一直在发。所以 0.3 只让 `TaskList` 是“所有节点 → 所有节点”的可靠 topic，其余可靠 topic 只在执行器和当前集群主节点之间 |
| DDS 发现 | 与参与者数、端点数相关 | 36 个参与者；控制面端点约 110 个 |
| ROS 2 自带的端点 | 可能是最大的一块 | 每个 ROS 节点默认带 6 个参数服务（12 个端点）、`/rosout`、`/parameter_events`；每个参与者还有 `ros_discovery_info` |
| **控制面稳态合计** | **目标约 50～100 kbps** | 数据面单个压缩视频流就是几 Mbps（第 7.6 节） |

这条预算是控制面的设计约束：以后往控制面里加任何东西，都要能用“与帧率无关、与节点数大致线性”这个标准来检验。每秒发送的消息必须能装进一个链路层帧（约 1.4 KB）：BEST_EFFORT 下，一条消息拆成 n 帧，丢失率就从 p 变成 1 − (1 − p)ⁿ（第 6.5 节）。

**带宽措施**，按“收益 / 成本”排序：

| 措施 | 内容 | 状态 |
|---|---|---|
| A. 砍掉 ROS 2 自带的开销 | 控制进程和数据面进程中的所有节点，创建时关闭参数服务和 rosout：`Node(name, start_parameter_services=False, enable_rosout=False)`（启动时传入的参数覆盖仍然有效，日志改写本地文件）；考虑把取图进程并入数据面进程，参与者从 36 个降到 24 个。改完后用 `ros2 node list`、`ros2 topic list`、`ros2 service list` 核对只剩自己定义的端点 | 待实施 |
| B. 调 DDS 配置（XML，不改代码） | `NodeStatus` 走组播，其他消息走单播（无线设备允许的话，调高组播速率）；拉长参与者公告周期和租约（例如 10～30 秒；本系统判断节点是否在线用的是自己的心跳，不依赖 DDS 租约）；拉长可靠发布者的心跳周期（`TaskList` 设 3～5 秒左右，代价是丢失的可靠消息要晚一点才重传） | 部分完成：`deploy/cyclonedds.xml` 指定网卡、可切换 `AllowMulticast`（Cyclone 的默认值在无线网卡上只让发现报文走组播，心跳会给每个订阅者各发一份单播）；公告周期和租约等现场抓包后再定（`deploy/README.md`） |
| C. 压缩心跳 | 节点编号代替名字、链路质量量化、二进制 `task_id`、资源和链路每 5 条心跳附带一次 | **已体现在 0.3 的消息定义中**（第 3.2 节、附录 C） |
| D. 合并消息 | 讨论过去掉 `TaskReport`；改为 topic 方案后，`TaskReport` 升级为 `ExecEvent`，同时承担命令回执 | 已由 `ExecEvent` 取代 |

**先测再改**：在一块板卡上抓包，让 12 个节点空闲运行 60 秒，用 Wireshark 的 RTPS 解析器按子消息类型统计（DATA、HEARTBEAT、ACKNACK，以及 SPDP、SEDP 发现报文）各占多少字节、多少个包，并确认 rmw 实际用的是组播还是单播。在无线网络上，**包数**往往比字节数更要命，因为每个帧都有固定的信道争用和前导开销，所以评估时除了 kbps，也要看每秒的包数。

### 2.9 事件日志

日志是给现场盯着一块板卡看的；**事件日志**（`control/journal.py`）是给事后还原“整个集群当时发生了什么”用的。每个节点把自己经历的控制面事件写到本机磁盘，每个事件一行 JSON；事后把各板卡的文件收到一起，用 `tools/merge_journal.py` 合并成一条时间线。它不占无线信道：节点之间不交换事件日志，也不为它订阅任何 topic。

**每一行**都带这些公共字段，后面跟事件自己的字段：

| 字段 | 含义 |
|---|---|
| `t` | 墙钟时间（秒，3 位小数），合并多块板卡时按它排序，所以只有板卡做了时钟同步才准 |
| `mono` | 本机单调时钟，同一次运行内计算间隔用 |
| `node`、`inc` | 写这一行的节点和它的 `incarnation`（重启后变化） |
| `term`、`leader` | 这个节点当时跟随的 term 和集群主节点 |
| `seq` | 本次运行内的序号 |
| `event` | 事件名 |

**事件**：

| 事件 | 谁记 | 字段 |
|---|---|---|
| `start`、`stop` | 每个节点，控制进程启动和正常退出时 | `node_id`、`protocol` |
| `node_online`、`node_offline` | 每个节点，集群视图判定某节点上线或离线时 | `peer`、`restarted`、`silent_s`、`missed`（上线时：听不到的这段时间里对方的 seq 前进了多少，数值大说明它一直在发、是途中丢的；离线时：离线前漏掉的心跳数） |
| `leader_changed` | 每个节点，跟随的 (集群主节点, term) 变化时 | `prev_leader`、`prev_term`、`leading` |
| `leader_start`、`term_raised`、`leader_stop` | 当选的节点 | `warmup_s`；`from_term`；`led_term` |
| `leader_active` | 当选的节点，预热结束、开始接请求时 | `warmup_s`（实际用时）。和其他节点的 `node_offline` 对照，就是这次换主的不可用时长 |
| `task_status` | 集群主节点，任务表里任务状态的每次变化 | `task`、`status`、`epoch`、`primary`、`message` |
| `task_scheduled` | 集群主节点 | `task`、`gen`、`primary`、`helpers`、`reason`（非空表示迁移，写明原因） |
| `task_adopted`、`task_reschedule`、`task_cancelled`、`task_stop`、`task_refused`、`task_input_stalled` | 集群主节点 | `task`、`gen` 和各自的原因字段；`task_cancelled.by` 是发起销毁的网关节点，或 `reconcile` |
| `mass_offline`、`mass_offline_end` | 集群主节点 | `nodes`；`reason` |
| `snapshot` | 每个节点，每 10 秒（`snapshot_period`） | 在线和离线的节点、每个在线节点心跳里的 term/是否声明/任务数/执行器/推理就绪、本机测到的各条链路的 RTT 和丢失率；本节点是集群主节点时加上任务表按状态的计数 |

快照的作用是兜底：某次变化漏记了或者没有对应的事件，最多 10 秒后就能从快照里看到结果。12 个节点时一份约 0.6 KB，每天约 5 MB。

**写在哪里**：`journal_dir`（默认 `$CCCP_DATA_DIR/journal`，`run_node.sh` 把宿主机的 `/var/lib/cccp` 挂进容器）下的 `<节点名>.jsonl`，超过 20 MB 就轮转为 `<节点名>.1.jsonl`，最多保留 9 个旧文件。没有配置目录时只保留在内存里。最近 2000 条可以通过 `GET /api/ue/journal?after=<seq>&limit=<n>&snapshots=0` 读取。

**不能拖慢控制面**：`record()` 只格式化一行、放进内存和一个有界队列；写盘在单独的线程里完成，每批写完 flush，fsync 最多每秒一次（板卡可能直接断电，而 SD 卡上一次 fsync 可能要几十毫秒）。磁盘写不进去时只丢事件日志、计数并每分钟告警一次，节点照常运行。事件日志不是任何控制逻辑的输入。

**合并与时钟检查**：`merge_journal.py <目录或文件...>` 按墙钟排序，可以按任务（`--task`）、节点（`--node`，含以它为对象的事件）、事件名（`--event`）筛选。它还检查各板卡的时钟：同一次换主，所有节点在一两秒内都会记一条 `leader_changed`（第 5.5 节），所以某个节点的这些记录如果总是离其他节点很远，它的时钟就偏了，工具会报出估计的偏差（至少要有 3 个节点记录了同一次换主才能判断是哪一个偏了；只有两个节点时只报两者相差多少）。

不包括的：推理结果和图像的录制（第 10.3 节第 3 条）、指标（Prometheus）、把各板卡的事件日志自动收集到地面站。

## 3 状态模型

### 3.1 系统里有哪些状态

分布式系统设计的核心问题是：每一份状态**存在哪里、谁写、谁读、丢了怎么办**。下表列出了控制面的全部状态（接入层的 `TaskStatus` 和事件缓存不在此表中，见第 2.7 节）。

| 状态 | 内容 | 存在哪里 | 谁写 | 谁读 | 丢了怎么办 |
|---|---|---|---|---|---|
| **节点心跳** `NodeStatus` | 身份、选主声明、就绪、资源、链路、任务摘要 | 每个节点各自发布；每个节点都缓存全集群的最新值 | 每个节点只写自己的 | 所有节点 | 1 秒后下一条覆盖 |
| **任务全量** `TaskList` | 本节点所有任务的完整 `TaskState`、墓碑 | 每个节点各自发布；每个节点都缓存全集群的最新一份，离线节点的保留 5 分钟 | 每个节点只写自己的（内容来自本机执行器） | 所有节点（换主后重建任务表） | 可靠传输，丢了重传 |
| **期望状态**：任务表 `TaskRecord` | 应该有哪些任务、由谁执行、处于什么状态 | **只在集群主节点内存** | 只有集群主节点的控制器和本机网关 | 集群主节点 | 换主后由实际状态重建；还没落到执行者身上的部分丢失 |
| **实际状态**：`TaskState` | 某个节点正在运行的某个任务（含完整规格） | 各执行器内存；摘要随心跳广播，全量随 `TaskList` 发布 | 执行器 | 集群主节点（对账）、所有节点（缓存） | 执行器进程挂了，它的任务就真的没了，对账会重新调度 |
| **墓碑** | 执行器因销毁而停止的任务 | 各执行器内存；随 `TaskList` 发布 | 执行器 | 集群主节点（接收任务时） | 执行器重启后丢失（第 10.1 节） |
| **执行事件** `ExecEvent` | 执行状态变化、命令回执 | 消息流，不存储 | 执行器 | 集群主节点 | 丢了由对账补上 |
| **本地辅助状态** | 链路测量、执行栅栏、对账计时等 | 各节点内存 | 本节点 | 本节点 | 重启后从头开始，只会让决策晚一点 |

整个系统的设计可以归结为一句话：**期望状态集中、短命；实际状态分散、可靠；两者每秒对一次账。** 这和 Kubernetes 的控制器模式是一样的，区别是我们的“期望状态”不持久化，丢了就从实际状态重建。

### 3.2 节点心跳 `NodeStatus` 和任务全量 `TaskList`

0.2 的 `NodeStatus` 同时承担心跳、选主、资源、链路和完整任务列表，每条 1～4 KB，超过一个链路层帧。0.3 按“每秒都要发的尽量小，大的只在变化时发”拆成两条消息（字段定义见附录 C）。

**心跳 `NodeStatus`**：每个节点每秒发布一条，所有节点都订阅（BEST_EFFORT；发布端 KEEP_LAST(1)，订阅端 KEEP_LAST(32)，见第 2.5 节）。

| 作用 | 字段 | 读的人用它做什么 |
|---|---|---|
| 心跳 | `node_id`、`incarnation`、`seq` | 5 秒收不到就判定离线；`incarnation` 变了说明节点重启过；`seq` 的空洞用来算丢包 |
| 选主声明 / 租约 | `leader_id`、`term`、`is_leader`、`visible_peers` | 选主（第 5 章）；集群主节点的每一条心跳都是一次续约 |
| 就绪 | `executor_alive`、`inference_ready`、`algorithms_ready` | 调度器过滤；`executor_alive=false` 时不派新任务，已有任务宽限后迁移（第 2.4 节） |
| 任务摘要 | `tasks[]`（`TaskBrief`：`task_id`、`epoch`、`assign_term`、`role`）、`tasks_version` | 对账的“实际状态”；`tasks_version` 和 `TaskList` 对应 |
| 资源（慢变，每 5 条附带一次） | `load[]`（`NodeLoad`：`cpu_cores`、`mem_total_mb`、`gpu_mem_total_mb`、各项使用率、电量） | 调度器过滤和评分。Jetson 的 `gpu_mem_total_mb` 填 0，表示 GPU 和系统共享内存；未知的值填 -1 |
| 链路（慢变，每 5 条附带一次） | `links[]`（`LinkQuality`：对端编号、量化后的 RTT/抖动/丢包、回显字段） | 调度器的网络评分；回显字段用于对端计算 RTT（第 8.4 节） |

心跳仍然**每一条都自包含**：收到任意一条，就知道这个节点此刻在不在、认谁当集群主节点、在跑哪些任务（摘要），不依赖之前的消息，所以可以用 BEST_EFFORT。资源和链路每 5 条附带一次（`slow_fields_every`），其余时候为空数组。调度只需要“好/中/差”这种粗粒度判断；新集群主节点在 5 秒预热期内，也一定能收到每个节点至少一份资源和链路信息。

**大小估算**（不含协议头）：

| 情况 | 大小 |
|---|---|
| 普通的一条（4 个任务） | 约 170 B |
| 带慢变部分的一条（加 1 条负载、11 条链路） | 约 290 B |

加上 RTPS/UDP/IP 头约 100 B，都能装进一个链路层帧。

**任务全量 `TaskList`**：本节点所有任务的完整 `TaskState`（含规格、幂等键、分工）和墓碑。只在内容变化时发布（RELIABLE、TRANSIENT_LOCAL），所以超过一帧也没关系，丢了会重传；新订阅者或重新连上的订阅者一订阅就能拿到每个节点的最新一份，不需要每秒重发几 KB 的规格。

- 本节点的任务列表或墓碑每变化一次，`tasks_version` 加 1，心跳和 `TaskList` 带同一个值。
- 接收任务（Adopt）时需要完整规格，从 `TaskList` 取。如果心跳的 `tasks_version` 比本地缓存的 `TaskList` 新，说明新版本还在路上，这一轮先不接收这个节点的任务，下一轮再说。
- `TaskList` 还带 `node_name`，让每个节点能把节点编号对应到节点名（命名空间、日志、`ros://` 地址用的都是节点名）。这个字段是整理 0.3 时补充的。

0.2 中只用于显示的 CPU/GPU 型号字符串和 `stamp`，不再出现在控制面消息里。

### 3.3 期望状态：任务表

任务表（`core/task_table.py`）的每条记录 `TaskRecord`：

| 字段 | 含义 |
|---|---|
| `task_id` | UUID，集群主节点在接受任务时生成。控制面消息里是 16 字节二进制，对外接口里是字符串 |
| `idempotency_key` | 幂等键。任务表维护“键 → task_id”的索引，同一个键只对应一个任务 |
| `spec` | 任务规格 `TaskSpec`：类型、协同模式、辅助节点数、资源需求、输入地址、参数，以及预留的 `priority`、`preemption_policy`（见下文） |
| `name` | 任务名；为空时自动生成为 `<类型>-<task_id 前 8 位>` |
| `status` | `Pending` / `Scheduled` / `Running` / `Finished` / `Failed` / `Cancelled` |
| `epoch`、`assign_term` | 执行代次（第 3.8 节） |
| `primary`、`helpers` | 当前代次的任务主节点和辅助节点（节点编号） |
| `error_code`、`error_message` | 失败原因 |
| `last_event`、`submitted_ms`、`updated_ms` | 给人看的最近事件和时间 |

**写入规则**：

- 唯一的写入口是 `apply(command)`，命令有 8 种：`Submit`、`Adopt`、`Assign`、`Requeue`、`ReportStatus`、`MarkFailed`、`Cancel`、`Prune`。记录不可变，每次修改生成新记录。`control/task_store.py` 负责加锁。
- 只有集群主节点的控制器和本机网关可以写任务表；其他节点的网关一律通过 `Request` 交给集群主节点。
- 每次**当选**时，任务表从空开始，预热结束后通过 `Adopt` 重建（第 4.9 节）。在任的集群主节点因为看到更高的 term 而提升自己的 term（第 5.3 节）不算当选：它一直在任，保留任务表、等待中的请求和就绪状态，只是之后的命令改用新任期。选主结果里的 `claimed_term`（本次在任是以哪个任期声明的）用来区分这两种情况。重建时：
  - `Adopt` 只接收比任务表中更新（执行代次更大）的版本；
  - **接收时保持 `assign_term` 不变**。接收只是“认领”，不是重新分配；如果改成自己的任期，执行代次就变了，执行器会认为是新会话而重启任务；
  - 幂等键已经被另一个任务占用，就拒绝接收；
  - 任何节点的 `TaskList` 里有这个任务的墓碑，就接收为 `Cancelled` 记录（第 4.5 节）。
- 改变执行代次的命令（`Assign`、`Requeue`）把 `epoch` 加 1，同时把 `assign_term` 设为当前任期。
- `Assign`、`Requeue`、`MarkFailed` 都带 `expected (epoch, assign_term)`，按“比较后再修改”的方式执行：任务已经不在这个代次了，命令就失败（`STALE_EPOCH`）。这样，基于同一份视图做出的两个决策，最多只有一个生效。
- **先写任务表，后下发**：调度结果必须先写进任务表，再发布 `Command`。这样在当前任期内，任务表总是领先于实际执行情况，对账才有依据。
- 每次修改产生一条 `StatusEvent`（带本任期内的序号 `seq`），供接入层发布为 `TaskStatus`。控制面不依赖它。

**状态机**：

```
            ┌─────────────── requeue(代次+1) ◄──────────────┐  下发被暂时拒绝，或重新调度时没有可用节点
            ▼                                               │
Pending ──assign(代次+1)──► Scheduled ──Running──► Running ──Finished──► Finished
   │                          │  ▲                    │
   │                          │  └──assign(代次+1)────┤  任务主节点离线 / 执行器卡住 / 丢失任务 / 迟迟不启动
   ▼                          ▼                       ▼
 Failed                     Failed                  Failed
（Pending 超时，            （执行器以 INVALID_INPUT   （任务主节点报告 FAILED）
  NO_FEASIBLE_NODE）         等永久错误拒绝：DISPATCH_FAILED）

（任务表不知道的运行中任务）──adopt──► Running（有墓碑时为 Cancelled）
任何非终态 ──destroy──► Cancelled
终态：Finished / Failed / Cancelled，之后不再变化
```

- **单调性**：定义状态序 Pending=0、Scheduled=1、Running=2、终态=3。`(epoch, assign_term, 状态序)` 按字典序**只增不减**，会让它变小的更新一律忽略。重新调度和 `Requeue` 让状态“往回走”，但同时把 epoch 加 1，所以整体仍然增大。
- **命令被拒绝时的处理**（执行器回 `ExecEvent REJECTED`，第 3.5 节）：
  - `INVALID_INPUT`、`UNSUPPORTED_VERSION` 是永久错误，直接判定 Failed（`DISPATCH_FAILED`）；
  - `BUSY`、`NOT_READY` 执行 `Requeue`，并在 60 秒内避开这个节点；
  - `STALE_TERM` 说明执行器见过更高的任期，自己已经不是集群主节点，什么也不做；
  - `STALE_EPOCH` 说明命令已经过期，忽略。
  
  任务主节点和辅助节点的拒绝都按这个规则处理；整体 `Requeue` 后，旧代次已经启动的参与者由对账停掉。0.2 中“下发调用超时 → Requeue”的路径不再存在：回执丢了由心跳兜底（第 6.1 节）。
- **运行中没有输入**：任务主节点超过 `input_timeout`（10 秒）收不到一帧，执行器上报 `FAILED`（`NOT_READY`）并停掉任务。集群主节点不把它记为终态，而是执行 `Requeue`，并在 60 秒内避开这个节点（换个节点也许能取到数据）；同一个任务累计 `max_input_stalls`（3）个任务主节点都没有输入，或者任务用 `request_node` 指定了节点，才判定 Failed（`NOT_READY`）。辅助节点不做这项检查，因为只有任务主节点的事件能驱动任务状态。计数只在集群主节点内存里，换主后重新计。
- **`request_node` 是硬性指定**：被指定的节点挂掉后，任务不会迁移到其他节点。不指定节点的任务会迁移。

**优先级（预留）**：

- `priority`：uint8，**数值越大越重要**，默认 0。档位约定：0 普通、100 重要、200 紧急，中间留出空间以后细分。方向写死，以后不能改。
- `preemption_policy`：uint8，0 表示不抢占别人（默认），其他取值预留。
- 两个字段放在任务规格里，内部随 `spec_json` 传递，以后再加任务属性不用改接口；只有对外的创建接口需要显式列出。
- **当前版本只透传，不影响调度的过滤、评分，也不抢占**。唯一用到它的地方是待调度队列的顺序：优先级从高到低，相同时按提交时间先后（第 8.1 节）。

**为什么任务表不复制给其他节点**：见第 9 章 D3。简单说，复制它需要共识协议；而它里面真正不可替代的信息（还没跑起来的任务、历史）用幂等重试和 UE 侧保存就能弥补。

### 3.4 实际状态：`TaskState`

执行器对它正在运行的每个任务，在 `ExecutorStatus.tasks` 中上报一条 `TaskState`。控制进程把它原样放进本节点的 `TaskList`，并从中提取摘要（`TaskBrief`）放进心跳。

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| `task_id`、`epoch`、`assign_term` | 哪个任务的哪个执行代次 | 对账的主键 |
| `role` | 任务主节点或辅助节点 | 区分任务主节点和辅助节点的副本 |
| `primary_node`、`helper_nodes` | 这一代的完整分工（节点编号） | 新集群主节点只看到辅助节点的副本时，也能恢复出任务主节点是谁 |
| `idempotency_key` | 幂等键 | 换主后重建“键 → task_id”索引，否则调用方重试会创建重复任务 |
| `name`、`spec_json` | 名称和完整规格（含 `priority` 等预留字段） | 换主后能完整恢复任务表记录，之后还能重新调度 |

`TaskState` 本质上是“执行者持有的任务表副本”，只不过每个执行者只持有自己参与的那几行。所有执行者的 `TaskState` 拼起来，就是“所有正在运行的任务”这部分任务表。

心跳只带 `TaskBrief`（每条约 28 B），足够对账判断“谁在跑哪个任务的哪个代次”；需要完整规格时（接收任务），才去读缓存的 `TaskList`。

### 3.5 执行事件 `ExecEvent`

`ExecEvent`（`/cluster/exec_event`，执行器 → 集群主节点）是 0.2 `TaskReport` 的升级版：除了通知执行状态变化，还承担命令回执，取代 0.2 中 Service 的回复。

| 种类 | 什么时候发 |
|---|---|
| `RUNNING` | 任务已在运行；也是 START 的成功回执，收到重复的 START 时再回一次 |
| `REJECTED` | 拒绝了命令，原因见 `error_code`（`STALE_TERM`、`STALE_EPOCH`、`BUSY`、`NOT_READY`、`INVALID_INPUT`、`UNSUPPORTED_VERSION`） |
| `FAILED` | 运行中失败（`INFERENCE_ERROR`、`INSUFFICIENT_PEERS` 等；任务主节点收不到输入帧时为 `NOT_READY`，处理见第 3.3 节） |
| `STOPPED` | 已停止；也是 STOP 的回执，任务本来就没在跑也回这个 |
| `FINISHED` | 预留：给以后有终态的任务 |

回执原样带回命令的 `term` 和 `request_id`；主动上报（例如 `FAILED`）时 `request_id` 填 0。

`ExecEvent` 是“快速通道”，心跳的任务摘要是“兜底通道”：

- 正常情况下，执行器启动任务后马上回 `RUNNING`，集群主节点几毫秒内就把任务表更新为 Running，然后回复请求方。
- 如果 `RUNNING` 丢了，下一轮对账发现“任务表说 Scheduled，但节点心跳说在跑”，就由集群主节点代为提交 `ReportStatus(Running)`（对账动作 `ConfirmRunning`）。

心跳和 `TaskList` 描述“现在是什么状态”（水平信号）；`ExecEvent` 描述“刚刚发生了什么”（边沿信号）。边沿信号丢了，由水平信号兜底。

处理规则：

- 集群主节点按 `(node_id, incarnation)` 记录每个执行器最后一条事件的 `seq`，重复或乱序的事件丢掉。
- 只有任务主节点的事件能驱动任务状态。辅助节点的事件、`STOPPED` 确认、对终态任务的迟到事件都只记录，不改变状态。两个例外：辅助节点的 `REJECTED` 按第 3.3 节的规则处理；销毁时，集群主节点用各参与者的 `STOPPED` 判断它们是否已经停止（第 4.5 节）。
- 执行代次小于任务当前代次的事件一律丢弃（`STALE_EPOCH`）。

### 3.6 本地辅助状态

| 状态 | 在哪里 | 内容 | 丢了的后果 |
|---|---|---|---|
| 集群视图 `ClusterView` | 每个节点的控制进程 | 每个节点最新的 `NodeStatus`、最新的 `TaskList`，以及**本地**收到它们的时间。**离线节点的条目保留 `offline_retain_s`（5 分钟）**；节点以新的 `incarnation` 回来时丢弃旧条目；离线后回来的节点不论 `incarnation` 大小都接受（第 3.8 节） | 重启后 5 秒内视图不完整，所以选主有启动等待 |
| 链路估计 `LinkEstimator` | 每个节点的控制进程 | 每个对端的 RTT、抖动、丢包窗口 | 重新测量，调度器在测出之前用默认值 |
| 选主状态 `Election` | 每个节点的控制进程 | 自己认的集群主节点、任期、最近一次看到声明的时间 | 重启后重新等待和跟随 |
| 执行器监视 | 每个节点的控制进程 | 最后一次收到 `ExecutorStatus` 的时间和内容（任务、墓碑、执行器的 `incarnation`） | 重启后重新等待 |
| 执行栅栏 `ExecutionGuard` | 每个执行器 | 见过的最大 `term`、每个任务当前的执行代次 | 执行器重启后最大 term 归零（第 10.1 节的已知限制） |
| 墓碑 | 每个执行器 | 因销毁而停止的任务，保留 `tombstone_ttl_s`（10 分钟），最多 16 条 | 执行器重启后丢失（第 10.1 节） |
| 对账记忆 `LeaderMemory` | 集群主节点 | 每个任务何时下发、何时发现缺失、何时发过 STOP；每个节点 `executor_alive` 变为 false 的时间；最近一段时间内被判离线的节点（大面积离线保护，第 4.9 节） | 换主后重新计时，决策晚几秒 |
| 失败节点表 | 集群主节点 | 某任务在某节点上被拒绝启动或没有输入的时间（60 秒内避开）；每个任务没有输入的次数 | 换主后可能再试一次那个节点 |
| 等待中的请求 | 集群主节点 | 每个还没回复的 `Request` 的标识 `(origin_node, origin_incarnation, request_id)` 和截止时间 | 换主后丢失；网关超时，调用方重试 |
| 事件缓存 `EventLog` | 每个节点的 UE 后端（接入层） | 最近 2000 条事件（状态变化、逐帧结果） | UE 可以重新查询 |

### 3.7 只存在于集群主节点内存里的信息

这一节回答“集群主节点挂了到底丢什么”：

| 信息 | 换主后能否恢复 | 后果 |
|---|---|---|
| 正在运行的任务（Running） | **能**，从各节点的 `TaskList` 恢复 | 无 |
| 已调度、已在执行者上启动的任务（Scheduled，但实际已在跑） | **能**，同上，接收后状态是 Running | 无 |
| 集群主节点自己正在执行的任务 | **能**，从其他节点缓存的它最后一份 `TaskList` 恢复 | 它的任务主节点（就是旧集群主节点）已离线，所以会被重新调度，**从头开始**（第 6.2 节） |
| 已销毁、但还没全部停止的任务 | **能**，从墓碑恢复为 Cancelled | 剩余的副本被停掉 |
| 已调度、但 START 还没到执行者的任务 | 不能 | 丢失；调用方的请求会收到失败，用同一个幂等键重试 |
| 排队中的任务（Pending） | 不能 | 同上 |
| 刚创建、还没调度的任务 | 不能 | 同上。0.3 在下一个控制周期（≤ 100 ms）就调度，这个窗口比 0.2 小得多 |
| 已结束任务（Finished/Failed/Cancelled）的历史 | 不能 | 查询返回 `NOT_FOUND`；需要的话由 UE 保存 |
| 已结束任务的幂等键 | 不能 | 换主后用同一个键重试，会创建一个新任务（因为旧任务已结束，这通常也是期望的行为） |
| 对账计时、失败节点表、等待中的请求 | 不能 | 只会让决策晚一点；等待中的请求由网关超时后重试 |

“不能”的那几类任务（下发途中、排队中、刚创建）的共同点是：**任务还没有落到任何一个执行者身上**。这类任务统一按“下发失败”处理，由调用方重试。这是整个设计中最关键的一次简化（第 9 章 D4、D5）。

### 3.8 标识

| 标识 | 生成方式 | 规则 |
|---|---|---|
| `node_id` | 部署时配置，1～254；默认从节点名末尾的数字推导（`edge-07` → 7） | 集群内唯一，由部署保证；运行时如果同一个编号出现两个交替的 `incarnation`，记录错误日志 |
| `task_id` | 集群主节点在接受任务时生成 UUID | 全局唯一，不依赖计数器，换主后也不会重复。控制面消息里是 16 字节二进制，对外接口里是字符串 |
| `epoch` | 每次（重新）调度时加 1 | 首次调度时为 1；换主后沿用执行者上报的值 |
| `assign_term` | 每次（重新）调度时设为当前任期 | 换主后接收任务时**不变** |
| `term` | 选主时取“已知最大 term 加 1” | 只增不减 |
| `request_id` | `Command`：集群主节点在 `(leader_id, term)` 内递增；`Request`：请求方在 `(origin_node, origin_incarnation)` 内递增 | 把回执、回复对应到命令、请求 |
| `TaskStatus.seq`（接入层） | 集群主节点在本任期内的变更序号 | 订阅方按 `(term, seq)` 去重和排序；换主后从 1 重新开始 |
| `incarnation` | 进程启动时的 Unix 毫秒 | 用来判断节点或执行器是否重启过 |
| PKCT 会话 ID | `task-<task_id>-<epoch>-<assign_term>` | 不同执行代次是不同的会话 |
| 幂等键 | 调用方生成，格式见下文 | 同一个“意图”的重试沿用同一个键 |

下面解释几个不直观的点。

**`task_id` 为什么是 UUID**：没有复制的计数器，换主后新集群主节点不知道旧的计数器到了多少；用 UUID 就不需要知道。代价是 UE 侧要把 task_id 当字符串处理。

**`term` 和执行代次的区别**：

| | `term`（任期） | 执行代次 `(epoch, assign_term)` |
|---|---|---|
| 属于谁 | 集群主节点 | 任务 |
| 何时变化 | 选出新的集群主节点时 | 任务每次（重新）调度时 |
| 防的是什么 | **过期的集群主节点**继续下发或停止任务 | **过期的执行会话**继续上报状态和结果 |
| 谁来检查 | 执行器（`ExecutionGuard`） | 执行器、任务表、结果的汇总方 |
| 例子 | 旧集群主节点从网络隔离中恢复，向某个执行器发 STOP，执行器已经见过更高的 term，拒绝 | 任务主节点 A 掉线，任务以代次 (2, 4) 迁移到 B；A 恢复后还在发代次 (1, 4) 的结果，汇总方丢弃 |

换主不改变执行代次：新集群主节点接收任务时沿用执行者上报的 `(epoch, assign_term)`，任务不重启。迁移任务不改变 term：同一个集群主节点在任期内可以多次重新调度。

**为什么执行代次要带 `assign_term`**：两个集群主节点短暂并存时，如果都对同一个任务做了重新调度，0.2 中会在两个节点上各出现一份 epoch 2 的副本：两者都是任务主节点，都能通过 epoch 栅栏，PKCT 的会话 ID 也相同，汇总方会把两份结果都当成有效的。带上做调度的那个集群主节点的任期后，两份副本的代次就不同了（例如 (2, 4) 和 (2, 5)），执行器、汇总方、对账都能分出新旧。

**执行器怎么检查命令**（`core/execution_guard.py`）：执行器记录自己见过的最大 term，以及每个任务当前的执行代次。收到 `Command` 后依次检查：

| 收到的命令 | 处理 |
|---|---|
| 自己不在 `targets` 里 | 忽略 |
| `term` < 已知的最大 `term` | 回 `REJECTED`（`STALE_TERM`） |
| START：同一 `task_id`、同一代次，任务已经在运行 | 回 `RUNNING`（幂等，所以集群主节点可以放心重发） |
| START：同一 `task_id`、更大的代次 | 先停掉旧会话，再按新代次启动 |
| START：同一 `task_id`、更小的代次 | 回 `REJECTED`（`STALE_EPOCH`） |
| START：本节点实际运行的任务数（不含同一 `task_id` 的旧会话）已经达到 `max_tasks_per_node` | 回 `REJECTED`（`BUSY`） |
| STOP：本节点运行的代次不大于命令里的代次 | 停止会话，回 `STOPPED` |
| STOP：本节点运行的代次比命令里的新 | 回 `REJECTED`（`STALE_EPOCH`），不停新会话 |
| STOP：任务本来就不在运行 | 回 `STOPPED`（幂等） |
| STOP 的原因是 `CANCEL` | 无论任务是否在运行，都留一条墓碑 |

**为什么执行器要自己做准入检查**：调度器的容量过滤按任务表统计每个节点已分配的任务数。但有好几种情况会让这个数字是错的：短暂出现两个集群主节点、两边各自往同一个节点派任务；新集群主节点刚接收完任务，统计还不完整；节点上有一份因为 STOP 没送到而残留的副本。执行器按自己**实际**运行的任务数检查，是最后一道防线，保证再乱的情况下也不会把一块板卡压垮。

集群主节点处理 `ExecEvent`、汇总方处理 `TaskResult` 时，同样丢弃代次小于任务当前代次的消息；`TaskResult` 因此增加 `assign_term` 字段。

**幂等键**：调用方为每个“意图”生成一个键，重试时沿用。在这个设计里，幂等键是调用方重试时避免重复执行的唯一手段。格式按触发来源区分（第 4.8 节）：

| 来源 | 格式 | 由谁生成 |
|---|---|---|
| manual | `manual:<客户端ID>:<UUID>` | UE 或前端在每次用户操作时生成一次 |
| schedule | `schedule:<规则ID>:<计划触发时刻的 Unix 毫秒>` | 集群主节点上的定时器 |
| chain | `chain:<父任务ID>:<规则名>[:<frame_id>]` | 父任务的任务主节点 |
| event | `event:<节点名>:<事件源>:<事件序号>` | 产生事件的节点 |
| 为空 | `anon:<UUID>` | 网关自动生成；这样的请求无法去重 |

注意：同一个键对应的任务**失败之后**，在它被清理（1 小时）之前，再用这个键提交只会返回那个失败的任务；想重新来一次，需要用新的键。

**`incarnation`**：进程启动时的 Unix 毫秒。同一个节点编号的 `incarnation` 变了，说明进程重启过，它的 `seq` 从头开始，链路测量和事件去重都要重置，集群视图里它的旧条目（包括缓存的 `TaskList`）也要丢弃。执行器有自己的 `incarnation`（在 `ExecutorStatus` 和 `ExecEvent` 里），用来判断执行器是否单独重启过。

**不能假设 `incarnation` 只增不减**：板卡没有 RTC 电池、外场又没有 NTP 时，重启后系统时钟回到出厂时间，新的 `incarnation` 比旧的小。所以集群视图的规则是：节点在线时，比当前小的 `incarnation` 是重启前迟到的消息，丢掉；节点离线后，不论大小都算新的一轮。被替换掉的 `incarnation` 记下来（每个节点最近 8 个），之后再出现也丢掉，免得旧一轮迟到的消息被当成又一次重启。离线前就到达的新一轮 `TaskList` 先暂存，等它的心跳被接受时再装上（`TaskList` 只在变化时发，丢了就不会再来）。链路测量对端沉默 10 秒后自动重置，不需要单独处理。执行器的 `incarnation` 只做相等比较，不受影响（“实现时的调整”第 23 条）。

## 4 关键流程

### 4.1 创建任务

```
UE         网关(edge-07)              集群主节点(edge-01，term 4)            执行器(edge-04, edge-05)
 │ POST /tasks │                            │                                        │
 │────────────►│ 1 校验和规范化规格           │                                        │
 │             │ 2 自己不是集群主节点：       │                                        │
 │             │   发布 Request              │                                        │
 │             │   target_leader = 1         │                                        │
 │             │──── /cluster/request ─────►│ 3 Submit：生成 UUID，Pending              │
 │             │                            │   （键已存在：直接返回原任务，duplicate）  │
 │             │                            │ 4 下一个控制周期（≤ 100 ms）：             │
 │             │                            │   调度 → Assign：代次 (1, 4)，Scheduled   │
 │             │                            │   （先写任务表，再下发）                   │
 │             │                            │ 5 Command START，targets = [4, 5]        │
 │             │                            │──────── /cluster/command ──────────────►│ 6 栅栏、准入检查
 │             │                            │                                        │   订阅输入、建会话
 │             │                            │◄──── /cluster/exec_event: RUNNING ──────│
 │             │                            │ 7 ReportStatus → Running                │
 │             │◄──── /cluster/reply: OK ───│                                        │
 │◄── 200 ─────│                            │                                        │
```

步骤说明：

1. **校验**（`normalize_spec`）：类型、模式、辅助节点数和 `target_nodes` 是否匹配、链式触发的深度、资源需求的范围、`params_json` 是否合法（PKCT 必须有 bbox）、输入地址能否解析、`priority` 和 `preemption_policy` 是否在取值范围内、任务名是否超过 64 个字符。不合法直接返回 `INVALID_INPUT`，不打扰集群主节点。`ros://` 地址会自动把 `input_node` 设为数据所在节点。
2. **路由**（`Gateway._route`）：
   - 自己是集群主节点且预热完毕 → 本地处理，直接交给本机控制器；
   - 知道集群主节点是谁 → 发布 `Request`（`target_leader` 填它的编号），等对应的 `Reply`，最多 `request_timeout_s`（15 秒 = 等待时间 10 秒 + 5 秒余量）；
   - 当前没有集群主节点 → 立即返回 `NO_LEADER`。

   集群主节点收到 `Request` 时：自己不是 `target_leader` → 忽略；自己是 `target_leader` 但已经不是集群主节点 → 立即回复 `NOT_LEADER`，让网关马上返回 503，不必等满超时；自己刚当选、还在预热 → 回复 `NO_LEADER`。
3. **Submit**：幂等键已存在，就直接返回那个任务（`duplicate=true`），然后同样等它跑起来。
4. **调度**：控制器在下一个控制周期（10 Hz，≤ 100 ms）就为新的 Pending 任务调度，不等每秒的对账；每秒的对账仍然兜底。多个 Pending 任务按优先级从高到低、相同时按提交时间先后处理（第 8 章）。选中后先 `Assign`（写任务表，代次为 `(epoch + 1, 当前任期)`），再下发。
5. **下发**：发布**一条** START `Command`，`targets` 为任务主节点加所有辅助节点。每个执行器按 `primary_node` 和 `helper_nodes` 判断自己的角色，各自回一条 `ExecEvent`。协同任务的下发因此天然是并行的。
6. **执行器**：先检查目标、term、执行代次、容量（第 3.8 节），再检查算法是否就绪、能否获得输入，然后建立会话、订阅输入，回 `RUNNING`。
7. **等待**：集群主节点在任务表上等待，直到任务变成 Running 或终态，最多 10 秒（`create_wait_timeout_s`），然后发布 `Reply`。集群主节点不为等待中的请求占用线程，只记下请求的标识。

**创建请求的所有可能结果**：

| 情况 | 返回 | HTTP | 调用方应该 |
|---|---|---|---|
| 任务已在运行 | 成功，`task_id`、`assigned_node`、`dispatched_nodes` | 200 | — |
| 同一个键的任务已经在运行 | 成功，`duplicate=true` | 200 | — |
| 规格不合法 | `INVALID_INPUT` / `CHAIN_TOO_DEEP`，没有 task_id | 400 | 修正请求 |
| 没有集群主节点 / 正在选主 / 新集群主节点在预热 | `NO_LEADER`，没有 task_id | 503 | 退避后重试（同一个键） |
| 请求发给的集群主节点已经让位 | `NOT_LEADER`，没有 task_id | 503 | 退避后重试（同一个键） |
| 10 秒内没跑起来（排队、命令被暂时拒绝后重试中） | `TIMEOUT`，**带 task_id** | 503 | 用同一个键重试；跑起来后会返回原任务 |
| 等待期间集群主节点挂掉 | 网关等不到 `Reply`：`TIMEOUT`，没有 task_id | 503 | 用同一个键重试 |
| 没有可用节点（Pending 超过 8 秒） | `NO_FEASIBLE_NODE`，带 task_id | 502 | 调用方决定 |
| 执行器拒绝（规格错误等永久错误） | `DISPATCH_FAILED`，带 task_id | 502 | 检查规格 |
| 任务启动后立即失败 | `TASK_FAILED`，附执行器报告的错误码，例如 `INFERENCE_ERROR` | 502 | 调用方决定 |

`pending_timeout_s`（8 秒）故意比等待时间（10 秒）短：找不到节点时，调用方能在等待时间内拿到明确的 `NO_FEASIBLE_NODE`，而不是含糊的 `TIMEOUT`。

**为什么只有“跑起来”才算成功**：如果“写入任务表”就算成功，集群主节点在下发前挂掉，任务就凭空消失了，而调用方以为已经成功。现在的语义是：成功意味着任务已经在某个执行者上，它的存在由执行者保证；失败意味着调用方需要重试，重试是安全的，因为有幂等键。

**正常耗时估算**（尚未在真实环境测量）：

| 环节 | 耗时 |
|---|---|
| 网关发布 `Request` 到集群主节点 | 约半次往返 |
| 等控制器下一个周期 | ≤ 100 ms |
| 调度计算 | 毫秒级 |
| 发布 START 到所有参与者 | 约半次往返 |
| 执行器启动：栅栏检查、订阅输入 | 本机输入是毫秒级；跨节点输入要等 DDS 端点发现，无线网络上可能是几百毫秒 |
| `RUNNING` 回到集群主节点，`Reply` 回到网关 | 约一次往返 |

链路往返在 20～50 ms 时，普通任务约 0.1～0.3 秒；需要跨节点订阅输入的协同任务会慢一些。**对 UE 来说，Running 不等于第一个结果出来了**：PKCT 还要等第一帧完成初始化。如果 UE 关心首个结果的时间，建议单独测量“创建 → 第一条 `TaskResult`”的延迟。

### 4.2 重试和幂等

```
第一次：  POST /tasks {idempotency_key: "manual:ue-3:9f1c…"}  ──►  503 TIMEOUT, task_id=T
          （任务在排队，或者集群主节点刚挂了）
重试：    POST /tasks {idempotency_key: "manual:ue-3:9f1c…"}  ──►  200, task_id=T, duplicate=true
                                                               或  200, task_id=T'（旧集群主节点
                                                                    挂了，任务 T 从未落地，新建 T'）
```

- 如果任务 T 其实已经在跑了（哪怕是旧集群主节点下发的），新集群主节点已经从 `TaskState` 中接收了它，包括它的幂等键，所以重试会命中 T。
- 如果 T 从未落到任何执行者上，新集群主节点不知道 T，就新建一个任务 T'。因为 T 不存在于任何地方，这不是重复。
- 唯一的窗口：T 的下发请求已经到达执行者、执行者正在启动，而新集群主节点恰好在这个时刻处理重试。新集群主节点会新建 T'，下一轮对账时发现 T 和 T' 的幂等键相同，判定后出现的那个为重复，停掉它（第 4.9 节对账表第 2 行）。这就是“可能短暂重复”的一个具体例子。

UE 侧需要做的事：每次用户操作生成一个键；收到 503 时退避重试，**沿用同一个键**；连不上某个节点就换下一个节点（所有节点的接口都一样）。

### 4.3 每一帧的处理

```
输入 topic ──► 执行器 _on_frame ──► 推理后端 ──► 引擎（PKCI classify / PKCT track）
   │              │ 该任务上一帧                       │
   │              │ 还没处理完：丢弃这一帧              ▼
   │                                       TaskResult ──► <ns>/task/result
   │                                       结果叠加图 ──► <ns>/task/result_image（有人订阅时）
```

- **只处理最新帧**：一个任务的上一帧还在处理时，新到的帧直接丢弃。这样任务总是处理最新的画面，延迟不会累积；PKCT 收到的帧也严格有序。
- **PKCT 的会话**：第一帧用规格里的 bbox 初始化跟踪器，之后逐帧跟踪。会话 ID 是 `task-<task_id>-<epoch>-<assign_term>`，所以迁移后的新代次是一个全新的会话，旧会话的残留不会干扰它。
- **结果带执行代次**：`TaskResult` 带 `frame_id` 和 `(epoch, assign_term)`，汇总方和子任务据此丢弃旧代次的结果。
- **失败计数**：连续失败 10 次（`max_consecutive_failures`），执行器上报 `FAILED`（`INFERENCE_ERROR`）。PKCT 初始化失败立即上报失败。
- **无输入检测**：任务主节点从启动或上一帧起超过 `input_timeout`（10 秒）收不到帧，上报 `FAILED`（`NOT_READY`）。只看帧是否到达，被丢弃的帧也算，所以推理慢不会触发。集群主节点收到后换节点重试，见第 3.3 节。
- **推理后端**（`inference.py`）：默认 `LocalBackend`，在同一进程内用线程池直接调用引擎，返回 future；设置 `INFERENCE_BACKEND=ros` 可以改走 `<ns>/algorithms/*` 服务。两种后端接口相同，集成测试各跑一遍。
- **结果的接收者**：网关只有在 UE 问到某个任务时，才订阅执行它的节点的结果 topic（`ue_backend` 的 `watch`）。如果每个节点都订阅所有结果，无线链路上会多出约 8 Mbps 的流量。

**实测推理耗时**（640×480 合成图，`tools/inference_bench.py`）：

| 设备 | PKCI P50 | PKCT P50 |
|---|---|---|
| x86 CPU，8 线程 | 20.5 ms | 24.4 ms |
| x86 CPU，不限线程（144 核） | 约 102 ms | 约 147 ms |
| RTX 4090 | 10.2 ms | 12.1 ms |

所以启动脚本里用 `OMP_NUM_THREADS`（`INFERENCE_THREADS`，默认 4）限制线程数。Orin 上的数据还要实测。

### 4.4 协同任务

| 模式          | 参与者                                   | 输入                                                          | 结果                                            | 当前实现状态                                                                                                             |
| ------------- | ---------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `local`     | 只有任务主节点                           | 按地址取                                                      | 任务主节点的结果                                | 完整                                                                                                                     |
| `redundant` | 任务主节点 + `helper_count` 个辅助节点 | **同一份输入**（必须用共享或绑定到节点的地址，第 7 章） | 最先返回的有效结果                              | 调度、下发、取数、每个参与者各自推理并发布 `TaskResult` 都已实现；**按 frame_id 选取最先有效结果的汇总尚未实现** |
| `fusion`    | 同上                                     | 各自的视角                                                    | 任务主节点汇总（PKCI `fuse`、PKCT `elect`） | 同上；**汇总尚未实现**                                                                                             |

协同任务的生命周期由任务主节点驱动：任务表只认任务主节点的状态报告。辅助节点失效时，MVP 不替换辅助节点，任务按 `min_participants`（最少有效参与数，含任务主节点）降级继续，达不到时任务主节点报告 `INSUFFICIENT_PEERS`。任务主节点失效时，整个任务（含所有辅助节点）以新的执行代次重新调度，旧代次的辅助节点副本在对账时被停掉。

协同载荷（PKCI 的 `increment`、PKCT 的 `identity`，都小于 1 KB）放在 `TaskResult.payload` 中通过 topic 传输，不放进服务请求，也不传图像。

### 4.5 销毁任务

```
UE ──DELETE /tasks/T──► 网关 ──/cluster/request(DESTROY)──► 集群主节点：Cancel → Cancelled（终态）
                                                              │ 立即发布 STOP(CANCEL)，
                                                              │ targets = 当前代次的所有参与者
                                                              ▼
                                      执行器停止会话、释放输入、留墓碑，回 ExecEvent STOPPED
                                                              ▼
                     当前代次的所有在线参与者都已确认 → Reply OK ──────────► 网关 ──► 200
                     超过 destroy_wait_timeout_s 仍未全部确认 → Reply TIMEOUT ──► 503，调用方重试
```

规则：

1. **立即下发**：Cancel 之后立即发布 STOP（原因 `CANCEL`），不等下一轮对账。
2. **确认了才算成功**：当前代次的所有**在线**参与者都确认已停止，才回复成功。确认来自 `ExecEvent STOPPED`；`STOPPED` 丢了时，心跳的任务摘要里已经没有这个任务也算确认。超过 `destroy_wait_timeout_s`（10 秒）仍未全部确认，回复 `TIMEOUT`（HTTP 503），调用方重试销毁。
3. **不等不该等的**：销毁时离线的参与者，以及旧代次的残留副本，不计入成功条件，因为它们可能在一个联系不上的节点上，等它们确认，销毁可能永远都成功不了。它们回来后，对账发现它们还在运行一个 Cancelled 任务，每 `stop_retry_s` 发一次 STOP(CANCEL)。
4. **墓碑**：执行器因 `CANCEL` 停止任务时（任务本来就不在运行也一样），在本机留一条墓碑，随 `TaskList` 发布，保留 `tombstone_ttl_s`（10 分钟）。因为迁移、去重而停止任务时不留墓碑。
5. **换主后不复活**：新集群主节点接收任务时，如果任何节点（包括离线节点缓存的 `TaskList`）有这个任务的墓碑，就把它接收为 Cancelled 记录，对账随后停掉剩余的副本。

**为什么要这样做**：0.2 中 Cancel 之后立即回复成功，真正的 StopTask 要等下一轮对账才发出。如果集群主节点在这不到 1 秒的时间里挂掉，新集群主节点会从执行器的上报中看到这个任务还在运行，就把它接收回来：任务复活了，而调用方以为它已经停了。这和创建任务的问题对称，所以用同样的标准：执行者确认了才算成功。现在的情况是：

- 换主前没有任何参与者停下：调用方没有拿到成功（`TIMEOUT` 或连接断开），重试销毁时，新集群主节点已经接收了这个任务，能找到并停掉它；
- 换主前有部分参与者停下了：它们的墓碑让新集群主节点把任务接收为 Cancelled，剩余副本由对账停掉。

任务表会随集群主节点一起消失，但“这个任务已经被销毁”记在执行器身上，而执行器在换主时不会消失。之所以接收为 Cancelled 记录、而不是干脆不接收，是为了让调用方重试销毁、查询时得到一致的结果，停掉剩余副本也走对账的常规规则。

**重复销毁**：

| 任务状态 | 返回 |
|---|---|
| Cancelled（例如上次销毁超时后重试） | 等待确认后返回成功；超时仍返回 `TIMEOUT`（503）。所以超时后重试是安全的 |
| Finished / Failed | `INVALID_STATE`（HTTP 409） |
| 不存在 | `NOT_FOUND`（404）。换主后，如果所有副本都已停止，任务不会被接收，重试销毁会得到 404，调用方可以把它视为已销毁 |

### 4.6 查询和事件流

- **查询**（`GET /tasks/<id>`）：网关发布 `Request(QUERY)`，集群主节点读任务表后回复。换主后查不到已结束的任务（第 3.7 节）。
- **事件流**（接入层，本版不修订）：`GET /events?after=<seq>&wait=<秒>`，长轮询。每个节点的 UE 后端订阅 `/cluster/task_status`，按 `(term, seq)` 去重后放进本地事件缓存。逐帧结果也会进入事件流（只针对被问过的任务）。
- **已知缺口**：只有集群主节点发布 `TaskStatus`。旧集群主节点已经应用、还没来得及发布就挂掉的那几条变化不会补发，`seq` 会跳号。UE 发现跳号时可以查询最新状态。另外，UE 从一个节点切换到另一个节点时，新节点的网关此前没有订阅这个任务的结果，切换后的一小段结果会出现空洞；UE 应该在换节点后用查询补状态。

### 4.7 HTTP 状态码

网关回复中的 `error_code` 决定 HTTP 状态码（`ue_api.py`）：

| 情况 | HTTP |
|---|---|
| 成功 | 200 |
| 可以稍后重试：`NO_LEADER`、`NOT_LEADER`、`BUSY`、`NOT_READY`、`TIMEOUT` | **503** |
| 创建：请求本身有问题，没有生成 task_id | 400 |
| 创建：任务已生成但失败 | 502 |
| 查询：任务不存在 | 404 |
| 销毁：任务不存在 | 404 |
| 销毁：任务已被销毁（Cancelled） | 确认停止后 200；超时 503 |
| 销毁：任务已经结束（Finished/Failed） | 409 |

可以重试的错误一律不能映射成 4xx：如果“没有集群主节点”返回 400，UE 按状态码判断时，会把一个只需要稍后重试的情况当成请求错误而放弃（第 9 章 D15）。

### 4.8 其他触发方式

`CreateTask.origin` 区分四种触发来源，它们走同一个创建接口，只是幂等键的生成者不同（格式见第 3.8 节）：

| 来源 | 谁调用创建接口 | 状态 |
|---|---|---|
| `manual` | UE 或前端 | 已实现 |
| `chain` | 父任务的任务主节点（检测到某个结果后触发下一个任务）：执行器调用本机网关的 `<ns>/api/task/create`，网关再按常规路径交给集群主节点；`chain_depth` 最大 5 | 接口和校验已实现；**触发规则未实现** |
| `schedule` | 集群主节点上的定时器 | **未实现** |
| `event` | 产生事件的节点 | **未实现** |

统一接口的意义在于：不管谁触发，任务的去重、调度、迁移、状态都一样，触发方只需要生成正确的幂等键。

链式任务的**数据**走发布订阅，不走存储，也不用 Action（第 9 章 D19）。父任务结束或被销毁时子任务是否级联停止，还没有定义（第 10.5 节）。

### 4.9 对账

前面几节的流程都依赖对账来兜底。对账器（`core/reconciler.py`）在集群主节点上每秒运行一次：输入是任务表（应该跑什么）、各节点心跳的任务摘要（实际在跑什么）和缓存的 `TaskList`（接收任务时需要的完整信息），输出是一组动作。规则：

| # | 观察到的情况 | 动作 |
|---|---|---|
| 1 | 某节点运行着任务表**不知道**的任务，或者执行代次**比任务表新**。“某节点”包括在线节点，以及 `offline_retain_s` 内离线节点缓存的 `TaskList` | **接收**（`Adopt`），规格取自该节点的 `TaskList`（`tasks_version` 和心跳不一致时，这一轮跳过该节点）。同一任务有多份副本时，取代次最大的；代次相同时优先取任务主节点上的那份；再相同就取编号最小的节点。任何节点有这个任务的墓碑时，接收为 Cancelled；任何节点的 `TaskList` 里有这个任务的墓碑，而任务表里它还没结束（另一个集群主节点在双主期间销毁了它），就把它改为 Cancelled。其余副本在下一轮被停掉 |
| 2 | 同上，但这个任务的幂等键已经属于任务表里的另一个任务 | 判定为重复，向该节点发送 STOP（原因 `DUPLICATE`） |
| 3 | Pending | 调度（第 8 章）。正常情况下 Submit 后的下一个控制周期已经调度过，这里是兜底。超过 `pending_timeout_s`（8 秒）仍无可用节点，判定 Failed |
| 4 | 任务主节点离线（超过 `node_offline_timeout_s` 没有收到它的心跳） | 重新调度，代次 + 1。**大面积离线保护生效时暂停**（见下文） |
| 5 | 任务主节点在线，但 `executor_alive=false` 已超过 `executor_stall_grace_s`（10 秒） | 重新调度，代次 + 1 |
| 6 | 节点在线、执行器正常，上报的任务里有它且代次一致 | 正常；如果任务表里还是 Scheduled，说明 `RUNNING` 丢了，由集群主节点代为提交 `ReportStatus(Running)`（`ConfirmRunning`） |
| 7 | 节点（任务主节点或辅助节点）在线但没有这个任务，任务状态是 Scheduled | 每隔 `dispatch_retry_s`（5 秒）用同一个代次重发 START（幂等）；超过 `start_timeout_s`（15 秒）仍未启动，重新调度 |
| 8 | 任务主节点在线、执行器正常，但没有这个任务，任务状态是 Running | 先等 `missing_grace_s`（3 秒），因为心跳可能比 `ExecEvent` 晚到；仍然没有就重新调度 |
| 9 | 某节点运行的任务在任务表中是 Cancelled | 每隔 `stop_retry_s`（5 秒）发送 STOP（原因 `CANCEL`，执行器会留墓碑） |
| 10 | 某节点运行的任务已经是其他终态、代次比任务表旧，或者并没有分配给它 | 每隔 `stop_retry_s`（5 秒）发送 STOP（原因 `STALE` 或 `UNASSIGNED`） |

- 第 1 行把离线节点缓存的 `TaskList` 也算进来，是为了救回离线节点上的任务，尤其是旧集群主节点自己执行的任务。这些任务的任务主节点离线，所以接收后会被第 4 行重新调度。离线节点的缓存只用于接收，不参与其他各行的判断。
- 如果任务主节点已经挂了、只剩辅助节点的副本，也照样接收，下一轮对账发现任务主节点离线，再重新调度。这样，迁移途中的任务不会因为换主而丢失。
- 执行器卡住（`executor_alive=false`）时，心跳里的任务列表是最后一次已知的值，所以第 8 行不会因此触发，由第 5 行按更长的宽限时间处理。
- “节点在线”和各种计时一律使用集群主节点本地的单调时钟，只保存在当前集群主节点的内存里（第 3.6 节的 `LeaderMemory`）。换主后从头开始计时，结果只是决策晚一点，不会导致非幂等的操作被重复执行。
- MVP 阶段不替换失效的辅助节点（第 4.4 节）。

**大面积离线保护**（最小版本）。集群主节点自己的无线链路变差时（飞远了、被遮挡），它会收不到大部分节点的心跳，而其他节点之间互相通信正常。在集群主节点看来，“我看不到很多节点”和“很多节点挂了”是一样的。如果照常迁移，少数还能看到的节点会被塞满；原来的副本其实还在正常运行，集群主节点发出的 STOP 又送不到它们，大量重复执行不会在几秒内被清理；而其他节点仍然能看到集群主节点的心跳，不会触发换主。

规则：在 `mass_offline_window_s`（10 秒）内，新判定离线的节点数超过窗口开始时在线节点数的 `mass_offline_ratio`（1/3），就进入保护状态：

- 暂停第 4 行（因任务主节点离线而迁移）；
- 其他动作照常：调度新任务（只放在在线节点上）、停止、确认、接收；
- 离线节点数回落到阈值以下时退出保护；持续 `mass_offline_hold_s`（30 秒）仍未恢复，也退出保护、恢复迁移，因为如果真的有大量节点同时故障，迁移不能无限推迟。

进入和退出保护状态都要打日志。阈值需要实测。完整的解决办法是集群主节点在看不到足够多节点时主动让位（第 10.3 节）：有了它，链路变差的集群主节点会在保护期内被换掉。

## 5 选主

### 5.1 为什么需要一个集群主节点

完全无主（每个节点各自决定）也是一种选择，但调度决策需要全局视图和互斥：两个节点同时看到 edge-04 空闲，都把任务派过去，edge-04 就过载了；两个节点同时收到同一个请求，就会创建两个任务。用一个集群主节点集中做这些决策，是最简单的互斥方式。代价是需要选主和换主，这就是本章的内容。

### 5.2 机制

每个节点在心跳 `NodeStatus` 中广播四个字段：

- `leader_id`：我认谁当集群主节点（可以是自己，也可以是 0 表示还没有）；
- `term`：我知道的任期；
- `is_leader`：我是否在声明自己是集群主节点；
- `visible_peers`：我判定在线的对端数，用于候选排序。

**集群主节点的每一条心跳就是一次续约**。它停止发布 5 秒后（`node_offline_timeout_s`），其他节点把它判为离线，它的声明随之失效，这相当于租约到期。

每个节点每秒发布心跳之前调用一次 `Election.update(peers, now)`，peers 是当前在线的其他节点。所有节点执行同样的确定性规则，只要视图一致，结论就一致。本版假设所有节点处在同一个广播域、互相直接可见（第 1.3 节），这是“视图一致”的前提。这个前提会被**单向丢心跳**打破：某个节点长时间收不到集群主节点的心跳，而其他节点都收得到（11-08 在真实 DDS 上出现过）。第 5.3 节的“间接证据”规则专门处理这种情况。

### 5.3 规则

（代码见 `core/election.py`。）

**支持者数量**：在本节点的视图中，所有在线节点（包括声明者本身）以及本节点自己，`leader_id` 等于 X 的个数。每个节点读到的是同样的心跳，所以只要视图一致，算出的数就一致。

**声明的排序**：多个节点同时声明时，按以下顺序比较，越大越好：

1. **支持者数量**；
2. **term**：任期更高的优先；
3. **编号更小**的优先。

**间接证据**：本节点听不到 X 的心跳，但视图里有节点把 X 报为 `leader_id`，这就是 X 在任的间接证据。X 的支持者数量同样按上面的方法计算（这些跟随者，加上 X 本身），term 取这些跟随者上报的最大值。只有支持者达到本节点视图（在线节点加本节点自己）的**过半**时，间接证据才算数。规则：

- 在任者看到排名比自己高的间接声明，就**卸任，但不跟随 X**，进入“无主”状态；
- 非在任者没有直接声明可跟随、但存在间接声明时，**不声明**，同样处于“无主”状态。

之所以“不跟随”：跟随者会在心跳里把 X 报出去，这又成了别人的间接证据。X 死掉之后，几个都听不到 X 的节点会互相引用 X，谁也不放手，集群就一直没有集群主节点。之所以要“过半”：只有少数节点还听得到的集群主节点，不应该阻止大多数节点另选一个；否则这些节点会一直无主（`test_election.py` 的 `only 03 still hears the leader 01`）。

**等候选的兜底**：同一个例子里，听不到 01 的节点要另选时，按候选排序排第一的是 03（它看得到的节点最多），可 03 还在跟随 01，永远不会宣布，大家就一直等下去。所以等候选超过 `candidate_wait_s`（10 秒）仍没有任何声明时，候选里去掉正在跟随别人的节点。不一开始就去掉，是因为集群主节点死掉时各节点超时的时刻差一两秒，先超时的节点会把还没超时的当成“在跟随”，于是好几个节点同时宣布。

没有这条规则时：B 收不到 A 的心跳、其他节点都跟随 A，于是 B 在超时后自己声明。B 永远听不到 A 的声明，也就没有让位的理由，却能从跟随者的心跳里看到 A 的 term，于是一直往上抬；A 听得到 B，也跟着抬。两个集群主节点就这样长期并存（第 10.1 节第 24 条）。仿真（各节点按自己的视图上报 `visible_peers`）：随机放 1～3 条持续的单向丢失，旧规则在 300 个例子里有 24 个最终是多主，新规则一个都没有。服务器上的情形是两个条件叠加：B 听不到 A，**而且 B 自己的心跳也时断时续**，别人看到的在线节点数降到和 B 一样，B 才会排到候选第一而宣布。只有前一个条件时，B 排在后面，旧规则也不会出事（11-08 用 iptables 在真实 DDS 上验证过）；两个条件都有时，旧规则 100 个例子全部多主，新规则没有。代价是：集群主节点死后，跟随者要多花一个心跳周期才不再报它，换主慢约 1 秒；听不到集群主节点的少数节点处于无主状态，它们的网关返回 `NO_LEADER`（这些节点本来也收不到它的命令）。

**候选的排序**（没有声明、需要有人站出来时用），越靠前越优先：

1. **有资格**：协议版本一致、推理就绪（`inference_ready`）、电量未知或不低于 `leader_min_battery`（取值待定，第 10.5 节）。如果没有任何在线节点有资格，就忽略资格条件，避免集群永远没有集群主节点；
2. **`visible_peers` 更多**；
3. **编号更小**。

`visible_peers` 由每个节点在自己的心跳里上报，所有人读到的是同一个数，而不是各自测量的结果，所以所有节点算出的排名一致。在单广播域、链路良好时，大家的 `visible_peers` 都是 11，规则退化为按编号选，和 0.2 一样；只有链路变差时它才起作用。之所以优先选连通性好的节点，是因为没有 `input_node` 的任务，网络评分以集群主节点为参照，命令和请求也都经过集群主节点（第 9 章 D21）。

**每个节点的决策**：

```
如果我是集群主节点：
    看到比我更好的声明                → 让位，跟随它
    否则，有比我更好的间接声明（过半） → 让位，不跟随任何人
    否则，看到有人上报更高的 term      → 把我的 term 提到它之上，继续担任
    否则                               → 继续担任
否则：
    有声明                             → 跟随最好的那个
    没有声明：
        term 取已知最大值
        有间接声明（过半）             → 不声明，不跟随任何人
        如果（启动后从未见过声明，且已过 startup_grace_s），
           或（上次看到声明已经过去 leader_timeout_s）：
            如果我是在线节点中候选排名第一的 → 声明自己，term = 已知最大 + 1
            否则                             → 等排名第一的那个声明
```

几点说明：

- **已在任的集群主节点不因为别人的 `visible_peers` 稍多而让位**。保留第 5.4 节“不被抢位”的规则，避免频繁换主。如果它的连通性真的很差、大家都看不到它，自然会触发换主。“看不到足够多节点时主动让位”尚未实现（第 10.3 节）。
- 不同节点判定“已经没有集群主节点”的时刻可能差一个心跳周期，期间可能有两个候选者同时声明，由声明的排序规则收敛（第 5.6 节）。

### 5.4 为什么先比支持者数量

如果只按 term 比较（像 Raft 那样“term 高的赢”），会出现这样的问题：

> edge-09 因为干扰被隔离了 30 秒。它看不到任何声明，于是自己声明为集群主节点，term 从 3 涨到 4。恢复连通后，它的 term 4 高于真正的集群主节点 edge-01 的 term 3，于是所有节点都转而跟随 edge-09，触发一次完全没必要的换主。

Raft 用 PreVote 解决这个问题，但我们评估过的 Python Raft 库 PySyncObj 不支持 PreVote（第 9 章 D2）。我们的解决方法是先比较支持者数量：edge-09 只有自己一个支持者，edge-01 有 11 个，edge-01 胜出。同时，edge-01 看到更高的 term 4，就把自己的 term 提到 5，继续担任。这一步很重要：edge-09 在隔离期间可能已经用 term 4 向某些执行器发过命令，执行器记住了 term 4；如果 edge-01 还停在 term 3，它的命令会被这些执行器拒绝。

同样的规则让网络分区恢复后**节点多的一侧胜出**，而不是编号小的一侧或者 term 高的一侧（`test_after_a_partition_the_side_with_more_nodes_keeps_its_leader`）。

**已在任的集群主节点不会被抢位**：编号更小的节点后来加入，看到已有声明就直接跟随，不会因为编号更小而取而代之（`test_new_node_follows_the_existing_leader_even_if_its_name_is_smaller`）。

### 5.5 时间线

**冷启动**：

```
t=0     12 个节点先后启动，开始广播心跳（leader_id = 0）
t=5 s   startup_grace_s 到期。候选排名第一的节点（链路良好时就是编号最小的，例如 edge-01）声明，term=1
t≈5~6 s 其他节点在下一条心跳里看到声明，跟随
t≈10 s  edge-01 的预热（warmup_s=5 s）结束，开始接受请求和对账。
        预热期间它创建 Command、Reply 的发布端和 ExecEvent、Request 的订阅端，等待 DDS 匹配
```

启动等待的作用：给每个节点 5 秒时间听一听“当前是否已经有集群主节点”。没有这个等待，一个后启动的节点可能在还没收到任何人的心跳时就声明自己。

**集群主节点故障**：

```
t=0       edge-01 掉电。它最后一条心跳发于 t∈(-1, 0]
t≈4~5 s   其他节点超过 5 秒没收到它的心跳，判为离线；它的声明随之消失
t≈5~6 s   距离最后一次看到声明已过 leader_timeout_s（1 秒），候选排名第一的存活节点 edge-02 声明，term+1
          其他节点在下一个心跳周期看到声明并跟随
t≈10~11 s edge-02 预热结束：根据各节点的 TaskList 接收所有正在运行的任务，开始对账。
          edge-01 自己执行的任务也在它最后一份 TaskList 里（各节点都缓存着），一并接收；
          它们的任务主节点已离线，下一轮对账重新调度（第 6.2 节）
```

在 t=0 到约 10 秒之间：

- 正在运行的任务**不受任何影响**，继续出结果，UE 能继续收到逐帧结果；
- 创建、销毁、查询返回 `NO_LEADER`（HTTP 503），或者网关等不到回复，超时后返回 503；
- 如果有任务主节点和集群主节点同时挂了，这些任务要等新集群主节点预热结束后才会重新调度；edge-01 自己执行的任务大约在 11 秒后在别处重新启动。

### 5.6 短时间出现两个集群主节点时

各节点的视图可能有短暂差异（例如某个节点刚好丢了几条心跳），所以可能短时间内出现两个声明者。设计不试图完全避免这种情况，而是保证它造成的后果有界：

1. **声明会收敛**：两个声明者都能看到对方时，按规则必有一方让位，通常在 1～2 个心跳周期内完成。只有一方听得到另一方时，听不到的那一方靠间接证据让位（第 5.3 节）。
2. **term 栅栏**：执行器记住见过的最大 term。只要任期较高的集群主节点向某个执行器发过任何命令，任期较低的那个就再也不能让这个执行器启动或停止任务（`STALE_TERM`）。命令是广播的 topic，执行器从发给别的节点的命令里也能看到更高的 term，栅栏收紧得更快。
3. **执行代次不重复**：两边都重新调度了同一个任务时，代次分别是 `(epoch, 4)` 和 `(epoch, 5)`，执行器、汇总方、对账都能分出新旧，重复的结果不会被当成有效结果（第 3.8 节）。
4. **执行器准入**：两边各自往同一个节点派任务，执行器按自己实际运行的任务数拒绝超额的部分（`BUSY`）。
5. **请求只被处理一次**：`Request` 带 `target_leader`，一个请求只会被网关认定的那个集群主节点处理。
6. **重复清理**：如果两边都启动了同一个请求（同一个幂等键）对应的任务，胜出的集群主节点在对账时发现两个任务的幂等键相同，停掉后出现的那个。
7. **接入层**：只有 ready 的集群主节点才发布 `TaskStatus`，而且订阅方按 `(term, seq)` 去重，所以事件流不会因为两个集群主节点而混乱（但可能有短暂的、来自较低任期的事件）。

已知不足：如果两个节点在**同一个任期号**上同时声明（视图不一致的罕见情况），它们产生的执行代次仍可能相同；这时靠第 1、6 条收敛（第 10.1 节）。

`test_controller.py` 中有两个测试专门覆盖这种情况：任期较高的一方把重复副本停掉；任期较低的一方发出的停止命令被执行器拒绝。

### 5.7 协议版本

`NodeStatus.PROTOCOL_VERSION`（0.3 为 3）不同的节点：

- 不参与选主（它的声明被忽略，它也不算支持者）；
- 不会被派发任务（调度器的硬性过滤）。

这让升级时的行为可预测：升级到一半时，新旧两个版本各自组成一个集群，互不干扰。但这不等于支持滚动升级：ROS 2 Humble 的接口不支持类型演进，新旧版本的节点本来就无法正常交换消息。所以：

- 接口包（`cccp_*`）的任何改动，都要把 `PROTOCOL_VERSION` 加 1；
- 12 个节点必须一起升级，镜像标签带上协议版本号（例如 `cccp-node:p4-<git短哈希>`）；
- 不改变已有字段的含义，需要新含义就新增字段。

正因为每次改接口都要全体升级，0.3 把能预见的字段一次性加了进去：`priority`、`preemption_policy`（在任务规格里）、`Command.leader_id`（以后做“只接受本机跟随的集群主节点的命令”时用）、`ExecEvent` 的 `FINISHED`（以后有终态任务时用）。以后启用它们只需要改逻辑。

## 6 故障处理

### 6.1 总表

| 故障 | 如何发现 | 系统的反应 | 大约多久恢复 | 残留影响 |
|---|---|---|---|---|
| 集群主节点挂掉（它没有执行任务） | 5 秒收不到心跳 | 候选排名第一的存活节点接任，预热后接收所有运行中的任务 | 5～6 秒选出，10～11 秒恢复服务 | 排队中的任务和历史丢失 |
| 集群主节点挂掉（它在执行任务） | 同上 | 同上；它执行的任务从缓存的 `TaskList` 接收后重新调度 | 同上，它的任务约 11 秒后在别处重启 | 这些任务从头开始 |
| 任务主节点挂掉 | 5 秒收不到心跳 | 对账：重新调度，代次 + 1，旧辅助节点副本被停掉 | 约 5～6 秒 | 任务从头开始（PKCT 重新初始化） |
| 辅助节点挂掉 | 同上 | MVP 不替换；任务主节点按 `min_participants` 降级或报失败 | — | 协同质量下降 |
| 执行器卡住（进程还在，`ExecutorStatus` 发不出来） | 3 秒没收到 `ExecutorStatus`，心跳 `executor_alive=false` | 不再派新任务；10 秒宽限内恢复则什么都不做，否则迁移它担任任务主节点的任务 | 约 13 秒 | 恢复后旧副本被停掉 |
| 执行器进程重启（控制进程正常） | `ExecutorStatus` 的 `incarnation` 变了，任务列表为空 | Running：等 3 秒（`missing_grace_s`）后重新调度 | 约 4 秒 | 执行器的最大 term 和墓碑归零（已知限制） |
| 控制进程重启（执行器正常） | 节点短暂离线，`incarnation` 变化 | 如果超过 5 秒，节点被判离线，它的任务被迁走；它回来后，旧副本因代次过期被停掉 | — | 可能多一次迁移 |
| `RUNNING` 事件丢失 | 对账：任务表是 Scheduled，心跳显示在跑 | 代为提交 Running | ≤ 1 秒 | 无 |
| START 命令丢失 | 节点在线但心跳里没有这个任务 | 每 5 秒用同一个代次重发（幂等）；15 秒仍未启动就重新调度 | 5～15 秒 | 无 |
| STOP 命令丢失 | 节点还在上报这个任务 | 每 5 秒重发 | 5 秒 | 多跑几秒 |
| `Reply` 丢失 / 等待期间换主 | 网关等满 15 秒 | 返回 `TIMEOUT`（503），调用方重试 | 一次重试 | 无（幂等） |
| 两个集群主节点 | 互相看到声明 | 收敛到一个；term 栅栏；执行代次区分；对账去重 | 1～2 秒 | 可能短暂重复 |
| 节点被隔离后恢复 | 它独自声明，恢复后只有一个支持者 | 它让位；现任集群主节点提升 term | 1～2 秒 | 无 |
| 集群主节点自己的链路变差 | 10 秒内超过 1/3 的节点被判离线 | 大面积离线保护：暂停迁移，其他照常 | 链路恢复后自动退出；最长保护 30 秒 | 真有大量节点故障时，迁移最多推迟 30 秒 |
| 销毁后集群主节点立即挂掉 | — | 墓碑让新集群主节点把任务接收为 Cancelled，停掉剩余副本；没拿到成功的调用方重试销毁 | 新集群主节点预热后 | 无 |
| 数据所在节点挂掉（`ros://` 输入） | 调度器发现 owner 离线 | 任务无法放置，留在 Pending，8 秒后 `NO_FEASIBLE_NODE` | — | 任务失败 |
| 节点没有配置 AirSim（`AIRSIM_HOST` 为空）却被派了 `airsim://` 任务 | 执行器启动时检查 | 拒绝启动（`NOT_READY`），集群主节点 Requeue 并换节点 | 下一个控制周期 | 无 |
| AirSim 运行中不可用（RPC 失败、仿真重启） | 取图线程报错，每 5 秒记一条警告；任务主节点 `input_timeout`（10 秒）内没有帧 | 取图线程每秒重试；执行器上报 `NOT_READY`，集群主节点换节点（见下一行） | 10 秒内恢复则无影响 | 超过 10 秒会换节点 |
| 任务主节点收不到输入帧（AirSim 不可用、`ros://` 数据所在节点的 topic 停了、本机相机停了） | 执行器：`input_timeout`（10 秒）内没有帧 | 上报 `FAILED`（`NOT_READY`）；Requeue，避开该节点换一个；累计 3 个节点都没有输入（或指定了 `request_node`）判定 Failed | 约 10 秒换一次节点，约 30 秒判定失败 | 迁移后从头开始；空输入的任务换到别的节点后读的是那个节点的相机 |

0.2 中“`StartTask` 的回复丢失 → 下发调用超时 → Requeue 并避开该节点 60 秒”的情况已经不存在：回执是 `ExecEvent`，丢了由心跳兜底（`ConfirmRunning`），不会误判为下发失败。

### 6.2 集群主节点挂掉：逐步说明

以“edge-01 是集群主节点（term 3），同时执行任务 A；edge-04 执行任务 B；edge-01 刚收到任务 C 还在排队”为例：

1. edge-01 掉电。B 继续在 edge-04 上运行，UE 能继续收到 B 的逐帧结果。
2. 约 5～6 秒后，edge-02 当选，term 从 3 变为 4，任务表清空，开始 5 秒预热（同时创建按角色的端点）。期间所有创建/查询请求返回 503。
3. 预热结束，edge-02 第一次对账：
   - edge-04 的心跳里有 B（代次 (1, 3)），任务表里没有 → 用 edge-04 的 `TaskList` **接收**，状态 Running，代次仍为 (1, 3)，B 没有重启；
   - A 只在 edge-01 上运行。edge-01 已经离线，但每个节点都缓存着它最后一份 `TaskList`（保留 5 分钟），A 在里面 → **接收**。A 的任务主节点 edge-01 离线 → 下一轮对账重新调度，代次 (2, 4)，A 在别的节点上从头开始；
   - C 只在 edge-01 的内存里，丢失。
4. 提交 C 的调用方在等待中收到失败：如果 UE 连的是其他节点，那个节点的网关最长等 15 秒后返回 `TIMEOUT`（HTTP 503）；如果 UE 直接连的就是 edge-01，则是 HTTP 连接断开。两种情况下 UE 都用同一个键重试（必要时换一个节点），edge-02 预热结束后新建 C 并调度。
5. 提交 A 的调用方不需要做任何事：A 在约 11 秒后恢复运行。但它是从头开始的（PKCT 重新初始化），而且这段时间没有结果。

0.2 中第 5 步是这个设计最大的弱点：A 丢失，而调用方并不知道。0.3 通过缓存离线节点的 `TaskList` 解决了“丢失”，剩下的是“从头开始”，与任务主节点故障时一样（第 6.3 节）。`leader_self_penalty`（10 分）仍然让调度器尽量不把任务放在集群主节点自己身上；节点充足时，集群主节点上通常没有任务。

### 6.3 任务主节点挂掉：任务迁移

1. edge-04（任务 B 的任务主节点）掉电。
2. 约 5 秒后，集群主节点（term 4）判定 edge-04 离线。对账：B 的任务主节点离线 → `Reschedule`（大面积离线保护没有生效的前提下）。
3. 调度器在剩余节点中选出 edge-06（`request_node` 指定了 edge-04 的任务**不迁移**，第 3.3 节）。`Assign`：代次 (1, 4) → (2, 4)，任务表先更新，然后下发。
4. edge-06 以代次 (2, 4) 启动 B。如果 B 的输入是 `airsim://uav_4/0`，edge-06 自己通过 RPC 去取同一个相机的画面，输入不变（第 7 章）。PKCT 的会话 ID 变为 `task-B-2-4`，用规格中原始的 bbox 重新初始化。
5. edge-04 如果之后恢复，它还在以代次 (1, 4) 运行 B，对账发现代次过期，发送 STOP（原因 `STALE`）停掉。

**关于状态恢复**：迁移后任务是**从头开始**的。对 PKCI（逐帧分类，无状态）没有影响；对 PKCT，用最初的 bbox 重新初始化，而目标可能早就移动了，跟踪可能失败。怎样恢复取决于具体任务，第 10.4 节给出了一个通用方案的草案。

### 6.4 执行器卡住和重启

**卡住**：数据面进程还在，但 `ExecutorStatus` 发不出来（例如 GIL、CPU 满载让定时器被饿死几秒）。

- 3 秒没收到 `ExecutorStatus`，控制进程把心跳的 `executor_alive` 置为 false，任务列表保持最后一次已知的值；
- 调度器不再往这个节点派新任务（过滤条件 `executor_stalled`）；
- 从集群主节点看到 `executor_alive=false` 算起，超过 `executor_stall_grace_s`（10 秒），它担任任务主节点的任务被迁走；它恢复后，旧代次的副本由对账停掉；
- 在宽限期内恢复，什么都不会发生。

0.2 的做法是 3 秒后直接上报“没有任务”，再过 3 秒就迁移；而原执行器其实一直在跑，于是出现重复执行，直到它被停掉。

**重启**：新的 `ExecutorStatus` 带着新的 `incarnation`，任务列表为空。

- 对它担任任务主节点的 Running 任务：集群主节点先等 `missing_grace_s`（3 秒），因为心跳可能比 `ExecEvent` 晚到，然后重新调度（可能还是这个节点）。
- 已知限制：执行器记录的最大 term 归零。在重启后的短暂窗口里，一个过期的集群主节点发来的命令可能被接受。由于正常情况下同一时刻只有一个集群主节点，概率很低，暂不处理。可以通过让执行器跟随本机控制进程认定的集群主节点来解决（第 10.3 节）。
- 已知限制：执行器的墓碑随重启丢失。同一任务的墓碑通常在多个参与节点上都有一份，单个执行器重启的影响很小。

### 6.5 消息丢失

本系统中所有“必须送达”的信息都有兜底：

| 消息 | 丢了会怎样 | 兜底 |
|---|---|---|
| `NodeStatus` | 一条丢了没关系；连续丢 5 秒，节点被判离线 | 每条自包含，下一秒补上 |
| `TaskList` | 可靠传输，丢了会重传；重传完成前，新集群主节点暂不接收这个节点的任务 | 心跳的 `tasks_version` 告诉接收方“还有更新的版本” |
| `ExecEvent` | 任务表不知道状态变化 | 对账根据心跳推断（`ConfirmRunning`，或发现任务消失后重新调度）；销毁时用心跳确认 |
| START 命令 | 任务没启动 | 每 5 秒用同一个代次重发（幂等）；多余副本由对账停掉 |
| STOP 命令 | 任务没停 | 每 5 秒重发 |
| `Request` / `Reply` | 网关等不到回复 | 15 秒后返回 `TIMEOUT`，调用方重试同一个请求 |
| `TaskStatus`（接入层） | UE 少收到一个事件 | UE 发现 `seq` 跳号时查询 |
| 逐帧结果、图像 | 少一帧 | 不需要兜底 |

验收要求之一是在 30% 丢包率下节点不被误判离线、不频繁换主（第 10.2 节）。按 1 Hz 发布、5 秒超时粗算，30% 的独立丢包下连续丢 5 条的概率约为 0.3⁵ ≈ 0.24%，即每一对节点之间大约每 7～10 分钟会出现一次误判。**这个估算只在每条心跳只占一个链路层帧时成立**：

| 心跳大小 | 帧数 | 单条消息丢失率 | 连续丢 5 条的概率 |
|---|---|---|---|
| < 1.4 KB（0.3） | 1 | 30% | 约 0.24% |
| 约 2.5 KB | 2 | 约 51% | 约 3.5% |
| 约 4 KB（0.2 的上限） | 3 | 约 66% | 约 12.5% |

这是 0.3 把心跳压到一帧以内的主要原因。此外，如果心跳走组播，802.11 的组播帧没有 MAC 层确认和重传，并且按最低基础速率发送，实际丢包会比单播更严重。

进一步降低误判率的办法，是把心跳提到 2 Hz、判定条件改为“连续 N 次没收到”：超时时间不变，样本更多，误判率会大幅下降。是否这样做，等 `tc netem` 实测后决定（第 10.5 节）。无线丢包往往是突发的，实际情况可能比独立丢包的估算更差。

误判集群主节点不一定导致换主（第 5.4 节：误判者如果独自声明，恢复后因支持者少而让位），但误判任务主节点会导致一次不必要的迁移。所以 `node_offline_timeout_s` 需要在真实网络上实测后调整。

### 6.6 网络分区

MVP 不保证分区期间的正确性，但保证恢复后收敛：

- 分区期间，两侧可能各自选出集群主节点。只能看到少数节点的一侧，选出的集群主节点也能工作（我们没有多数派要求）。
- 两侧都可能接受同一个请求（UE 重试到了不同侧），各自启动一个任务。
- 恢复后：节点多的一侧的集群主节点胜出（支持者数量规则），并提升 term；另一侧的集群主节点让位。胜出方在对账时接收另一侧启动的任务（它们是“未知的运行中任务”）；同一任务的两份副本按执行代次（两侧任期不同，代次一定不同）保留一份；幂等键重复的，停掉其中一个。

这是我们和 Raft 的一个重要差别：Raft 的少数派一侧无法写入，所以不会接受新任务；我们的两侧都能继续工作。对于“无人机编队被临时分成两组”的场景，两侧都能继续工作可能反而是更好的行为。

**是否接受分区期间短暂双主，尚未决定**（第 10.5 节）。能接受，就保持现在的设计；不能接受，可以只把“选主”这一件事交给 etcd 这类多数派组件，其余部分（执行者是事实来源、对账、栅栏）不变。

## 7 任务输入

### 7.1 要解决的问题

如果每块板卡只读自己无人机的相机（`<ns>/camera/image`），会有两个问题：

1. **任务迁移后输入变了**：任务主节点挂了，任务迁到另一块板卡，处理的就是另一架无人机的画面。对 PKCT 来说，原来的目标框在新画面里没有意义。
2. **冗余模式无法保证同一份输入**：每个参与者各读各的相机，做的根本不是同一件事。

### 7.2 数据源地址

任务的输入用一个地址描述（`CreateTask.input`，代码 `core/input_source.py`）：

| 地址                            | 含义                             | 位置属性                                    |
| ------------------------------- | -------------------------------- | ------------------------------------------- |
| 空                              | 执行节点自己的默认相机           | 绑定到执行节点                              |
| `airsim://<vehicle>/<camera>` | AirSim 中某架无人机的某个相机    | **共享**：任何节点都能通过 RPC 直接取 |
| `ros://<node>/<topic>`        | 某个节点上的 topic（真实传感器） | **绑定到该节点**                      |

核心原则：**请求里只放地址，不放数据**。把数据打包进服务请求的做法有三个问题：大块数据走服务调用，每个参与者都要传一份；迁移时数据要重新传；而且服务请求没有压缩。改成地址后，大块数据只通过 topic 传输，发布一次可以有多个订阅者，并且压缩后再发。小数据（参数、bbox、几 KB 以内的协同载荷）仍然可以直接放进请求。

仿真和真机走同一套机制：仿真时用 `airsim://`，真机时用 `ros://` 或空地址，平台的其他部分完全一样。

### 7.3 每个参与者怎么拿到数据

`plan_input()` 根据地址、本节点名、角色、任务主节点、AirSim 取图模式，决定订阅哪个 topic、是否压缩、是否自己取图：

| 地址             | 本节点是…… | `each` 模式（默认）                                       | `relay` 模式                                                         |
| ---------------- | ------------ | ----------------------------------------------------------- | ---------------------------------------------------------------------- |
| 空               | 任意         | 订阅本节点的 `camera/image`（或规格中的 `image_topic`） | 同左                                                                   |
| `airsim://v/c` | 任务主节点   | 自己取图，订阅 `input/airsim/v/cam_c`                     | 同左                                                                   |
| `airsim://v/c` | 辅助节点     | 自己取图，订阅本节点的 `input/airsim/v/cam_c`             | 不取图，订阅**任务主节点**的 `input/airsim/v/cam_c/compressed` |
| `ros://n/t`    | 节点 n 本身  | 订阅本地的 `t`                                            | 同左                                                                   |
| `ros://n/t`    | 其他节点     | 订阅 `/<n 的命名空间>/t/compressed`                       | 同左                                                                   |

`each` 和 `relay` 的取舍：

- `each`：每个参与者独立向 AirSim 取图，不经过无线网络，但 AirSim 的 RPC 负载随参与者数量增加，可能拖慢 UE 的帧率。
- `relay`：只有任务主节点取图，辅助节点通过无线网络收压缩流，AirSim 负载最小。
- 用 `AIRSIM_FETCH_MODE` 切换，代码不用改。哪种更好需要实测 AirSim 多客户端的负载。

### 7.4 AirSim 按需取图

`airsim_feeds.py`：

- 只有当某个任务使用 `airsim://<v>/<c>` 时，才为这个相机启动取图线程；多个任务共用一个相机时引用计数，最后一个任务结束时停止线程。
- 取图频率由 `airsim_fps` 控制（默认 10），发布到 `<ns>/input/airsim/<vehicle>/cam_<camera>`。
- 节点没有设置 `AIRSIM_HOST` 时，不能执行 `airsim://` 任务：执行器返回 `NOT_READY`，集群主节点换一个节点。

### 7.5 压缩转发

`relay.py`：

- 本节点对外提供的 topic（执行器参数 `relay_topics`，默认 `camera/image`；AirSim 取图的 topic 自动加入）会额外提供一个 `<topic>/compressed`（JPEG，质量 80）。
- **只有在有其他节点订阅时才编码**：没人订阅时，不解码也不编码，不占 CPU。
- 接收方（`images.py`）收到 `CompressedImage` 后用 PIL 解码，再交给推理。

### 7.6 带宽估算

| 数据 | 大小 | 10 fps 时 |
|---|---|---|
| 640×480 原始 RGB 帧 | 约 920 KB | 约 74 Mbps |
| 同一帧 JPEG（质量 80） | 约 30～60 KB | 约 2.4～4.8 Mbps |
| `TaskResult`（含协同载荷） | 约 1～2 KB | 约 0.1 Mbps |
| `NodeStatus`（全集群） | 平均约 250 B（含协议头）× 12 | 约 25 kbps（1 Hz，组播；第 2.8 节） |

所以禁止跨节点逐帧传输原始图像，跨节点的图像一律走压缩流。JPEG 大小随画面内容变化很大，以上是估算值。

### 7.7 与调度的联动

- **绑定到节点的数据源**（`ros://n/...`）：调度器给节点 n 加 15 分（`input_locality_bonus`），优先让任务主节点在数据所在的地方读本地数据；节点 n 离线时任务无法放置，返回 `NO_FEASIBLE_NODE`。
- 网络评分以数据所在节点为参照点（`input_node`），选出离数据近的辅助节点。
- **共享数据源**（`airsim://`）：任何节点都行，迁移后输入不变。

### 7.8 新增数据类型

平台不关心数据是什么，只关心它在哪里。新增一种数据类型（例如点云）时，由算法声明自己需要的消息类型，平台的取数逻辑（地址解析、订阅、转发）不用改。目前只实现了图像（`Image` 和 `CompressedImage`）。

## 8 调度

### 8.1 流程

调度器（`core/scheduler.py`）采用“过滤 + 评分”两阶段选节点。调度在两个时机发生：Submit 后的下一个控制周期（10 Hz），以及每秒对账时兜底（第 4.9 节）。有多个 Pending 任务时，按 `priority` 从高到低、相同时按提交时间先后依次调度；`priority` 不影响过滤和评分，也不抢占（第 3.3 节）。

调用一次 `schedule()` 的流程：

```
数据源绑定到某节点且该节点离线？ ──是──► NO_FEASIBLE_NODE
        │否
指定了 target_nodes？ ──是──► 只检查硬性条件，按指定的顺序放置（第一个是任务主节点）
        │否
指定了 request_node？ ──是──► 任务主节点固定；不需要辅助节点就到此为止
        │                    需要辅助节点的话，辅助节点仍按评分选
        ▼
对每个在线节点：过滤（硬性条件 + 资源条件） → 评分 → 排序
        ▼
可用节点数 < 需要的参与者数？ ──是──► NO_FEASIBLE_NODE（附带每个节点被拒的原因）
        ▼
第 1 名是任务主节点，接下来 helper_count 名是辅助节点
```

### 8.2 过滤条件

| 条件 | 拒绝原因 | 对指定节点也生效？ |
|---|---|---|
| 协议版本不同 | `protocol_mismatch` | 是 |
| 执行器卡住（`executor_alive=false`） | `executor_stalled` | 是 |
| 推理未就绪 | `not_ready` | 是 |
| 节点不支持该任务类型 | `algorithm_unavailable` | 是 |
| 最近 60 秒内启动这个任务失败过 | `recently_failed` | 否 |
| 已分配任务数 ≥ 4 | `busy` | 否 |
| 电量 < 20% | `battery_low` | 否 |
| 需要 GPU 但没有（`gpu_mem_total_mb > 0` 或 `gpu_usage >= 0` 才算有） | `gpu_unavailable` | 否 |
| 空闲 CPU 核数不足 | `cpu_insufficient` | 否 |
| 空闲内存不足（共享内存 GPU 的显存需求也算在内存里） | `mem_insufficient` | 否 |
| 独立显卡的空闲显存不足 | `gpu_mem_insufficient` | 否 |

“已分配任务数”来自任务表，而不是节点上报的 CPU 使用率。原因是：任务启动后几秒，CPU 使用率才会反映出来，这期间如果只看 CPU，所有决策都会选同一个节点。任务表的统计在某些情况下会不准（短暂双主、刚接收完任务、有残留副本），所以执行器还会按自己实际运行的任务数再检查一次（第 3.8 节）：调度器是第一道关口，执行器是最后一道。

### 8.3 评分

```
得分 = w_lrs × LRS + w_brs × BRS + w_net × NET
       − 5 × 该节点已分配的任务数
       − 10（如果是集群主节点自己）
       + 15（如果数据绑定在这个节点上）
```

推理任务的默认权重是 `(0.3, 0.3, 0.4)`，可以按任务类型配置。

| 分项                   | 含义                                   | 计算（0～100）                                                                                                                                                                            |
| ---------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LRS** 最少资源 | 放上这个任务后剩余资源越多越好         | CPU、内存（使用 GPU 时再加 GPU）剩余比例的平均值 × 100。已用量 = 上报的使用率 + 预留（CPU 10%、内存 20%）                                                                                |
| **BRS** 资源均衡 | 放上这个任务后各维度的使用率越均衡越好 | 比较放置前后各维度使用比例的标准差：50 + (50 + 放置后的均衡度 − 放置前的均衡度) / 2                                                                                                      |
| **NET** 网络     | 到参照节点的链路越好越好               | 从 100 开始扣：RTT 超过 50 ms 每 50 ms 扣 10（最多 40）；抖动超过 10 ms 每 10 ms 扣 5（最多 30）；丢包超过 1% 每 1% 扣 5（最多 50）；三项都乘以任务的 `latency_sensitivity`（默认 0.5） |

NET 的参照节点：任务规格有 `input_node`（数据所在节点）时用它，否则用集群主节点。链路测量值优先取参照节点对候选节点的测量，没有就取反方向的，都没有就用默认值（RTT 30 ms、抖动 5 ms、丢包 0.5%）。

**一个例子**：两个候选节点资源相同，LRS=60、BRS=80；edge-03 到参照节点 RTT 20 ms，NET=100；edge-05 RTT 150 ms，`latency_sensitivity`=1，NET=100−20=80。edge-03 得分 0.3×60+0.3×80+0.4×100=82；edge-05 得分 74。如果 edge-03 上已经有 2 个任务，它就要扣 10 分，变成 72，任务会被派给 edge-05。

### 8.4 链路测量

`core/link_estimator.py` 只用心跳流量测量链路，不额外发包，也不依赖时钟同步：

- **RTT**（类似 RTCP 接收报告）：节点 B 在自己的心跳里，对每个对端 A 回显“我最后收到的 A 的 seq（低 16 位）”和“我收到它之后过了多久”。A 收到后，用“自己发出那条 seq 至今的时间”减去 B 的持有时间，就是 RTT。两端都只读自己的单调时钟。回显字段只在每 5 条心跳的慢变部分里发送，所以每对节点每 5 秒采样一次 RTT，收敛比 0.2 慢。
- **平滑**：RTT 用 1/8 增益（同 TCP SRTT），抖动用 1/16 增益（同 RTP）。
- **丢包**：接收方根据对端每一条心跳的 `seq` 空洞计算，按时间窗口统计，不受慢变部分的影响。
- **量化**：上报时，RTT、抖动、持有时间以 4 ms 为单位存成 uint8（255 表示未知；测量值最大取 254，约 1 秒，所以很慢的链路仍然显示为慢，而不是“未测量”；持有时间饱和时这次回显不用来算 RTT），丢包率以百分比存成 uint8（255 表示未知）。
- **对端重启**（`incarnation` 变化）：清空这个对端的测量。

精度受发布频率和量化的限制：持有时间最长 1 秒，回显本身也有调度抖动。这对调度用的“好/中/差”判断足够了，但不能当作精确的网络测量。

### 8.5 几个取舍

| 做法                                                                   | 原因                                                                |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 网络评分用实测的链路，而不是固定值                                     | 自组网中不同节点对之间的链路差异很大                                |
| 不做带宽评分                                                           | 链路测量只有 RTT、抖动、丢包，没有测带宽                            |
| 时延、抖动、丢包共用一个敏感度 `latency_sensitivity`                 | `CreateTask` 只有一个敏感度字段，调用方不需要理解三个参数         |
| GPU 维度用节点上报的显存使用率；均衡评分的显存维度加的是任务的显存需求 | 每个维度都用同一种单位的量，评分才可比                              |
| 按已分配任务数做容量过滤，每个任务再扣 5 分                            | 见第 8.2 节：CPU 使用率滞后于任务分配                               |
| 集群主节点给自己扣 10 分                                               | 减少任务随集群主节点一起丢失的情况（第 6.2 节）；也给控制面留出 CPU |
| Jetson 的 `gpu_mem_total_mb` 填 0                                    | 让调度器区分独立显卡和共享内存的 GPU：后者的显存需求算进内存        |

### 8.6 调参建议

- 权重、扣分、加分都需要在真实负载下调整。建议先记录每次调度的候选列表和各项得分（`ScheduleResult.candidates` 已经有这些数据），再根据实际放置效果调整。
- `max_tasks_per_node=4` 与 PKCT 的 `MAX_TRACKERS` 一致。如果以后某种任务很轻，可以改成按资源而不是按个数限制。

## 9 设计决策记录

每条记录的格式：**决定**、**理由**、**代价**、**什么情况下应该重新考虑**。

### D1 用单一集群主节点，而不是完全无主

- **决定**：任何时刻由一个节点集中做调度和任务管理。
- **理由**：调度需要全局视图和互斥，集中决策是最简单的互斥方式（第 5.1 节）。需求里也明确说“一段时间内由一个节点充当集群主节点”。
- **代价**：需要选主；换主期间（约 10 秒）不能创建任务。
- **重新考虑**：节点规模大到集群主节点成为瓶颈（远超 12 个）时。

### D2 不用 Raft

这是影响最大的一个决定。我们完整实现并实测过一个基于 Raft 的版本，最后没有采用。

**Raft 的吸引力**：任务表复制到多数派节点上，换主后不丢任何信息；理论上可以做到“任务不重复”。实现用的是 PySyncObj（纯 Python 的 Raft 库），转 C++ 时换 NuRaft。

**Raft 版本的实测**（12 个节点在 localhost 上）：

| 项目                               | 结果                                              |
| ---------------------------------- | ------------------------------------------------- |
| 换主耗时                           | 中位数 3.3 秒，最长 4.2 秒                        |
| 一次提交的延迟                     | 约 316 ms（PySyncObj 把命令攒到下一次心跳发送）   |
| 创建一个任务                       | 3 次提交（Submit、Assign、ReportStatus），约 1 秒 |
| 新集群主节点刚当选时查已提交的任务 | 5 次中 1 次查不到，必须先提交一条 Barrier         |

**为什么去掉**：

1. **Raft 不能消除执行层的重复**。Raft 保证的是任务表一致，但“下发 StartTask”和“执行器真的启动”发生在 Raft 日志之外。旧集群主节点在被罢免前发出的下发请求、执行器重启、回复丢失……这些情况下，仍然需要 term 栅栏和对账来清理。也就是说，**有了 Raft，第 5.6 节的那套机制一样不能少**。
2. **Raft 实际多保住的东西不多**。对比第 3.7 节：Raft 能多保住的，只有“排队中/下发途中的任务”和“历史记录”。前者用“没跑起来就如实回复失败 + 幂等重试”可以弥补，后者可以由 UE 保存。
3. **Raft 对自组网的要求高**。每次提交需要 7 个节点（12 个中的多数）确认；PySyncObj 要求节点之间两两建立 TCP 连接、配置静态成员表（`cluster.yaml`）；要处理持久化（全集群重启后任务表该恢复还是清空？）。这些都是额外的部署和运维负担。
4. **PySyncObj 没有 PreVote**，节点短暂断网再恢复会引发不必要的换主。
5. **团队只有 3 个人**。Raft 库是一个需要专人理解、调试的黑盒，转 C++ 时还要换一个库（NuRaft），两个库的行为差异又是一层风险。

**采用的做法**：广播选主（第 5 章）+ 执行者是事实来源（D4）。三人讨论后确定接受“故障时可能短暂重复，几秒内自动清理”。

- **代价**：见第 1.4 节的“不保证”一列。
- **重新考虑**：如果业务要求“集群主节点挂掉时排队中的任务也不能丢”或“任何时刻都不能重复”，而且无法由调用方重试来满足。

### D3 任务表只放在集群主节点内存里

- **决定**：不复制、不持久化；换主后从执行者的上报重建。
- **理由**：复制需要共识（D2）；持久化在全集群重启时反而带来“该恢复还是清空”的问题。任务表里真正重要的部分（正在运行的任务）已经由执行者持有。
- **代价**：第 3.7 节列出的信息会丢失。
- **重新考虑**：同 D2。

### D4 执行者是事实来源

- **决定**：“实际在跑什么”只以执行者的上报为准；集群主节点的任务表是期望状态，靠对账让两者一致。新集群主节点不知道的运行中任务，一律**接收**而不是停掉。
- **理由**：执行者持有的信息是最可靠的，因为任务就在它那里跑。这个思路和 Kubernetes 的控制器一样：期望状态 + 实际状态 + 持续对账，任何一方出了问题都会被下一轮对账纠正。
- **代价**：执行者需要上报完整的任务规格（`spec_json`）。0.3 把它放进变化时才发布的 `TaskList`，心跳只带摘要（D16）。
- **细节**：同一任务有多个副本时，接收执行代次最大的；代次相同时优先取任务主节点上的；再相同取编号最小的节点。只剩辅助节点副本时也接收，下一轮发现任务主节点离线再重新调度。离线节点缓存的 `TaskList` 里的任务也接收（第 4.9 节）。这些规则保证迁移途中换主、集群主节点自己执行的任务都不会丢。

### D5 只有跑起来才算创建成功

- **决定**：网关只在任务进入 Running 后回复成功；否则回复失败并附带 task_id，调用方用同一个幂等键重试。
- **理由**：让“成功”有一个可以兑现的含义：成功的任务一定在某个执行者上，因此一定能在换主后被接收。“写进任务表就算成功”在没有复制的任务表上是兑现不了的。
- **代价**：调用方必须正确实现重试和幂等键；创建请求最长阻塞 10 秒。
- **重新考虑**：如果有调用方无法实现重试。

### D6 task_id 用 UUID

- **决定**：集群主节点生成 UUID。控制面消息里用 16 字节二进制，对外接口用字符串。
- **理由**：没有复制的计数器（D3），换主后无法保证整数 ID 不重复。二进制形式比 36 字节的字符串小一半以上，心跳里每个任务摘要都要带它。
- **代价**：UE 接口的 task_id 是字符串而不是整数，UE 侧要按字符串处理；适配层要负责两种形式的转换。

### D7 term 和执行代次两道栅栏

- **决定**：执行器检查 term（拒绝旧集群主节点）；执行器、任务表和汇总方检查执行代次 `(epoch, assign_term)`（拒绝旧执行会话）。
- **理由**：两者防的是不同的东西（第 3.8 节）。只有 term 的话，同一个集群主节点任期内的迁移无法区分新旧会话；只有执行代次的话，旧集群主节点可以用“看起来合法”的代次停掉任务。代次为什么要带 `assign_term`，见 D17。
- **代价**：执行器需要记住最大 term；重启后归零（已知限制）。

### D8 命令和请求带目标地址，转发只转一次

- **决定**：`Command` 带 `targets`，`Request` 带 `target_leader`，收到不是发给自己的就忽略。网关只转发一次，集群主节点不再转发。
- **理由**：topic 会把消息送给所有订阅者；没有目标地址的话，短暂双主时一个请求会被两个集群主节点各处理一次。0.2 用“服务名唯一”解决的是同一个问题。转发多次可能形成环路。
- **代价**：网关需要知道集群主节点的编号（来自选主状态）。换主瞬间可能发给旧集群主节点，此时得到 `NOT_LEADER` 或超时，调用方重试。

### D9 跨节点的命令和请求用 topic，不用 Service 或 Action

- **决定**：下发（`Command`）、回执（`ExecEvent`）、请求（`Request`）、回复（`Reply`）都是可靠 topic，用 `request_id` 对应；只有集群主节点在当选时创建对应的端点。长时间运行的状态通过心跳和 `TaskList` 传递。
- **理由**：
  1. 对账模型本来就是水平触发的：命令幂等，丢了下一轮重发，执行结果最终都能从心跳里观察到。Service 提供的“一问一答”是多余的。
  2. **端点多**：每个 Service 底层是请求、响应两个 topic。任何节点都可能当选，要么每个节点预先对其他 11 个节点建好客户端（全集群约 500 个端点），要么当选时临时创建（现场等 DDS 发现）。
  3. **回复发给所有客户端**：在大多数 rmw 实现里，一个服务的回复会送到这个服务的所有客户端，由各客户端按请求 ID 丢掉不属于自己的。
  4. **发现竞态**：`wait_for_service` 只确认请求通道连通，不确认回复通道。在发现较慢的无线网络上，可能出现请求已被执行、回复却丢失的情况。
  5. **同步调用**：给多个辅助节点下发要逐个调用或者自己写并发；rclpy 里还需要可重入回调组来避免死锁。
  6. **不用 Action**：Action 的 goal 由发起它的客户端持有，换主后新集群主节点接管不了旧集群主节点发起的 goal；Action 自带的状态机（accepted/executing/succeeded…）和我们的任务状态机重复，两套状态容易不一致；Action 的反馈是点对点的，而我们需要任何一个可能成为新集群主节点的节点都能看到任务状态。
- **代价**：要自己用 `request_id` 匹配回复、自己管理超时。改动集中在适配层（`ros/` 下的 dispatcher、forwarder，本来就是注入的接口），核心层不用改。

### D10 本地直接调用，跨节点一律用 topic

- **决定**：执行器和推理引擎在同一进程，直接调用函数（`LocalBackend`）；跨节点的命令、请求和逐帧数据都用 topic。
- **理由**：同一进程内走 ROS 服务要序列化、过 DDS、再反序列化，对 640×480 的图像来说是纯开销。跨节点的命令见 D9。逐帧数据用 topic，因为可以多个订阅者、可以丢帧、不需要逐条确认。
- **代价**：执行器和推理引擎必须在同一进程（数据面进程）；推理崩溃会带走执行器。保留 `RosServiceBackend` 作为退路（`INFERENCE_BACKEND=ros`）。

### D11 任务输入用地址描述，请求里不放数据

- **决定**：见第 7 章。
- **理由**：迁移后输入不变；冗余模式下各参与者处理同一份输入；大块数据只传一次、可以压缩、可以多播。
- **代价**：`ros://` 输入绑定到节点，那个节点挂了任务就无法继续（这是物理事实，不是设计缺陷）。

### D12 不用合同网（招标—投标）方式分配任务

- **决定**：由集群主节点集中调度，不采用合同网方式（发布任务 → 各节点投标 → 选中标者）。
- **理由**：招标需要额外一轮广播和等待投标的时间；多个招标同时进行时，一个节点可能同时中标多个任务，又需要额外的确认机制；而集群主节点本来就从 `NodeStatus` 掌握了所有节点的资源和链路，不需要再问一遍。
- **代价**：调度结果依赖 `NodeStatus` 的新鲜度（最多 1 秒的延迟）。
- **重新考虑**：如果节点的“意愿”包含 `NodeStatus` 表达不了的信息（例如飞行任务的优先级）。

### D13 每个节点 3 个进程

- 见第 2.4 节。理由是控制进程必须轻、数据面受 GIL 影响、DDS 参与者数量。

### D14 核心逻辑不依赖 ROS

- 见第 2.3 节。理由是测试和转 C++。

### D15 可重试的错误在 HTTP 上返回 503

- **决定**：`NO_LEADER`、`NOT_LEADER`、`BUSY`、`NOT_READY`、`TIMEOUT` 一律返回 503。
- **理由**：HTTP 客户端普遍把 4xx 理解为“请求错了，不要重试”，把 503 理解为“稍后重试”。换主期间返回 400 会让 UE 错误地放弃。

### D16 心跳只带摘要，完整任务信息走可靠的 TaskList

- **决定**：`NodeStatus` 每秒发布、小于 1 KB，只带任务摘要；完整的 `TaskState` 和墓碑放进变化时才发布的 `TaskList`（RELIABLE、TRANSIENT_LOCAL）；资源和链路每 5 条心跳附带一次。
- **理由**：0.2 的心跳 1～4 KB，超过一个链路层帧，BEST_EFFORT 下任何一帧丢失整条就丢（第 6.5 节）。规格很少变化，没必要每秒重发。
- **代价**：接收任务时要等 `TaskList` 到齐（`tasks_version` 不一致时跳过一轮）；RTT 每 5 秒采样一次；多了一个所有节点之间的可靠 topic。
- **重新考虑**：如果抓包发现 `TaskList` 的可靠传输开销（心跳、确认）很大，可以改为“看到心跳的 `tasks_version` 变化时，再按需向该节点查询”。

### D17 执行代次为 (epoch, assign_term)

- **决定**：执行代次按 `(epoch, assign_term)` 的字典序比较。只有真正重新调度时，才写入新的 `(epoch + 1, 当前 term)`；换主后接收任务时，`assign_term` 保持不变。
- **理由**：两个集群主节点短暂并存时，epoch 由各自加 1，可能在两个节点上各出现一份同 epoch 的副本，两份都能通过栅栏，汇总方会把两份结果都当成有效的（第 3.8 节）。
- **代价**：任务表、`TaskState`、`TaskBrief`、`Command`、`ExecEvent`、`TaskResult` 都多一个字段；PKCT 会话 ID 变长。
- **已知不足**：两个节点在同一个任期号上同时声明时（视图不一致的罕见情况），代次仍可能相同，靠对账去重清理（第 5.6 节）。

### D18 销毁以执行者确认为准，墓碑记在执行器上

- **决定**：当前代次所有在线参与者都确认停止，才算销毁成功；执行器因销毁而停止任务时留墓碑；接收任务时，有墓碑的任务接收为 Cancelled。
- **理由**：和创建对称（D5）。任务表随集群主节点消失，但“任务已被销毁”记在执行器身上，换主时不会消失。这和“执行者是事实来源”（D4）一致：执行者既记住“我在跑什么”，也记住“我被要求停掉了什么”。
- **代价**：销毁请求最长阻塞约 10 秒；`TaskList` 多几十字节；墓碑只在内存里，执行器重启后丢失。
- **重新考虑**：如果出现“所有参与者都离线时也必须销毁成功”的需求。

### D19 链式任务走发布订阅，平台不做结果存储

- **决定**：链式任务的触发（父任务创建子任务）走本机网关的创建接口，小数据（bbox、`frame_id`）放进 `params_json`；流式链（父任务每帧的输出作为子任务每帧的输入）走发布订阅。不引入分布式存储，不用 Action。推理结果本身也不在平台层存储（第 1.5 节）。
- **理由**：
  - 链式任务分三类：**触发式**（PKCI 发现目标后触发一个 PKCT 去跟踪）、**流式**（检测 → 跟踪）、**产物式**（父任务结束时产出地图、视频，子任务之后再处理）。前两类不需要存储；只有产物式需要一个比父节点活得更久的地方，而目前没有这类任务。
  - Action 的 goal 属于发起它的客户端，父任务一迁移就失效；Action 是“请求—等待完成”，链式任务是“输出流接到输入流”；Action 的反馈是点对点的，而一份结果可能同时被子任务、网关和汇总方订阅，这正是 topic 擅长的。
- **计划（未实现）**：给任务结果一个按任务命名的地址 `task://<父任务ID>/result`，解析为 topic `/task/t_<去掉横线的 UUID>/result`。父任务无论当前在哪个节点运行都发布到这里，迁移时子任务不需要重新绑定输入；子任务按执行代次丢弃父任务旧代次的结果；子任务同时需要原图时，订阅和父任务相同的输入地址，按 `frame_id` 对齐；调度时把子任务的 `input_node` 设为父任务当前的任务主节点。
- **重新考虑**：出现产物式链任务时，先用绑定到节点的地址（例如 `blob://<节点>/<产物ID>`）；确实需要容错时，再把产物复制到多个节点或做编码分散存储。

### D20 优先级字段先预留

- **决定**：任务规格预留 `priority`（数值越大越重要，默认 0；档位 0 普通、100 重要、200 紧急）和 `preemption_policy`（默认 0，不抢占）。当前只透传，待调度队列按优先级排序。
- **理由**：Humble 的接口不支持类型演进，以后再加字段就要升协议版本、12 个节点一起升级；顺着这次升级一起加，以后启用优先级时只需要改逻辑。
- **代价**：几乎为零；要在文档和代码里写明“当前不影响调度决策”，避免以后有人误以为它已经生效。

### D21 选主候选按看得见的节点数优先

- **决定**：没有声明时，候选按（有资格，`visible_peers` 更多，编号更小）排序；已在任的集群主节点不因为别人的 `visible_peers` 稍多而让位。
- **理由**：没有 `input_node` 的任务，网络评分以集群主节点为参照；命令和请求也都经过集群主节点。所以在自组网里，让看得见最多节点的那个当集群主节点，比让编号最小的当更合适。
- **代价**：选主测试的组合更多；每条心跳都要带 `visible_peers`。
- **重新考虑**：如果实测发现连通性波动让选主结果不稳定。

### 10.3 后续工作

按优先级排列：

1. **真实环境验证**（10.2 全部），包括抓包。在此之前，本文中所有时间和带宽数字都只是推算。
2. **带宽措施 A、B**（第 2.8 节）：按抓包结果决定先做哪一项。A 的代码部分已完成（控制进程和执行器创建节点时关闭参数服务和 rosout），还需要在真机上用 `ros2 node list` 等核对端点。
3. **节点本地录制结果**：每个节点用 rosbag2（MCAP 格式）把自己的 `task/result` 录到本地盘，按时间或大小循环覆盖。不需要节点间协调，主要用于调试、复盘和收集数据，真机联调时会很有用。只录本机的 topic：录制器订阅 `/cluster/*` 的话，单播模式下每条心跳和 `TaskList` 都要给它多发一份，控制面的无线流量翻倍；控制面的历史由事件日志（第 2.9 节）负责。之后再加 Prometheus 指标（每个节点只导出自己的数据，集群视图在地面站拼）。
4. **缩短换主后的不可用窗口**。预热 5 秒是一个保守值。实际上跟随者平时就一直在接收所有节点的心跳和 `TaskList`，当选时已经有完整的视图，只有刚启动的节点才需要等待完整视图。可以改为：节点运行时间已超过 `node_offline_timeout_s` 时，预热缩短到 1～2 个心跳周期（但要留够按角色创建的端点完成 DDS 匹配的时间）。改之前需要确认“预热不足时漏接收的任务”在后续对账中一定会被接收（目前的对账规则应该已经保证了这一点）。
5. **集群主节点主动让位**（大面积离线保护的完整版）：集群主节点自己的 `visible_peers` 掉到阈值以下（例如看不到一半的节点）时，主动撤销声明，让连通性更好的节点接任。
6. **节点恢复的迟滞和迁移限速**：节点从离线恢复后，要连续稳定一段时间（例如 30 秒）才重新往它上面派任务；同一个任务在一段时间内最多迁移一次（例如 60 秒内一次）。等真机上测出链路抖动的实际情况后，再定迟滞时长和限速阈值。
7. **执行器只接受本机跟随的集群主节点的命令**：控制进程通过一条本机消息告诉执行器“我当前跟随的集群主节点和它的 term”，执行器只接受这个集群主节点发来、且 term 不低于已知最大值的命令（`Command.leader_id` 已预留）。这样执行器重启后不再从零开始，换主后本机一跟上新集群主节点，旧集群主节点的命令就被拒绝。
8. **协同结果汇总**（10.1 第 5 条），以及辅助节点替换（第 4 条）。
9. **定时触发和链式触发**。定时触发由集群主节点的定时器生成幂等键 `schedule:<规则ID>:<计划时刻>`，换主后新集群主节点用同一个键补触发，不会重复。链式触发包括 `task://` 地址（第 9 章 D19）和父子级联停止（第 10.5 节）。

### 10.4 任务状态恢复：方案草案

迁移后任务是否需要恢复执行状态，取决于具体任务：

| 任务 | 状态 | 迁移后需要什么 |
|---|---|---|
| PKCI 逐帧分类 | 无 | 什么都不需要 |
| PKCT 跟踪 | 目标当前的位置和外观特征 | 用最近的位置重新初始化跟踪器，而不是最初的 bbox |
| 以后的累积型任务（例如计数、建图） | 累积量 | 从最近的检查点继续 |

通用机制（草案，尚未实现）：

1. 算法在 `TaskResult` 中可选地附带一个**检查点**（几 KB 以内的 JSON 或字节，例如 PKCT 的最新 bbox）。
2. 执行器把最近一次检查点放进 `TaskState`，随 `TaskList` 发布，这样集群主节点和其他节点都能看到。
3. 重新调度时，集群主节点把最近的检查点放进 START 命令的规格里；新执行者用它初始化。
4. 检查点和执行代次绑定：只接受当前代次的检查点。

这样平台只负责“搬运”检查点，检查点的内容由算法定义。代价是：`TaskList` 是变化时发布的可靠消息，检查点每更新一次就要重发一次，所以检查点必须低频更新（例如每 5 秒一次），不能逐帧更新；如果检查点较大，可以只放摘要，内容走 topic。

## 附录 C 接口定义（协议版本 4）

**约定**：

- **节点编号**：`uint8`，1～254，0 表示“无”。
- **task_id**：消息里是 `uint8[16]`（二进制 UUID）；对外接口（HTTP/JSON、`CreateTask` 等）里是字符串。
- **数组都有上限**（rosidl 的有界数组 `[<=N]`），避免序列化时因为超长而失败，也让消息大小有上界；有界字符串由 `ros/convert.py` 截断到上限。
- **以后可能扩展的任务属性**（`priority`、`preemption_policy`，以及以后可能加的 `parent_task_id`）放在 `spec_json` 里，不进消息定义，往里加字段不需要升级协议版本。
- 下面的定义直接取自 `ros2_ws/src/cccp_cluster_interfaces/msg/`，相对评审稿的补充见“实现时的调整”第 4～7 条。uint8 枚举与 `ros/convert.py` 中的对照表由 `test_constants.py` 保持一致。

### C.1 公共子消息

```
# TaskBrief.msg
# NodeStatus.tasks 的一项：本节点正在运行的一个任务的摘要，约 28 B（设计 0.3 附录 C.1）。
# 对账判断“谁在跑哪个任务的哪个执行代次”只需要这些；完整信息在 TaskList 里。

uint8 ROLE_PRIMARY=0
uint8 ROLE_HELPER=1

uint8[16] task_id                 # 二进制 UUID
uint32 epoch                      # 执行代次 (epoch, assign_term)，按字典序比较
uint32 assign_term
uint8 role
```

```
# LinkQuality.msg
# NodeStatus.links 的一项：发布方（记为 Y）对对端 peer（记为 X）的链路测量，约 8 B。
#
# RTT 不需要额外的探测消息，做法与 RTCP 接收报告相同：
#   1. Y 收到 X 的心跳后，记下它的 seq 和收到时刻（Y 的单调时钟）；
#   2. Y 下次发布带慢变部分的心跳时，在这一项里带上 echo_seq 和 echo_delay_4ms；
#   3. X 收到后计算 RTT = 当前时刻 - 自己发出 echo_seq 那条心跳的时刻 - echo_delay。
# 两端都只用自己的时钟，不受节点间时钟偏差影响。
#
# 每个值占 1 字节：时间以 4 ms 为单位，丢包率以 % 为单位。255 表示未知；
# 测量值最大取 254，所以超过约 1 秒的坏链路仍然显示为“很慢”，而不是“未测量”。

uint8 UNKNOWN=255

uint16 echo_seq                   # Y 最近收到的 X 的心跳 seq 的低 16 位；还没收到过时为 0
uint8 peer                        # 对端节点编号
uint8 rtt_4ms                     # 平滑后的 RTT
uint8 jitter_4ms                  # RTT 抖动，按 RFC 3550 的方式平滑
uint8 loss_pct                    # 最近窗口内 X -> Y 方向心跳的丢失比例
uint8 echo_delay_4ms              # 从 Y 收到那条心跳到 Y 本次发布经过的时间；饱和时不能用来算 RTT
```

```
# NodeLoad.msg
# NodeStatus.load：资源容量和使用率，约 20 B。每 slow_fields_every 条心跳附带一次。
# 使用率和电量单位均为 %，-1 表示未知。

uint16 cpu_cores
uint32 mem_total_mb
uint32 gpu_mem_total_mb           # 独立显存总量；Jetson 等与系统共享内存的 GPU 填 0
int8 cpu_usage
int8 mem_usage
int8 gpu_usage                    # 有 GPU 的节点总能测出它（>= 0），没有 GPU 时为 -1
int8 gpu_mem_usage
int8 battery                      # 非无人机节点填 -1
```

```
# TaskState.msg
# 一个任务在本节点上的完整执行信息，由执行者上报（ExecutorStatus.tasks → TaskList.tasks）。
# 执行者是“实际在跑什么”的唯一来源：新的集群主节点上任后，靠各节点的 TaskList 重建任务表
# （开发规范 5.3），所以这里带着重建所需的全部信息，而不只是 task_id。

uint8 ROLE_PRIMARY=0
uint8 ROLE_HELPER=1

uint8[16] task_id                 # 二进制 UUID
uint32 epoch                      # 执行代次 (epoch, assign_term)
uint32 assign_term                # 做这次调度的集群主节点的任期；换主接收时不变
uint8 role
uint8 primary_node                # 这一代的任务主节点（节点编号）
uint8[<=15] helper_nodes          # 这一代的辅助节点（节点编号）
string idempotency_key
string<=64 name
string spec_json                  # TaskSpec 的 JSON，含 priority、preemption_policy
```

```
# Tombstone.msg
# 墓碑：本节点因“销毁”而停止的任务（设计 4.5）。保留 tombstone_ttl_s，最多 16 条。
# 新集群主节点在任何节点的 TaskList 里看到某任务的墓碑，就把它接收为 Cancelled，不让它复活。

uint8[16] task_id
```

### C.2 心跳 `NodeStatus`（`/cluster/node_status`）

```
# NodeStatus.msg
# /cluster/node_status：心跳。每个节点按 1 Hz 发布，所有节点都订阅（设计 0.3 第 3.2 节、附录 C.2）。
# 每条都自包含：收到任意一条，就知道这个节点此刻在不在、认谁当集群主节点、在跑哪些任务（摘要）。
# 必须装进一个链路层帧（约 1.4 KB）：BEST_EFFORT 下一条消息拆成 n 帧，丢失率就从 p 变成 1-(1-p)^n。
# 完整的任务信息在 TaskList 里，只在变化时可靠发布。
# QoS：BEST_EFFORT + KEEP_LAST(1) + VOLATILE。

# 接口协议版本。cccp_* 接口包有不兼容修改时 +1；12 个节点必须一起升级。
# 3：心跳拆成 NodeStatus + TaskList；节点编号代替名字；跨节点的 Service 改为 topic；执行代次 (epoch, assign_term)。
# 4：algorithms_ready 增加 bit2～bit4（批处理任务 FASTLIVO、HETEROMAP、RSSMAP），字段类型不变。
uint8 PROTOCOL_VERSION=4
uint8 protocol_version

# ---- 身份与序号 ----
uint8 node_id                     # 部署时配置的节点编号，1~254；名字见 TaskList.node_name
uint64 incarnation                # 控制进程启动时的 Unix 毫秒；变化说明节点重启过
uint32 seq                        # 每次发布 +1，从 1 开始；incarnation 变化后重新计数

# ---- 选主（每条都带）：每个节点都广播自己认可的集群主节点 ----
uint8 leader_id                   # 0 表示还没有跟随任何集群主节点
uint32 term                       # 本节点已知的最大任期
bool is_leader                    # true 即本节点声明自己是集群主节点；同时也是它的续约
uint8 visible_peers               # 本节点判定在线的对端数，用于选主候选排序

# ---- 就绪（每条都带）----
bool executor_alive               # false：本机执行器超过 executor_timeout 没有出声；tasks 是最后一次已知的值
bool inference_ready
uint8 algorithms_ready            # 位掩码：bit0 = PKCI，bit1 = PKCT，bit2 = FASTLIVO，bit3 = HETEROMAP，bit4 = RSSMAP

# ---- 任务摘要（每条都带）----
TaskBrief[<=8] tasks
uint32 tasks_version              # 与 TaskList.tasks_version 对应；比缓存的 TaskList 新说明新版本还在路上

# ---- 慢变部分：每 slow_fields_every 条附带一次，其余时候为空数组 ----
NodeLoad[<=1] load
LinkQuality[<=15] links
```

### C.3 任务全量 `TaskList`（`/cluster/task_list`）

```
# TaskList.msg
# /cluster/task_list：本节点所有任务的完整 TaskState 和墓碑（设计 0.3 第 3.2 节、附录 C.3）。
# 只在内容变化时发布。每个节点都缓存所有节点的最新一份，离线节点的保留 offline_retain_s，
# 新集群主节点据此接收任务（包括已经离线的旧集群主节点自己执行的任务）。
# QoS：RELIABLE + TRANSIENT_LOCAL；发布端 KEEP_LAST(1)，订阅端 KEEP_LAST(32)。
# 订阅端也必须声明 TRANSIENT_LOCAL，否则收不到历史消息；深度要开大，因为订阅端的历史槽位是所有发布者共用的。

uint8 node_id
string<=32 node_name              # 节点编号 → 名字的对应（命名空间、日志、ros:// 地址用的都是名字）
uint64 incarnation
uint32 tasks_version              # 本节点任务列表或墓碑每变化一次 +1
TaskState[<=8] tasks
Tombstone[<=16] tombstones
```

### C.4 本机 `ExecutorStatus`（`<ns>/exec/status`）

```
# ExecutorStatus.msg
# <ns>/exec/status：数据面进程（执行器）按 1 Hz 发布，只有本节点的控制进程订阅（设计 0.3 附录 C.4）。
# 控制进程据此生成心跳的任务摘要和本节点的 TaskList；任务或墓碑变化时 tasks_version +1。
# 超过 executor_timeout 没收到这条消息，控制进程把心跳的 executor_alive、inference_ready 置为 false，
# 任务列表和墓碑保持最后一次已知的值（执行器没有出声，不等于任务没了）。
# 执行器里发布它的定时器放在独立的回调组，不和推理回调抢线程。
# QoS：BEST_EFFORT + KEEP_LAST(1) + VOLATILE。

uint64 incarnation                # 执行器进程启动时的 Unix 毫秒
uint32 seq
bool inference_ready
uint8 algorithms_ready            # 位掩码，同 NodeStatus
TaskState[<=8] tasks
Tombstone[<=16] tombstones        # 墓碑由执行器产生，控制进程原样放进 TaskList
```

### C.5 下行命令 `Command`（`/cluster/command`，集群主节点 → 执行器）

```
# Command.msg
# /cluster/command：集群主节点 → 执行器的命令（设计 0.3 第 2.5 节、附录 C.5）。
# 所有执行器一直订阅；只有集群主节点在当选时创建发布端。一条命令可以同时发给多个节点，
# 执行器收到不是发给自己的就忽略。命令都是幂等的，丢了由对账重发。
# 执行器的检查顺序见设计 3.8 节（开发规范 5.4）。
# QoS：RELIABLE + KEEP_LAST(32) + VOLATILE。

uint8 OP_START=1
uint8 OP_STOP=2

uint8 STOP_CANCEL=1               # 任务被销毁：执行器停止后留下墓碑
uint8 STOP_STALE=2                # 旧代次的残留副本，或任务已是其他终态
uint8 STOP_DUPLICATE=3            # 与其他任务的幂等键重复
uint8 STOP_UNASSIGNED=4           # 本节点不在当前代次的分工里

# ---- 发送方与栅栏 ----
uint8 leader_id                   # 发送方；目前只用于日志
uint32 term
uint32 request_id                 # 在 (leader_id, term) 内递增；执行器在 ExecEvent 里原样带回

# ---- 目标 ----
uint8[<=15] targets

uint8 op
uint8 stop_reason                 # 只在 OP_STOP 时有意义
string<=64 reason                 # 给人看的原因，只用于日志

# ---- 任务与代次 ----
uint8[16] task_id
uint32 epoch
uint32 assign_term

# ---- 只在 OP_START 时填写 ----
uint8 primary_node
string<=32 primary_name           # 任务主节点的名字：辅助节点按名字找它的命名空间（压缩转发）
uint8[<=15] helper_nodes
string idempotency_key
string<=64 name
string spec_json
```

### C.6 上行事件 `ExecEvent`（`/cluster/exec_event`，执行器 → 集群主节点）

```
# ExecEvent.msg
# /cluster/exec_event：执行器 → 集群主节点（设计 0.3 第 3.5 节、附录 C.6）。
# 既通知执行状态变化，也是命令的回执。它是“快速通道”：丢了由心跳和对账兜底。
# 所有执行器一直有发布端；只有集群主节点在当选时创建订阅端。
# QoS：RELIABLE + KEEP_LAST(32) + VOLATILE。

uint8 KIND_RUNNING=1              # 已在运行；也是 START 的成功回执，重复 START 时再回一次
uint8 KIND_REJECTED=2             # 拒绝了命令，原因见 error_code
uint8 KIND_FAILED=3               # 运行中失败
uint8 KIND_STOPPED=4              # 已停止；也是 STOP 的回执，任务本来就没在跑也回这个
uint8 KIND_FINISHED=5             # 预留：给以后有终态的任务

uint8 ERR_NONE=0
uint8 ERR_STALE_TERM=1
uint8 ERR_STALE_EPOCH=2
uint8 ERR_BUSY=3
uint8 ERR_NOT_READY=4             # 运行中失败时表示没有输入帧（开发规范 5.5）
uint8 ERR_INVALID_INPUT=5
uint8 ERR_UNSUPPORTED_VERSION=6
uint8 ERR_INFERENCE_ERROR=7
uint8 ERR_INSUFFICIENT_PEERS=8
uint8 ERR_FUSION_ERROR=9
uint8 ERR_CANCELLED=10            # 只用在 Reply.exec_error：等任务跑起来时它被销毁了

uint8 node_id
uint64 incarnation                # 执行器进程的；与 seq 一起用于去重
uint32 seq

# 回执时原样带回命令的 term 和 request_id；主动上报（FAILED 等）时 request_id 填 0
uint32 term
uint32 request_id

uint8[16] task_id
uint32 epoch
uint32 assign_term
uint8 kind
uint8 error_code
string<=128 message
```

### C.7 请求 `Request`（`/cluster/request`，网关 → 集群主节点）
