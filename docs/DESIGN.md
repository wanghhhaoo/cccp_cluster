## 术语

“主节点”在本系统里有三种不同的含义，所以本文**从不单独写“主节点”**，一律用下表中的全称。

| 术语                      | 含义                                                                                                         | 代码中的名字         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------- |
| **集群主节点**      | 通过选主选出的节点，负责调度、对账、任务表和对外的任务接口（第 5 章）                                        | `leader`           |
| **任期**            | 每选出一次新的集群主节点就加 1                                                                               | `term`             |
| **任务主节点**      | 执行某个任务、并负责协调辅助节点的节点                                                                       | `primary`          |
| **辅助节点**        | 协同任务中由任务主节点调用的其他节点                                                                         | `helper`           |
| **主视角**          | PKCT 协同跟踪时由算法选举（`ElectPrimary`）选出的那架无人机，属于算法层的概念，与调度无关                  | `primary_drone_id` |
| **执行代次**        | 任务每（重新）调度一次就加 1，用来区分新旧执行会话                                                           | `epoch`            |
| **任务表**          | 集群主节点内存中的任务清单：应该有哪些任务、由谁执行（第 3.3 节）                                            | `TaskTable`        |
| **控制面 / 数据面** | 控制面（调度、对账、任务表）只在集群主节点上工作；数据面（执行器和推理）在所有节点上运行                     | —                   |
| **PKCI / PKCT**     | 平台目前支持的两种推理任务：逐帧图像分类 / 目标跟踪                                                          | —                   |
| **UE**              | 运行 AirSim 的 Unreal Engine 仿真端，也是平台的调用方：通过 HTTP 创建、查询、销毁任务，接收结果（第 4.7 节） | —                   |

## 0 一页纸概览

**是什么**：12 架无人机机载板卡组成的协同推理平台。没有中心后端，所有节点对等；任何时刻由其中一个节点充当**集群主节点**，负责调度和任务管理；所有节点（包括集群主节点）都执行推理任务。

**核心机制**，一共五条：

1. **广播选主**。每个节点每秒广播一条 `NodeStatus`，里面带着“我认谁当集群主节点、任期多少”。按（支持者数量，任期，名字更小）的规则，所有节点收敛到同一个集群主节点。不需要 Raft，不需要成员名单（第 5 章）。
2. **执行者是事实来源**。每个节点在 `NodeStatus` 中上报自己正在运行的任务（含完整规格）。“集群里实际在跑什么”只由执行者说了算（第 3 章）。
3. **任务表只在集群主节点的内存里**。它记录“应该跑什么、由谁跑”。换主后，新集群主节点根据各节点的上报重建任务表（第 3.3、4.1 节）。
4. **对账**。集群主节点每秒比较一次“应该”和“实际”，补发、重新调度、接收、停掉多余的副本（第 4.9 节）。
5. **两道栅栏**。执行器拒绝来自旧任期（`term`）的命令；任务表和汇总方丢弃来自旧执行代次（`epoch`）的报告。即使短时间出现两个集群主节点，重复执行也会在几秒内被清理（第 5.6 节）。

**换来的性质**（完整版见第 1.4 节）：

- 正在运行的任务不受集群主节点故障影响，新集群主节点原样接收。
- 任务主节点掉线，任务约 5 秒后迁移到其他节点。
- 创建任务返回成功时，任务一定已经跑起来了；否则调用方用**同一个幂等键**重试，不会重复创建。
- 代价：故障期间可能短暂重复执行；集群主节点挂掉时，还没跑起来的任务和历史记录会丢失。

**关键时间**（由参数推算，尚未在真实自组网上实测）：

| 事件                                       | 时间                           |
| ------------------------------------------ | ------------------------------ |
| 冷启动到选出第一个集群主节点               | 约 5 秒（`startup_grace_s`） |
| 集群主节点故障 → 选出新的集群主节点       | 约 5～6 秒                     |
| 集群主节点故障 → 新集群主节点开始接受请求 | 约 10～11 秒（再加 5 秒预热）  |
| 任务主节点故障 → 任务在别处重新启动       | 约 5～6 秒                     |
| 创建一个任务（正常情况）                   | 1 秒左右（等下一轮对账）       |

## 1 目标与约束

### 1.1 背景：为什么不用中心后端

一个协同推理平台除了在各节点上做推理，还需要三项管理职责：

- **节点管理**：知道有哪些节点、各自的资源和链路状况；
- **调度**：为每个任务选出执行节点；
- **任务管理**：记录有哪些任务、处于什么状态，节点故障时迁移任务。

最直接的做法是放一台中心后端来承担这三项职责，各无人机节点只负责执行。但后端是单点：它挂了，整个系统就无法创建、查询、迁移任务。而且后端需要一台不在无人机上的机器，部署场景里不一定有。

### 1.2 目标

做一个**完全分布式**的平台：网络只由无人机节点组成，没有后端。具体来说：

1. 节点管理、调度、任务管理由节点自己承担。
2. 任何一个节点故障，包括承担管理职责的节点，系统都能自动恢复。
3. UE 可以连接任意一个节点，得到同样的服务。
4. 支持 PKCI、PKCT 两种推理任务和三种协同模式（第 4.4 节），UE 通过 HTTP 使用（第 4.7 节）。

### 1.3 约束

| 约束                                                      | 对设计的影响                                                           |
| --------------------------------------------------------- | ---------------------------------------------------------------------- |
| 12 个节点，自组网；是单个广播域还是多跳**尚未确定** | 不能依赖“所有节点都能直接互通”之外的网络假设；选主和状态同步只走 DDS |
| 允许动态选主，“一段时间内由一个节点充当集群主节点”      | 采用单一集群主节点的控制面，而不是完全无主（第 9 章 D1）               |
| 集群主节点**也要承担推理**                          | 每个节点都有两种身份；控制面必须轻，不能和推理抢 CPU（第 2.4 节）      |
| 除冗余协同外，**不允许两个节点做同一个任务**        | 重复执行必须被检测和清理（第 5.6、6 章）                               |
| MVP 阶段**不考虑网络分区**                          | 分区时不保证正确性，但分区恢复后必须自动收敛（第 6.7 节）              |
| 以 AirSim 仿真为主，但**不能影响真实部署**          | 任务输入用地址描述，仿真和真机走同一套机制（第 7 章）                  |
| 先用 Python 实现，以后转 C++                              | 业务逻辑不依赖 ROS，可以逐个模块翻译（第 2.3 节）                      |
| 平台组 3 个人                                             | 越简单越好；不引入需要专人维护的组件（第 9 章 D2）                     |
| ROS 2 Humble，节点是 Jetson Orin 和 x86                   | 接口不支持类型演进，改接口必须全体升级（第 5.7 节）                    |

### 1.4 系统的承诺

这是整个设计的出发点。下表列出系统对使用者的全部承诺，以及每一条背后的取舍。

| 方面             | 保证                                                                   | 不保证                                                         | 为什么这样取舍                                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 重复执行         | 同一任务的重复执行只会短暂存在，几秒内被自动清理                       | 不保证任何时刻都不重复                                         | 要做到“永不重复”，需要在下发前达成多数派共识，并且执行器在每次处理前都确认自己仍持有租约。代价是 Raft 级别的复杂度，而 Raft 本身也不能完全消除执行层的重复（第 9 章 D2） |
| 正在运行的任务   | 集群主节点挂掉不影响它们；新集群主节点原样接收，`epoch` 不变，不重启 | 只在集群主节点上运行的任务会随它一起丢失                       | 执行者是事实来源；集群主节点自己的执行者也一起挂了，没有人能报告它的任务                                                                                                   |
| 还没跑起来的任务 | 对调用方的回复如实反映结果：返回成功时任务一定已经在跑                 | 集群主节点挂掉时，排队中或下发途中的任务会丢失，调用方需要重试 | 这些任务只存在于集群主节点的内存里。如实回复 + 幂等重试，比复制它们简单得多                                                                                                |
| 历史记录         | 集群主节点在任期内保留终态任务 1 小时                                  | 换主后历史丢失                                                 | 历史是给人看的，UE 或前端可以自己保存                                                                                                                                      |

一句话：**正在跑的任务很稳，没跑起来的任务靠调用方重试，历史不保证。**

### 1.5 不做的事情

- **模型并行**（把一个模型切分到多个节点上执行）：暂不支持，需要时新增协同模式。
- **拜占庭容错、鉴权**：节点之间互相信任；UE 接口没有认证。
- **持久化**：节点重启后不恢复任何控制面状态。全集群重启等于从零开始。
- **网络分区期间的正确性**：分区两侧可能各自选出集群主节点并各自执行任务，恢复后收敛（第 6.7 节）。
- **跨节点时钟同步作为正确性前提**：所有超时只用本地单调时钟（`time.monotonic()`）计算；消息里的 `stamp` 只用于显示和日志，从不拿两个节点的时间戳做减法。各节点仍然应该部署 chrony，但那只是为了方便对照日志。

## 2 整体架构

### 2.1 职责由谁承担

| 职责           | 由谁承担                                                       | 代码                                                                      |
| -------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 节点管理       | 每个节点都广播 `NodeStatus`，每个节点都维护一份集群视图      | `core/cluster_view.py`、`monitor/`                                    |
| 选主           | 每个节点都运行，只有一个节点胜出                               | `core/election.py`                                                      |
| 调度           | 集群主节点上的调度器                                           | `core/scheduler.py`                                                     |
| 任务管理       | 集群主节点内存中的任务表 + 对账器                              | `core/task_table.py`、`core/reconciler.py`、`control/controller.py` |
| 对 UE 的接口   | **每个节点**都提供同样的 HTTP 接口，请求转发给集群主节点 | `ue_api.py`、`control/ue_backend.py`、`control/gateway.py`          |
| 资源监测       | 每个节点的控制进程：资源采集和链路测量                         | `monitor/probes.py`、`core/link_estimator.py`                         |
| 任务执行       | 每个节点的执行器：接收任务、检查 term/epoch、上报状态          | `cccp_task_executor/executor_node.py`、`core/execution_guard.py`      |
| 推理           | PKCI/PKCT 引擎，与执行器在同一进程内直接调用                   | `collab_inference_ros/engines.py`、`cccp_task_executor/inference.py`  |
| 节点之间的协同 | 协同载荷放在 `TaskResult` 中通过 topic 传输（第 4.4 节）     | —                                                                        |

### 2.2 每个节点的两种身份

```
                       UE / 前端（HTTP，可以连任意节点，连不上就换一个）
                                           │
 ┌─────────────────────────────────────────┼─────────────────────────────────────────┐
 │ 自组网：同一个 ROS domain，DDS 自动发现，不需要成员名单                              │
 │                                                                                   │
 │  ┌──────── edge-01（当前的集群主节点）──────────┐   ┌──── edge-02 … edge-12 ──────┐  │
 │  │ 控制进程                                     │   │ 控制进程                      │  │
 │  │   选主 · 网关 · UE HTTP · 资源/链路测量        │   │   选主 · 网关 · UE HTTP · 测量 │  │
 │  │   ★ 控制面：任务表 · 调度 · 对账               │   │   （控制面不启用）              │  │
 │  │ 数据面进程                                   │   │ 数据面进程                    │  │
 │  │   执行器 ─直接调用→ PKCI / PKCT 引擎           │   │   执行器 → PKCI / PKCT        │  │
 │  │ 取图进程（airsim_camera）                     │   │ 取图进程                      │  │
 │  └──────────────────────────────────────────────┘   └───────────────────────────────┘  │
 └───────────────────────────────────────────────────────────────────────────────────┘
```

- **所有节点**都是执行者：运行数据面，接收任务、做推理、发布结果。
- **一个节点**同时是集群主节点：它的控制进程额外启用控制面。其他节点的控制面代码也在，只是不工作；一旦当选就开始工作。
- **所有节点**都运行网关：UE 可以连任意节点。不是集群主节点的网关把请求转发给集群主节点。

集群主节点的身份是**临时的**：它只在当选期间持有任务表，卸任或挂掉时任务表随之消失。这是有意为之（第 9 章 D3）。

### 2.3 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层   ue_api.py (HTTP)        ros/control_node.py (ROS 服务) │
├──────────────────────────────────────────────────────────────┤
│ 控制层   control/  网关 · 集群主节点控制器 · 任务表存储 · UE 后端  │  不依赖 ROS
├──────────────────────────────────────────────────────────────┤
│ 核心层   core/     选主 · 任务表 · 调度 · 对账 · 执行栅栏 ·       │  纯逻辑
│                    链路估计 · 集群视图 · 任务规格 · 数据源地址     │  禁止 import ROS
├──────────────────────────────────────────────────────────────┤
│ 适配层   ros/      dispatcher · forwarder · convert · qos         │  ROS 消息 ↔ 核心对象
├──────────────────────────────────────────────────────────────┤
│ 数据面   cccp_task_executor/  执行器 · 推理后端 · AirSim 取图 ·    │  每个节点都运行
│          压缩转发    collab_inference/  PKCI/PKCT 引擎             │
└──────────────────────────────────────────────────────────────┘
```

为什么核心层禁止 import ROS（`test_core_is_ros_free.py` 会检查）：

1. **测试**：选主、任务表、对账这些最容易出错的逻辑，可以在没有 ROS 的机器上用 pytest 跑完，包括随机历史测试和多节点仿真。
2. **转 C++**：核心层的每个模块都是“输入一份视图，输出一组动作”，可以逐个对照翻译，并用同一组测试用例验证。
3. **时间可注入**：所有时钟都由调用方传入，测试可以精确模拟“5 秒后”。

控制层也不依赖 ROS：下发（`Dispatcher`）和转发（`Forwarder`）都是注入的接口。`test_controller.py` 用一个模拟的集群（`_sim.py`）驱动控制器，可以模拟丢消息、节点离线、两个集群主节点并存等情况。

### 2.4 进程和线程

每个节点运行 3 个进程：

| 进程       | 入口                                       | 内容                                                           | 为什么单独一个进程                                                                    |
| ---------- | ------------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 控制进程   | `ros2 run cccp_node control_node`        | 选主、网关、UE HTTP、资源采集、链路测量；当选后启用控制面      | 必须保持轻量。如果被推理拖慢，`NodeStatus` 发不出去，节点会被判定离线，甚至引发换主 |
| 数据面进程 | `ros2 run cccp_task_executor data_plane` | 执行器 + PKCI + PKCT，用一个 `MultiThreadedExecutor` 运行    | 推理和图像处理很耗 CPU，受 GIL 影响，不能和控制进程放在一起                           |
| 取图进程   | `airsim_camera`                          | 从 AirSim 取本机无人机的相机画面，发布到 `<ns>/camera/image` | 独立的取图程序，和平台其他部分只通过这个 topic 交互                                   |

执行器、PKCI、PKCT 如果各占一个进程，每块板卡就是 5 个进程；合并成一个数据面进程后是 3 个，全集群的 DDS 参与者从 60 个降到 36 个。DDS 发现流量和参与者数量的平方相关，在无线网络上这一点很重要。

**控制进程内部的线程**：

| 线程                     | 做什么                                                                                     | 注意                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| ROS 执行器（8 线程）     | 收发 `NodeStatus`、`ExecutorStatus`、`TaskReport`；处理 `api/*`、`leader/*` 服务 | `NodeStatus` 的收发和选主在一个互斥回调组里，保证选主的输入一致 |
| 控制器线程               | 10 Hz 循环：处理 `TaskReport`；每秒对账一次                                              | 只在当选且预热结束后真正工作                                      |
| UE HTTP 线程             | 每个请求一个线程                                                                           | 创建任务的请求会阻塞最多 10 秒，等任务跑起来                      |
| 出站队列（50 ms 定时器） | 把其他线程产生的 ROS 动作（发布 `TaskStatus`、订阅结果）交给 ROS 线程执行                | ROS 实体只在执行器线程里创建                                      |

阻塞的服务调用（下发 `StartTask`、转发请求）使用独立的可重入回调组，不会阻塞它们等待的回复。

**数据面进程和控制进程之间**只有一个 topic：`<ns>/exec/status`（`ExecutorStatus`，1 Hz）。控制进程把它的内容（正在运行的任务、算法是否就绪）填进下一条 `NodeStatus`。如果超过 3 秒（`executor_timeout`）没收到，控制进程就上报“没有任务、推理未就绪”：调度器不再往这个节点派任务，集群主节点也会认为这个节点上的任务消失了，按第 6.4 节处理。

### 2.5 通信方式

先讲选择的逻辑：

| 通信方式                 | 用在哪里                                                                                               | 原因                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| **Topic 广播**     | `/cluster/node_status`（所有节点 ↔ 所有节点，1 Hz）                                                 | 一对多、周期性、只有最新值有用；丢一条下一秒就补上     |
| **Topic（可靠）**  | `/cluster/task_report`（执行节点 → 集群主节点）、`/cluster/task_status`（集群主节点 → 所有网关） | 状态变化的通知；丢了有对账兜底                         |
| **Service**        | `leader/task/*`（网关 → 集群主节点）、`exec/task/*`（集群主节点 → 执行节点）                     | 低频、需要明确结果的请求                               |
| **Topic（逐帧）**  | `<ns>/task/result`、`<ns>/input/...`、`.../compressed`                                           | 高频数据流；可以多个订阅者；丢帧没关系                 |
| **进程内函数调用** | 执行器 → PKCI/PKCT 引擎                                                                               | 同一进程，省掉序列化和 DDS 往返                        |
| **HTTP**           | 只用于 UE ↔ 节点                                                                                      | UE 只需要知道任意一个节点的地址；节点之间禁止使用 HTTP |

整个系统**没有**独立的一致性协议，**没有**节点之间两两建立的 TCP 连接，对网络唯一的要求是 DDS 能正常发现和通信。

全部端点：

| 名称                                         | 类型                            | 方向                         | QoS                       | 说明                                                    |
| -------------------------------------------- | ------------------------------- | ---------------------------- | ------------------------- | ------------------------------------------------------- |
| `/cluster/node_status`                     | `NodeStatus` topic            | 所有节点 → 所有节点         | BEST_EFFORT, KEEP_LAST(1) | 资源、心跳、选主声明、链路、正在运行的任务（第 3.2 节） |
| `/cluster/task_report`                     | `TaskReport` topic            | 执行节点 → 集群主节点       | RELIABLE, KEEP_LAST(100)  | 执行状态变化（第 3.5 节）                               |
| `/cluster/task_status`                     | `TaskStatus` topic            | 集群主节点 → 所有节点       | RELIABLE, KEEP_LAST(100)  | 任务表变化，供网关生成事件流                            |
| `<ns>/api/task/create\|destroy\|query`       | `CreateTask` 等 srv           | 任何调用方 → 本节点网关     | —                        | 对外入口；本节点不是集群主节点时转发给它                |
| `<ns>/leader/task/create\|destroy\|query`    | 同上                            | 其他节点的网关 → 集群主节点 | —                        | 只在本地处理，**不再转发**                        |
| `<ns>/exec/task/start\|stop`                | `StartTask`/`StopTask` srv  | 集群主节点 → 执行节点       | —                        | 内部接口，其他程序不得调用                              |
| `<ns>/exec/status`                         | `ExecutorStatus` topic        | 数据面进程 → 本节点控制进程 | BEST_EFFORT, KEEP_LAST(1) | 正在运行的任务、算法是否就绪（第 2.4 节）               |
| `<ns>/algorithms/pkci/*`、`pkct/*`       | srv                             | 执行器 → 推理引擎           | —                        | 只在 `INFERENCE_BACKEND=ros` 时使用（第 4.3 节）      |
| `<ns>/camera/image`                        | `sensor_msgs/Image`           | 取图进程 → 本节点执行器     | sensor data               | 本机无人机的默认相机                                    |
| `<ns>/input/airsim/<vehicle>/cam_<camera>` | `sensor_msgs/Image`           | 按需取图 → 本节点执行器     | sensor data               | 有任务使用 `airsim://` 输入时才存在（第 7.4 节）      |
| `<ns>/<topic>/compressed`                  | `sensor_msgs/CompressedImage` | 数据所在节点 → 其他参与节点 | sensor data               | JPEG；只在有订阅者时才编码（第 7.5 节）                 |
| `<ns>/task/result`、`result_image`       | `TaskResult` / `Image`      | 执行节点 → 汇总方、网关     | RELIABLE, KEEP_LAST(10)   | 逐帧结果和结果叠加图                                    |
| `http://<节点>:18090/api/ue/*`             | HTTP/JSON                       | UE → 任意节点               | —                        | UE 接口（第 4.7 节）                                    |

所有 topic 的 Durability 都是 VOLATILE：新加入的订阅者不会收到历史消息，需要的状态都由周期性的 `NodeStatus` 或查询补上。QoS 集中定义在 `cccp_node/ros/qos.py`，端点名集中定义在 `cccp_node/names.py`。`<ns>` 是由节点名推导出的命名空间：非 `[A-Za-z0-9_]` 字符替换为 `_`，例如 `edge-01` 对应 `/edge_01`。

两条容易踩的坑：

- **服务名必须唯一**。整个 ROS domain 中，同一个服务名只能有一个服务端，所以所有服务都在节点自己的命名空间 `<ns>` 下，全局名字 `/cluster/*` 只用于 topic。同名服务有多个服务端时，ROS 2 没有定义会发生什么，实际上请求通常会被每个服务端都执行一遍。如果把下发接口命名成全局的 `/cluster/start`，换主过渡期里新旧两个集群主节点都会提供这个服务，一次请求会被两边都执行。
- **转发只转一次**。公开入口 `api/task/*` 收到请求后，如果自己不是集群主节点，就调用集群主节点的 `leader/task/*`；`leader/task/*` 只在本地处理，自己不是集群主节点就直接报错，不再转发。这样即使各节点对“谁是集群主节点”的看法暂时不一致，请求也不会在节点之间来回转。

## 3 状态模型

### 3.1 系统里有哪些状态

分布式系统设计的核心问题是：每一份状态**存在哪里、谁写、谁读、丢了怎么办**。下表列出了全部状态。

| 状态                                      | 内容                                                         | 存在哪里                                       | 谁写                         | 谁读                                 | 丢了怎么办                                         |
| ----------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------- | ---------------------------- | ------------------------------------ | -------------------------------------------------- |
| **节点状态** `NodeStatus`         | 资源、链路、选主声明、正在运行的任务                         | 每个节点各自发布；每个节点都缓存全集群的最新值 | 每个节点只写自己的           | 所有节点                             | 1 秒后下一条覆盖                                   |
| **期望状态**：任务表 `TaskRecord` | 应该有哪些任务、由谁执行、处于什么状态                       | **只在集群主节点内存**                   | 只有集群主节点的控制器和网关 | 集群主节点                           | 换主后由实际状态重建；还没落到执行者身上的部分丢失 |
| **实际状态**：`TaskState`         | 某个节点正在运行的某个任务（含完整规格）                     | 各执行器内存；随 `NodeStatus` 广播           | 执行器                       | 集群主节点（对账）、所有节点（缓存） | 执行器进程挂了，它的任务就真的没了，对账会重新调度 |
| **变化通知**                        | `TaskReport`（执行状态变化）、`TaskStatus`（任务表变化） | 消息流，不存储                                 | 执行器 / 集群主节点          | 集群主节点 / 网关和 UE               | 丢了由对账或查询补上                               |
| **本地辅助状态**                    | 链路测量、执行栅栏、对账计时、事件缓存等                     | 各节点内存                                     | 本节点                       | 本节点                               | 重启后从头开始，只会让决策晚一点                   |

整个系统的设计可以归结为一句话：**期望状态集中、短命；实际状态分散、可靠；两者每秒对一次账。** 这和 Kubernetes 的控制器模式是一样的，区别是我们的“期望状态”不持久化，丢了就从实际状态重建。

### 3.2 节点状态 `NodeStatus`

每个节点每秒发布一条，所有节点都订阅（`BEST_EFFORT`、`KEEP_LAST(1)`）。它同时承担五种作用：

| 作用                     | 字段                                                                                                                                                                                                        | 读的人用它做什么                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 心跳                     | `node_name`、`incarnation`、`seq`、`stamp`                                                                                                                                                          | 5 秒收不到就判定离线；`incarnation` 变了说明节点重启过；`seq` 的空洞用来算丢包            |
| 选主声明 / 租约          | `leader_name`、`term`、`is_leader`                                                                                                                                                                    | 选主（第 5 章）；集群主节点的每一条 `NodeStatus` 都是一次续约                               |
| 能力和资源               | `inference_ready`、`algorithms_ready`；`cpu_model`、`cpu_cores`、`mem_total_mb`、`gpu_model`、`gpu_mem_total_mb`；`cpu_usage`、`mem_usage`、`gpu_usage`、`gpu_mem_usage`、`battery` | 调度器过滤和评分。Jetson 的 `gpu_mem_total_mb` 填 0，表示 GPU 和系统共享内存；未知的值填 -1 |
| 链路测量                 | `links[]`（`LinkQuality`：对每个对端的 `rtt_ms`、`jitter_ms`、`loss_rate`，以及 `echo_seq`、`echo_delay_ms`）                                                                                 | 调度器的网络评分；回显字段用于对端计算 RTT（第 8.4 节）                                       |
| **正在运行的任务** | `tasks[]`（`TaskState`）                                                                                                                                                                                | 对账的“实际状态”；换主后重建任务表                                                          |

`NodeStatus` 是全系统最重要的消息。它的设计原则是**每一条都自包含**：收到任意一条，就知道这个节点此刻的全部情况，不依赖之前的消息。所以它可以用 `BEST_EFFORT`，丢了不用重传。

**大小估算**：基础字段约 300 字节；每条 `LinkQuality` 约 40 字节，11 个对端约 450 字节；每个 `TaskState` 含 `spec_json`，约 500～800 字节，每节点最多 4 个任务。合计每条约 1～4 KB，12 个节点每秒合计约 12～48 KB，在无线链路上可以接受。如果以后规格变大，可以考虑只在规格变化时附带 `spec_json`。

### 3.3 期望状态：任务表

任务表（`core/task_table.py`）的每条记录 `TaskRecord`：

| 字段                                             | 含义                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `task_id`                                      | UUID 字符串，集群主节点在接受任务时生成                                               |
| `idempotency_key`                              | 幂等键。任务表维护“键 → task_id”的索引，同一个键只对应一个任务                     |
| `spec`                                         | 任务规格 `TaskSpec`：类型、协同模式、辅助节点数、资源需求、输入地址、参数等         |
| `name`                                         | 任务名；为空时自动生成为 `<类型>-<task_id 前 8 位>`                                 |
| `status`                                       | `Pending` / `Scheduled` / `Running` / `Finished` / `Failed` / `Cancelled` |
| `epoch`                                        | 执行代次，每次（重新）调度加 1                                                        |
| `primary`、`helpers`                         | 当前代次的任务主节点和辅助节点                                                        |
| `error_code`、`error_message`                | 失败原因                                                                              |
| `last_event`、`submitted_ms`、`updated_ms` | 给人看的最近事件和时间                                                                |

**写入规则**：

- 唯一的写入口是 `apply(command)`，命令有 8 种：`Submit`、`Adopt`、`Assign`、`Requeue`、`ReportStatus`、`MarkFailed`、`Cancel`、`Prune`。记录不可变，每次修改生成新记录。`control/task_store.py` 负责加锁。
- 只有集群主节点的控制器和网关可以写任务表；其他节点的网关一律转发。
- 每次以新的 term 当选时，任务表从空开始，预热结束后通过 `Adopt` 重建（第 4.9 节）。`Adopt` 只接收比任务表中更新（epoch 更大）的版本；如果幂等键已经被另一个任务占用，就拒绝接收。
- 每次修改产生一条 `StatusEvent`（带本任期内的序号 `seq`），集群主节点把它发布为 `TaskStatus`。
- `Assign`、`Requeue`、`MarkFailed` 都带 `expected_epoch`，按“比较后再修改”的方式执行：任务已经不在这个 epoch 了，命令就失败（`STALE_EPOCH`）。这样，基于同一份视图做出的两个决策，最多只有一个生效。
- **先写任务表，后下发**：调度结果必须先写进任务表，再调用 `StartTask`。这样在当前任期内，任务表总是领先于实际执行情况，对账才有依据。

**状态机**：

```
            ┌─────────────── requeue(epoch+1) ◄──────────────┐  下发暂时失败，或重新调度时没有可用节点
            ▼                                                │
Pending ──assign(epoch+1)──► Scheduled ──report Running──► Running ──report Finished──► Finished
   │                            │  ▲                         │
   │                            │  └──assign(epoch+1)────────┤  任务主节点离线 / 丢失任务 / 迟迟不启动
   ▼                            ▼                            ▼
 Failed                       Failed                       Failed
（Pending 超时，              （下发时返回 INVALID_INPUT     （任务主节点报告 Failed）
  NO_FEASIBLE_NODE）           等永久错误：DISPATCH_FAILED）

（任务表不知道的运行中任务）──adopt──► Running        任何非终态 ──destroy──► Cancelled
终态：Finished / Failed / Cancelled，之后不再变化
```

- **单调性**：定义状态序 Pending=0、Scheduled=1、Running=2、终态=3。`(epoch, 状态序)` 按字典序**只增不减**，会让它变小的更新一律忽略。重新调度和 `Requeue` 让状态“往回走”，但同时把 epoch 加 1，所以 `(epoch, 状态序)` 仍然增大。
- **下发失败的处理**：`INVALID_INPUT`、`UNSUPPORTED_VERSION` 是永久错误，直接判定 Failed；其他错误（超时、`BUSY`、`NOT_READY`）执行 `Requeue`，并在 60 秒内避开这个节点；收到 `STALE_TERM` 说明自己已经不是集群主节点，什么也不做。
- **运行中没有输入**：任务主节点超过 `input_timeout`（10 秒）收不到一帧，执行器报告 `Failed`（`NOT_READY`）并停掉任务。集群主节点不把它记为终态，而是执行 `Requeue`，并在 60 秒内避开这个节点（换个节点也许能取到数据）；同一个任务累计 `max_input_stalls`（3）个任务主节点都没有输入，或者任务用 `request_node` 指定了节点，才判定 Failed（`NOT_READY`）。辅助节点不做这项检查。计数只在集群主节点内存里，换主后重新计。
- **`request_node` 是硬性指定**：被指定的节点挂掉后，任务不会迁移到其他节点。不指定节点的任务会迁移。

**为什么任务表不复制给其他节点**：见第 9 章 D3。简单说，复制它需要共识协议；而它里面真正不可替代的信息（还没跑起来的任务、历史）用幂等重试和 UE 侧保存就能弥补。

### 3.4 实际状态：`TaskState`

执行器对它正在运行的每个任务，在 `ExecutorStatus.tasks` 中上报一条 `TaskState`，控制进程原样转进 `NodeStatus.tasks`：

| 字段                               | 含义                      | 为什么需要                                                    |
| ---------------------------------- | ------------------------- | ------------------------------------------------------------- |
| `task_id`、`epoch`             | 哪个任务的哪一代          | 对账的主键                                                    |
| `role`                           | `primary` 或 `helper` | 区分任务主节点和辅助节点的副本                                |
| `primary_node`、`helper_nodes` | 这一代的完整分工          | 新集群主节点只看到辅助节点的副本时，也能恢复出任务主节点是谁  |
| `idempotency_key`                | 幂等键                    | 换主后重建“键 → task_id”索引，否则调用方重试会创建重复任务 |
| `name`、`spec_json`            | 名称和完整规格            | 换主后能完整恢复任务表记录，之后还能重新调度                  |

`TaskState` 本质上是“执行者持有的任务表副本”，只不过每个执行者只持有自己参与的那几行。所有执行者的 `TaskState` 拼起来，就是“所有正在运行的任务”这部分任务表。

### 3.5 变化通知

| 消息           | 方向                                   | 内容                                                                                                                                       | 用途                                                                |
| -------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| `TaskReport` | 执行节点 → `/cluster/task_report`   | `node_name`、`task_id`、`epoch`、`state`（Running/Finished/Failed/Stopped）、`error_code`、`message`、`incarnation`、`seq` | 让集群主节点**立即**知道状态变化，不用等下一条 `NodeStatus` |
| `TaskStatus` | 集群主节点 → `/cluster/task_status` | 任务表每次变化的快照，`(term, seq)` 唯一                                                                                                 | 各节点网关生成 UE 的事件流                                          |

`TaskReport` 是“快速通道”，`NodeStatus.tasks` 是“兜底通道”：

- 正常情况下，执行器启动任务后马上发 `Running` 报告，集群主节点几毫秒内就把任务表更新为 Running，网关就能回复调用方。
- 如果 `Running` 报告丢了，下一轮对账发现“任务表说 Scheduled，但节点上报说在跑”，就由集群主节点代为提交 `ReportStatus(Running)`（对账动作 `ConfirmRunning`）。

处理规则：

- 集群主节点按 `(node_name, incarnation)` 记录每个执行器最后一条报告的 `seq`，重复或乱序的报告丢掉。
- 只有任务主节点的报告能驱动任务状态。辅助节点的报告、`Stopped` 确认、对终态任务的迟到报告都只记录，不改变状态。
- `epoch` 小于任务当前 epoch 的报告一律丢弃（`STALE_EPOCH`）。

### 3.6 本地辅助状态

| 状态                        | 在哪里             | 内容                                                       | 丢了的后果                                         |
| --------------------------- | ------------------ | ---------------------------------------------------------- | -------------------------------------------------- |
| 集群视图 `ClusterView`    | 每个节点的控制进程 | 每个节点最新的 `NodeStatus` 和**本地**收到它的时间 | 重启后 5 秒内视图不完整，所以选主有启动等待        |
| 链路估计 `LinkEstimator`  | 每个节点的控制进程 | 每个对端的 RTT、抖动、丢包窗口                             | 重新测量，调度器在测出之前用默认值                 |
| 选主状态 `Election`       | 每个节点的控制进程 | 自己认的集群主节点、任期、最近一次看到声明的时间           | 重启后重新等待和跟随                               |
| 执行栅栏 `ExecutionGuard` | 每个执行器         | 见过的最大 `term`、每个任务当前的 `epoch`              | 执行器重启后最大 term 归零（第 10.1 节的已知限制） |
| 对账记忆 `LeaderMemory`   | 集群主节点         | 每个任务何时下发、何时发现缺失、何时发过 `StopTask`      | 换主后重新计时，决策晚几秒                         |
| 失败节点表                  | 集群主节点         | 某任务在某节点上启动失败或没有输入的时间（60 秒内避开）；每个任务没有输入的次数 | 换主后可能再试一次那个节点                         |
| 事件缓存 `EventLog`       | 每个节点的 UE 后端 | 最近 2000 条事件（状态变化、逐帧结果）                     | UE 可以重新查询                                    |

### 3.7 只存在于集群主节点内存里的信息

这一节回答“集群主节点挂了到底丢什么”：

| 信息                                                      | 换主后能否恢复                              | 后果                                                                             |
| --------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------- |
| 正在运行的任务（Running）                                 | **能**，从各节点的 `TaskState` 恢复 | 无                                                                               |
| 已调度、已在执行者上启动的任务（Scheduled，但实际已在跑） | **能**，同上，接收后状态是 Running    | 无                                                                               |
| 已调度、但下发请求还没到执行者的任务                      | 不能                                        | 丢失；调用方的创建请求会收到失败，用同一个幂等键重试                             |
| 排队中的任务（Pending）                                   | 不能                                        | 同上                                                                             |
| 刚创建、还没到第一轮对账的任务                            | 不能                                        | 同上                                                                             |
| 已结束任务（Finished/Failed/Cancelled）的历史             | 不能                                        | 查询返回 `NOT_FOUND`；需要的话由 UE 保存                                       |
| 已结束任务的幂等键                                        | 不能                                        | 换主后用同一个键重试，会创建一个新任务（因为旧任务已结束，这通常也是期望的行为） |
| 集群主节点自己正在执行的任务                              | 不能                                        | 丢失；调用方需要重新提交（第 6.1 节）                                            |
| 对账计时、失败节点表                                      | 不能                                        | 只会让决策晚一点                                                                 |

前四行的共同点是：**任务还没有落到任何一个执行者身上**。这类任务统一按“下发失败”处理，由调用方重试。这是整个设计中最关键的一次简化（第 9 章 D4、D5）。

### 3.8 标识

| 标识               | 生成方式                                  | 规则                                                     |
| ------------------ | ----------------------------------------- | -------------------------------------------------------- |
| `task_id`        | 集群主节点在接受任务时生成 UUID（字符串） | 全局唯一，不依赖计数器，换主后也不会重复                 |
| `epoch`          | 每次（重新）调度时加 1                    | 首次调度时为 1；换主后沿用执行者上报的值                 |
| `term`           | 选主时取“已知最大 term 加 1”            | 只增不减                                                 |
| `TaskStatus.seq` | 集群主节点在本任期内的变更序号            | 订阅方按 `(term, seq)` 去重和排序；换主后从 1 重新开始 |
| `incarnation`    | 进程启动时的 Unix 毫秒                    | 用来判断节点是否重启过                                   |
| PKCT 会话 ID       | `task-<task_id>-<epoch>`                | 新旧代次是不同的会话                                     |
| 幂等键             | 调用方生成，格式见下文                    | 同一个“意图”的重试沿用同一个键                         |

下面解释几个不直观的点。

**`task_id` 为什么是 UUID**：没有复制的计数器，换主后新集群主节点不知道旧的计数器到了多少；用 UUID 就不需要知道。代价是 UE 侧要把 task_id 当字符串处理。

**`term` 和 `epoch` 的区别**：

|            | `term`（任期）                                                                           | `epoch`（执行代次）                                                                 |
| ---------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 属于谁     | 集群主节点                                                                                 | 任务                                                                                  |
| 何时增加   | 选出新的集群主节点时                                                                       | 任务每次（重新）调度时                                                                |
| 防的是什么 | **过期的集群主节点**继续下发或停止任务                                               | **过期的执行会话**继续上报状态和结果                                            |
| 谁来检查   | 执行器（`ExecutionGuard`）                                                               | 执行器、任务表、结果的汇总方                                                          |
| 例子       | 旧集群主节点从网络隔离中恢复，向某个执行器发 `StopTask`，执行器已经见过更高的 term，拒绝 | 任务主节点 A 掉线，任务以 epoch 2 迁移到 B；A 恢复后还在发 epoch 1 的结果，汇总方丢弃 |

换主不改变 epoch：新集群主节点接收任务时沿用执行者上报的 epoch，任务不重启。迁移任务不改变 term：同一个集群主节点在任期内可以多次重新调度。

**执行器怎么检查 term 和 epoch**（`core/execution_guard.py`）：执行器记录自己见过的最大 term，以及每个任务当前的 epoch，按下表处理收到的命令：

| 收到的命令                                                      | 处理                                                   |
| --------------------------------------------------------------- | ------------------------------------------------------ |
| `term` < 已知的最大 `term`                                  | 拒绝，返回 `STALE_TERM`                              |
| `StartTask`：同一 `task_id`、同一 `epoch`，任务已经在运行 | 返回**成功**（幂等，所以集群主节点可以放心重发） |
| `StartTask`：同一 `task_id`、更大的 `epoch`               | 先停掉旧会话，再按新 epoch 启动                        |
| `StartTask`：同一 `task_id`、更小的 `epoch`               | 拒绝，返回 `STALE_EPOCH`                             |
| `StopTask`：任务本来就不在运行                                | 返回成功（幂等）                                       |

集群主节点处理 `TaskReport`、汇总方处理 `TaskResult` 时，同样丢弃 epoch 小于任务当前 epoch 的消息。

**幂等键**：调用方为每个“意图”生成一个键，重试时沿用。在这个设计里，幂等键是调用方重试时避免重复执行的唯一手段。格式按触发来源区分（第 4.8 节）：

| 来源     | 格式                                             | 由谁生成                          |
| -------- | ------------------------------------------------ | --------------------------------- |
| manual   | `manual:<客户端ID>:<UUID>`                     | UE 或前端在每次用户操作时生成一次 |
| schedule | `schedule:<规则ID>:<计划触发时刻的 Unix 毫秒>` | 集群主节点上的定时器              |
| chain    | `chain:<父任务ID>:<规则名>[:<frame_id>]`       | 父任务的任务主节点                |
| event    | `event:<节点名>:<事件源>:<事件序号>`           | 产生事件的节点                    |
| 为空     | `anon:<UUID>`                                  | 网关自动生成；这样的请求无法去重  |

注意：同一个键对应的任务**失败之后**，在它被清理（1 小时）之前，再用这个键提交只会返回那个失败的任务；想重新来一次，需要用新的键。

**`incarnation`**：进程启动时的 Unix 毫秒。同一个节点名的 `incarnation` 变了，说明进程重启过，它的 `seq` 从头开始，链路测量和报告去重都要重置。

## 4 关键流程

### 4.1 创建任务

```
UE           网关(edge-07)           集群主节点(edge-01)                    执行器(edge-04)
 │ POST /tasks   │                         │                                      │
 │──────────────►│ 1 校验和规范化规格        │                                      │
 │               │ 2 自己不是集群主节点：    │                                      │
 │               │   调用 edge-01 的         │                                      │
 │               │   leader/task/create      │                                      │
 │               │────────────────────────►│ 3 Submit：生成 UUID，Pending            │
 │               │                         │   （键已存在：直接返回原任务，duplicate）│
 │               │                         │ 4 下一轮对账（≤1 秒）：                  │
 │               │                         │   调度 → Assign：epoch=1，Scheduled     │
 │               │                         │   （先写任务表，再下发）                  │
 │               │                         │ 5 exec/task/start(term, epoch, 规格)   │
 │               │                         │─────────────────────────────────────►│ 6 栅栏检查 term/epoch
 │               │                         │                                      │   订阅输入、建会话
 │               │                         │◄──────────────── success ────────────│
 │               │                         │◄──── /cluster/task_report: Running ───│
 │               │                         │ 7 ReportStatus → Running              │
 │               │◄── success, task_id ────│   （网关一直在等这个状态）              │
 │◄── 200 ───────│                         │                                      │
```

步骤说明：

1. **校验**（`normalize_spec`）：类型、模式、辅助节点数和 `target_nodes` 是否匹配、链式触发的深度、资源需求的范围、`params_json` 是否合法（PKCT 必须有 bbox）、输入地址能否解析。不合法直接返回 `INVALID_INPUT`，不打扰集群主节点。`ros://` 地址会自动把 `input_node` 设为数据所在节点。
2. **路由**（`Gateway._route`）：
   - 自己是集群主节点且预热完毕 → 本地处理；
   - 知道集群主节点是谁 → 转发一次（超时 = 等待时间 10 秒 + 5 秒）；
   - 自己刚当选还在预热，或者当前没有集群主节点 → 立即返回 `NO_LEADER`。
3. **Submit**：幂等键已存在，就直接返回那个任务（`duplicate=true`），然后同样等它跑起来。
4. **调度**：对账器每秒运行一次，把 Pending 任务交给调度器（第 8 章）。选中后先 `Assign`（写任务表），再下发。
5. **下发**：对任务主节点和每个辅助节点依次调用 `exec/task/start`，单次超时 5 秒。
6. **执行器**：先检查 term/epoch（第 3.8 节），再检查算法是否就绪、能否获得输入，然后建立会话、订阅输入，发 `Running` 报告。
7. **等待**：网关在任务表上等待，直到任务变成 Running 或终态，最多 10 秒（`create_wait_timeout_s`）。

**创建请求的所有可能结果**：

| 情况                                           | 返回                                                       | HTTP | 调用方应该                           |
| ---------------------------------------------- | ---------------------------------------------------------- | ---- | ------------------------------------ |
| 任务已在运行                                   | 成功，`task_id`、`assigned_node`、`dispatched_nodes` | 200  | —                                   |
| 同一个键的任务已经在运行                       | 成功，`duplicate=true`                                   | 200  | —                                   |
| 规格不合法                                     | `INVALID_INPUT` / `CHAIN_TOO_DEEP`，没有 task_id       | 400  | 修正请求                             |
| 没有集群主节点 / 正在选主 / 新集群主节点在预热 | `NO_LEADER`，没有 task_id                                | 503  | 退避后重试（同一个键）               |
| 10 秒内没跑起来（排队、下发失败后重试中）      | `TIMEOUT`，**带 task_id**                          | 503  | 用同一个键重试；跑起来后会返回原任务 |
| 等待期间换主                                   | `NO_LEADER`，带 task_id                                  | 503  | 用同一个键重试                       |
| 没有可用节点（Pending 超过 8 秒）              | `NO_FEASIBLE_NODE`，带 task_id                           | 502  | 调用方决定                           |
| 执行器拒绝（规格错误等永久错误）               | `DISPATCH_FAILED`，带 task_id                            | 502  | 检查规格                             |
| 任务启动后立即失败                             | 执行器报告的错误码，例如 `INFERENCE_ERROR`               | 502  | 调用方决定                           |

`pending_timeout_s`（8 秒）故意比等待时间（10 秒）短：找不到节点时，调用方能在等待时间内拿到明确的 `NO_FEASIBLE_NODE`，而不是含糊的 `TIMEOUT`。

**为什么只有“跑起来”才算成功**：如果“写入任务表”就算成功，集群主节点在下发前挂掉，任务就凭空消失了，而调用方以为已经成功。现在的语义是：成功意味着任务已经在某个执行者上，它的存在由执行者保证；失败意味着调用方需要重试，重试是安全的，因为有幂等键。

**正常耗时估算**（尚未在真实环境测量）：转发 1 次服务调用 + 等待下一轮对账（0～1 秒）+ 下发 1 次服务调用 + 执行器启动（订阅输入，算法已就绪时为毫秒级）≈ 0.1～1.2 秒，加上网络往返。

### 4.2 重试和幂等

```
第一次：  POST /tasks {idempotency_key: "manual:ue-3:9f1c…"}  ──►  503 TIMEOUT, task_id=T
          （任务在排队，或者集群主节点刚挂了）
重试：    POST /tasks {idempotency_key: "manual:ue-3:9f1c…"}  ──►  200, task_id=T, duplicate=true
                                                               或  200, task_id=T'（旧集群主节点
                                                                    挂了，任务 T 从未落地，新建 T'）
```

- 如果任务 T 其实已经在跑了（哪怕是旧集群主节点下发的），新集群主节点已经从 `TaskState` 中接收了它，包括它的幂等键，所以重试会命中 T。
- 如果 T 从未落到任何执行者上，新集群主节点不知道 T，就新建一个任务 T'。因为 T 不存在于任何地方，这不是重复。
- 唯一的窗口：T 的下发请求已经到达执行者、执行者正在启动，而新集群主节点恰好在这个时刻处理重试。新集群主节点会新建 T'，下一轮对账时发现 T 和 T' 的幂等键相同，判定后出现的那个为重复，停掉它（第 4.9 节对账表第 2 行）。这就是“可能短暂重复”的一个具体例子。

UE 侧需要做的事：每次用户操作生成一个键；收到 503 时退避重试，**沿用同一个键**；连不上某个节点就换下一个节点（所有节点的接口都一样）。

### 4.3 每一帧的处理

```
输入 topic ──► 执行器 _on_frame ──► 推理后端 ──► 引擎（PKCI classify / PKCT track）
   │              │ 该任务上一帧                       │
   │              │ 还没处理完：丢弃这一帧              ▼
   │                                       TaskResult ──► <ns>/task/result
   │                                       结果叠加图 ──► <ns>/task/result_image（有人订阅时）
```

- **只处理最新帧**：一个任务的上一帧还在处理时，新到的帧直接丢弃。这样任务总是处理最新的画面，延迟不会累积；PKCT 收到的帧也严格有序。
- **PKCT 的会话**：第一帧用规格里的 bbox 初始化跟踪器，之后逐帧跟踪。会话 ID 是 `task-<task_id>-<epoch>`，所以迁移后的新代次是一个全新的会话，旧会话的残留不会干扰它。
- **失败计数**：连续失败 10 次（`max_consecutive_failures`），执行器报告 `Failed`（`INFERENCE_ERROR`）。PKCT 初始化失败立即报告失败。
- **无输入检测**：任务主节点从启动或上一帧起超过 `input_timeout`（10 秒）收不到帧，报告 `Failed`（`NOT_READY`）。只看帧是否到达，被丢弃的帧也算；推理慢不会触发。集群主节点收到后换节点重试，见第 3.3 节。
- **推理后端**（`inference.py`）：默认 `LocalBackend`，在同一进程内用线程池直接调用引擎，返回 future；设置 `INFERENCE_BACKEND=ros` 可以改走 `<ns>/algorithms/*` 服务。两种后端接口相同，集成测试各跑一遍。
- **结果的接收者**：网关只有在 UE 问到某个任务时，才订阅执行它的节点的结果 topic（`ue_backend` 的 `watch`）。如果每个节点都订阅所有结果，无线链路上会多出约 8 Mbps 的流量。

**实测推理耗时**（640×480 合成图，`tools/inference_bench.py`）：

| 设备                        | PKCI P50  | PKCT P50  |
| --------------------------- | --------- | --------- |
| x86 CPU，8 线程             | 20.5 ms   | 24.4 ms   |
| x86 CPU，不限线程（144 核） | 约 102 ms | 约 147 ms |
| RTX 4090                    | 10.2 ms   | 12.1 ms   |

所以启动脚本里用 `OMP_NUM_THREADS`（`INFERENCE_THREADS`，默认 4）限制线程数。Orin 上的数据还要实测。

### 4.4 协同任务

| 模式          | 参与者                                   | 输入                                                          | 结果                                            | 当前实现状态                                                                                                             |
| ------------- | ---------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `local`     | 只有任务主节点                           | 按地址取                                                      | 任务主节点的结果                                | 完整                                                                                                                     |
| `redundant` | 任务主节点 + `helper_count` 个辅助节点 | **同一份输入**（必须用共享或绑定到节点的地址，第 7 章） | 最先返回的有效结果                              | 调度、下发、取数、每个参与者各自推理并发布 `TaskResult` 都已实现；**按 frame_id 选取最先有效结果的汇总尚未实现** |
| `fusion`    | 同上                                     | 各自的视角                                                    | 任务主节点汇总（PKCI `fuse`、PKCT `elect`） | 同上；**汇总尚未实现**                                                                                             |

协同任务的生命周期由任务主节点驱动：任务表只认任务主节点的状态报告。辅助节点失效时，MVP 不替换辅助节点，任务按 `min_participants`（最少有效参与数，含任务主节点）降级继续，达不到时任务主节点报告 `INSUFFICIENT_PEERS`。任务主节点失效时，整个任务（含所有辅助节点）以新的 epoch 重新调度，旧 epoch 的辅助节点副本在对账时被停掉。

协同载荷（PKCI 的 `increment`、PKCT 的 `identity`，都小于 1 KB）放在 `TaskResult.payload` 中通过 topic 传输，不放进服务请求，也不传图像。

### 4.5 销毁任务

```
UE ──DELETE /tasks/T──► 网关 ──leader/task/destroy──► 集群主节点：Cancel → Cancelled（终态）
                                                         │ 立即回复成功
                                                         ▼ 下一轮对账（≤1 秒）
                                         发现执行者还在跑一个终态任务 → StopTask(term, T, epoch)
                                                         ▼
                                         执行器停止会话、释放输入、发 Stopped 报告
```

销毁是“先改期望，再由对账让实际追上”。这样，销毁请求时执行节点暂时不可达也没关系：只要它回来，对账就会停掉它的副本，每 5 秒重发一次 `StopTask`（第 4.9 节对账表最后一行）。

对终态任务再次销毁返回 `INVALID_STATE`（HTTP 409）；不存在的任务返回 `NOT_FOUND`（404）。

### 4.6 查询和事件流

- **查询**（`GET /tasks/<id>`）：转发给集群主节点，读任务表。换主后查不到已结束的任务（第 3.7 节）。
- **事件流**（`GET /events?after=<seq>&wait=<秒>`）：长轮询。每个节点的 UE 后端订阅 `/cluster/task_status`，按 `(term, seq)` 去重后放进本地事件缓存。逐帧结果也会进入事件流（只针对被问过的任务）。
- **已知缺口**：只有集群主节点发布 `TaskStatus`。旧集群主节点已经应用、还没来得及发布就挂掉的那几条变化不会补发，`seq` 会跳号。UE 发现跳号时可以查询最新状态。

### 4.7 HTTP 状态码

网关回复中的 `error_code` 决定 HTTP 状态码（`ue_api.py`）：

| 情况                                                              | HTTP          |
| ----------------------------------------------------------------- | ------------- |
| 成功                                                              | 200           |
| 可以稍后重试：`NO_LEADER`、`BUSY`、`NOT_READY`、`TIMEOUT` | **503** |
| 创建：请求本身有问题，没有生成 task_id                            | 400           |
| 创建：任务已生成但失败                                            | 502           |
| 查询：任务不存在                                                  | 404           |
| 销毁：任务不存在                                                  | 404           |
| 销毁：任务已经结束                                                | 409           |

可以重试的错误一律不能映射成 4xx：如果“没有集群主节点”返回 400，UE 按状态码判断时，会把一个只需要稍后重试的情况当成请求错误而放弃（第 9 章 D15）。

### 4.8 其他触发方式

`CreateTask.origin` 区分四种触发来源，它们走同一个创建接口，只是幂等键的生成者不同（格式见第 3.8 节）：

| 来源         | 谁调用创建接口                                                               | 状态                                       |
| ------------ | ---------------------------------------------------------------------------- | ------------------------------------------ |
| `manual`   | UE 或前端                                                                    | 已实现                                     |
| `chain`    | 父任务的任务主节点（检测到某个结果后触发下一个任务）；`chain_depth` 最大 5 | 接口和校验已实现；**触发规则未实现** |
| `schedule` | 集群主节点上的定时器                                                         | **未实现**                           |
| `event`    | 产生事件的节点                                                               | **未实现**                           |

统一接口的意义在于：不管谁触发，任务的去重、调度、迁移、状态都一样，触发方只需要生成正确的幂等键。

### 4.9 对账

前面几节的流程都依赖对账来兜底。对账器（`core/reconciler.py`）在集群主节点上每秒运行一次：输入是任务表（应该跑什么）和各节点 `NodeStatus.tasks`（实际在跑什么），输出是一组动作。规则：

| 观察到的情况                                                                  | 动作                                                                                                                                                     |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 某节点运行着任务表**不知道**的任务，或者 epoch **比任务表新**     | **接收**（`Adopt`）。同一任务有多份副本时，取 epoch 最大的；epoch 相同时优先取任务主节点上的那份；再相同就取节点名最小的。其余副本在下一轮被停掉 |
| 同上，但这个任务的幂等键已经属于任务表里的另一个任务                          | 判定为重复，向该节点发送 `StopTask`（原因：`duplicate of task <id>`）                                                                                |
| Pending                                                                       | 调度（第 8 章）；超过 `pending_timeout_s`（8 秒）仍无可用节点，判定 Failed                                                                             |
| 任务主节点离线（超过 `node_offline_timeout_s` 没有收到它的 `NodeStatus`） | 重新调度，epoch + 1                                                                                                                                      |
| 节点在线，上报的任务里有它且 epoch 一致                                       | 正常；如果任务表里还是 Scheduled，说明 `Running` 报告丢了，由集群主节点代为提交 `ReportStatus(Running)`（`ConfirmRunning`）                        |
| 节点（任务主节点或辅助节点）在线但没有这个任务，任务状态是 Scheduled          | 每隔 `dispatch_retry_s`（5 秒）用同一个 epoch 重发 `StartTask`（幂等）；超过 `start_timeout_s`（15 秒）仍未启动，重新调度                          |
| 任务主节点在线但没有这个任务，任务状态是 Running                              | 先等 `missing_grace_s`（3 秒），因为 `NodeStatus` 可能比 `TaskReport` 晚到；仍然没有就重新调度                                                     |
| 某节点运行的任务已经结束、epoch 比任务表旧，或者并没有分配给它                | 每隔 `stop_retry_s`（5 秒）向该节点发送 `StopTask`                                                                                                   |

- 如果任务主节点已经挂了、只剩辅助节点的副本，也照样接收，下一轮对账发现任务主节点离线，再重新调度。这样，迁移途中的任务不会因为换主而丢失。
- “节点在线”和各种计时一律使用集群主节点本地的单调时钟，只保存在当前集群主节点的内存里（第 3.6 节的 `LeaderMemory`）。换主后从头开始计时，结果只是决策晚一点，不会导致非幂等的操作被重复执行。
- MVP 阶段不替换失效的辅助节点（第 4.4 节）。

## 5 选主

### 5.1 为什么需要一个集群主节点

完全无主（每个节点各自决定）也是一种选择，但调度决策需要全局视图和互斥：两个节点同时看到 edge-04 空闲，都把任务派过去，edge-04 就过载了；两个节点同时收到同一个请求，就会创建两个任务。用一个集群主节点集中做这些决策，是最简单的互斥方式。代价是需要选主和换主，这就是本章的内容。

### 5.2 机制

每个节点在 `NodeStatus` 中广播三个字段：

- `leader_name`：我认谁当集群主节点（可以是自己，也可以为空）；
- `term`：我知道的任期；
- `is_leader`：我是否在声明自己是集群主节点。

**集群主节点的每一条 `NodeStatus` 就是一次续约**。它停止发布 5 秒后（`node_offline_timeout_s`），其他节点把它判为离线，它的声明随之失效，这相当于租约到期。

每个节点每秒发布 `NodeStatus` 之前调用一次 `Election.update(peers, now)`，peers 是当前在线的其他节点。所有节点执行同样的确定性规则，只要视图一致，结论就一致。

### 5.3 规则

（代码见 `core/election.py`。）

**声明的排序**：多个节点同时声明时，按以下顺序比较，越大越好：

1. **支持者数量**：在线节点中把它报为 `leader_name` 的数量，加上它自己（再加上本节点，如果本节点也认它）；
2. **term**：任期更高的优先；
3. **名字更小**的优先。

**每个节点的决策**：

```
如果我是集群主节点：
    看到比我更好的声明                → 让位，跟随它
    否则，看到有人上报更高的 term      → 把我的 term 提到它之上，继续担任
    否则                               → 继续担任
否则：
    有声明                             → 跟随最好的那个
    没有声明：
        term 取已知最大值
        如果（启动后从未见过声明，且已过 startup_grace_s），
           或（上次看到声明已经过去 leader_timeout_s）：
            如果我是在线节点中名字最小的 → 声明自己，term = 已知最大 + 1
            否则                         → 等名字最小的那个声明
```

### 5.4 为什么先比支持者数量

如果只按 term 比较（像 Raft 那样“term 高的赢”），会出现这样的问题：

> edge-09 因为干扰被隔离了 30 秒。它看不到任何声明，于是自己声明为集群主节点，term 从 3 涨到 4。恢复连通后，它的 term 4 高于真正的集群主节点 edge-01 的 term 3，于是所有节点都转而跟随 edge-09，触发一次完全没必要的换主。

Raft 用 PreVote 解决这个问题，但我们评估过的 Python Raft 库 PySyncObj 不支持 PreVote（第 9 章 D2）。我们的解决方法是先比较支持者数量：edge-09 只有自己一个支持者，edge-01 有 11 个，edge-01 胜出。同时，edge-01 看到更高的 term 4，就把自己的 term 提到 5，继续担任。这一步很重要：edge-09 在隔离期间可能已经用 term 4 向某些执行器发过命令，执行器记住了 term 4；如果 edge-01 还停在 term 3，它的命令会被这些执行器拒绝。

同样的规则让网络分区恢复后**节点多的一侧胜出**，而不是名字小的一侧或者 term 高的一侧（`test_after_a_partition_the_side_with_more_nodes_keeps_its_leader`）。

**已在任的集群主节点不会被抢位**：名字更小的节点后来加入，看到已有声明就直接跟随，不会因为名字更小而取而代之（`test_new_node_follows_the_existing_leader_even_if_its_name_is_smaller`）。

### 5.5 时间线

**冷启动**：

```
t=0     12 个节点先后启动，开始广播 NodeStatus（leader_name 为空）
t=5 s   startup_grace_s 到期。名字最小的节点（例如 edge-01）声明，term=1
t≈5~6 s 其他节点在下一条 NodeStatus 里看到声明，跟随
t≈10 s  edge-01 的预热（warmup_s=5 s）结束，开始接受请求和对账
```

启动等待的作用：给每个节点 5 秒时间听一听“当前是否已经有集群主节点”。没有这个等待，一个后启动的节点可能在还没收到任何人的 `NodeStatus` 时就声明自己。

**集群主节点故障**：

```
t=0       edge-01 掉电。它最后一条 NodeStatus 发于 t∈(-1, 0]
t≈4~5 s   其他节点超过 5 秒没收到它的 NodeStatus，判为离线；它的声明随之消失
t≈5~6 s   距离最后一次看到声明已过 leader_timeout_s（1 秒），名字最小的存活节点 edge-02 声明，term+1
          其他节点在下一个 NodeStatus 周期看到声明并跟随
t≈10~11 s edge-02 预热结束：根据各节点 NodeStatus 中的 TaskState 接收所有正在运行的任务，开始对账
          （edge-01 自己执行的任务没有人上报，所以不会出现在新任务表里，见第 6.2 节）
```

在 t=0 到约 10 秒之间：

- 正在运行的任务**不受任何影响**，继续出结果，UE 能继续收到逐帧结果；
- 创建、销毁、查询返回 `NO_LEADER`（HTTP 503）；
- 如果有任务主节点和集群主节点同时挂了，这些任务要等新集群主节点预热结束后才会重新调度。

### 5.6 短时间出现两个集群主节点时

各节点的视图可能有短暂差异（例如某个节点刚好丢了几条 `NodeStatus`），所以可能短时间内出现两个声明者。设计不试图完全避免这种情况，而是保证它造成的后果有界：

1. **声明会收敛**：两个声明者都能看到对方，按规则必有一方让位，通常在 1～2 个 `NodeStatus` 周期内完成。
2. **term 栅栏**：执行器记住见过的最大 term。只要任期较高的集群主节点向某个执行器发过任何命令，任期较低的那个就再也不能让这个执行器启动或停止任务（`STALE_TERM`）。
3. **重复清理**：如果两边都启动了同一个请求（同一个幂等键）对应的任务，胜出的集群主节点在对账时发现两个任务的幂等键相同，停掉后出现的那个。
4. **只有 ready 的集群主节点才发布 `TaskStatus`**，而且订阅方按 `(term, seq)` 去重，所以事件流不会因为两个集群主节点而混乱（但可能有短暂的、来自较低任期的事件）。

`test_controller.py` 中有两个测试专门覆盖这种情况：任期较高的一方把重复副本停掉；任期较低的一方发出的停止命令被执行器拒绝。

### 5.7 协议版本

`NodeStatus.PROTOCOL_VERSION`（当前为 2）不同的节点：

- 不参与选主（它的声明被忽略，它也不算支持者）；
- 不会被派发任务（调度器的硬性过滤）。

这让升级时的行为可预测：升级到一半时，新旧两个版本各自组成一个集群，互不干扰。但这不等于支持滚动升级：ROS 2 Humble 的接口不支持类型演进，新旧版本的节点本来就无法正常交换消息。所以：

- 接口包（`cccp_*`）的任何改动，都要把 `PROTOCOL_VERSION` 加 1；
- 12 个节点必须一起升级，镜像标签带上协议版本号（例如 `cccp-node:p2-<git短哈希>`）；
- 不改变已有字段的含义，需要新含义就新增字段。

### 6.2 集群主节点挂掉：逐步说明

以“edge-01 是集群主节点，同时执行任务 A；edge-04 执行任务 B；edge-01 刚收到任务 C 还在排队”为例：

1. edge-01 掉电。B 继续在 edge-04 上运行，UE 能继续收到 B 的逐帧结果。
2. 约 5～6 秒后，edge-02 当选，term 从 3 变为 4，任务表清空，开始 5 秒预热。期间所有创建/查询请求返回 503。
3. 预热结束，edge-02 第一次对账：
   - edge-04 的 `NodeStatus` 里有 B（epoch 1），任务表里没有 → **接收**（`Adopt`），状态 Running，epoch 仍为 1，B 没有重启；
   - A 只在 edge-01 上运行，edge-01 已经离线，**没有人报告 A**，A 丢失；
   - C 只在 edge-01 的内存里，丢失。
4. 提交 C 的调用方在等待中收到失败：如果 UE 连的是其他节点，那个节点的转发调用最长等 15 秒后返回 `TIMEOUT`（HTTP 503）；如果 UE 直接连的就是 edge-01，则是 HTTP 连接断开。两种情况下 UE 都用同一个键重试（必要时换一个节点），edge-02 预热结束后新建 C 并调度。
5. 提交 A 的调用方早就拿到了成功回复，不会自动重试。A 的丢失需要通过事件流或查询发现（查询 A 返回 `NOT_FOUND`）。

第 5 步是这个设计最大的弱点。缓解办法：

- `leader_self_penalty`（10 分）让调度器尽量不把任务放在集群主节点自己身上；节点充足时，集群主节点上通常没有任务。
- 后续可以考虑：新集群主节点上任时，根据 `TaskStatus` 的历史判断哪些任务“消失了”，主动通知 UE（第 10.3 节）。

### 6.3 任务主节点挂掉：任务迁移

1. edge-04（任务 B 的任务主节点）掉电。
2. 约 5 秒后，集群主节点判定 edge-04 离线。对账：B 的任务主节点离线 → `Reschedule`。
3. 调度器在剩余节点中选出 edge-06（`request_node` 指定了 edge-04 的任务**不迁移**，第 3.3 节）。`Assign`：epoch 1 → 2，任务表先更新，然后下发。
4. edge-06 以 epoch 2 启动 B。如果 B 的输入是 `airsim://uav_4/0`，edge-06 自己通过 RPC 去取同一个相机的画面，输入不变（第 7 章）。PKCT 的会话 ID 变为 `task-B-2`，用规格中原始的 bbox 重新初始化。
5. edge-04 如果之后恢复，它还在以 epoch 1 运行 B，对账发现 epoch 过期，发送 `StopTask` 停掉。

**关于状态恢复**：迁移后任务是**从头开始**的。对 PKCI（逐帧分类，无状态）没有影响；对 PKCT，用最初的 bbox 重新初始化，而目标可能早就移动了，跟踪可能失败。怎样恢复取决于具体任务，第 10.4 节给出了一个通用方案的草案。

### 6.4 执行器重启

执行器（数据面进程）重启后，它内存中的任务全部消失，`NodeStatus.tasks` 变空：

- 对它担任任务主节点的 Running 任务：集群主节点先等 `missing_grace_s`（3 秒），因为 `NodeStatus` 可能比 `TaskReport` 晚到，然后重新调度（可能还是这个节点）。
- 已知限制：执行器记录的最大 term 归零。在重启后的短暂窗口里，一个过期的集群主节点发来的命令可能被接受。由于正常情况下同一时刻只有一个集群主节点，概率很低，暂不处理。可以通过把最大 term 写入本地文件来解决。

### 6.5 消息丢失

本系统中所有“必须送达”的信息都有兜底：

| 消息                    | 丢了会怎样                                | 兜底                                                                               |
| ----------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `NodeStatus`          | 一条丢了没关系；连续丢 5 秒，节点被判离线 | 每条自包含，下一秒补上                                                             |
| `TaskReport`          | 任务表不知道状态变化                      | 对账根据 `NodeStatus.tasks` 推断（`ConfirmRunning`，或发现任务消失后重新调度） |
| `TaskStatus`          | UE 少收到一个事件                         | UE 发现 `seq` 跳号时查询                                                         |
| `StartTask` 请求/回复 | 不知道任务是否启动                        | 幂等重发；多余副本由对账停掉                                                       |
| `StopTask`            | 任务没停                                  | 每 5 秒重发                                                                        |
| 逐帧结果、图像          | 少一帧                                    | 不需要兜底                                                                         |

验收要求之一是在 30% 丢包率下节点不被误判离线、不频繁换主（第 10.2 节）。按 1 Hz 发布、5 秒超时粗算，30% 的独立丢包下连续丢 5 条的概率约为 0.3⁵ ≈ 0.24%，即每一对节点之间大约每 7～10 分钟会出现一次误判。误判集群主节点不一定导致换主（第 5.4 节：误判者如果独自声明，恢复后因支持者少而让位），但误判任务主节点会导致一次不必要的迁移。所以 `node_offline_timeout_s` 需要在真实网络上实测后调整；无线丢包往往是突发的，实际情况可能比独立丢包的估算更差。

### 6.6 网络分区

MVP 不保证分区期间的正确性，但保证恢复后收敛：

- 分区期间，两侧可能各自选出集群主节点。只能看到少数节点的一侧，选出的集群主节点也能工作（我们没有多数派要求）。
- 两侧都可能接受同一个请求（UE 重试到了不同侧），各自启动一个任务。
- 恢复后：节点多的一侧的集群主节点胜出（支持者数量规则），并提升 term；另一侧的集群主节点让位。胜出方在对账时接收另一侧启动的任务（它们是“未知的运行中任务”）；对幂等键重复的，停掉其中一个。

这是我们和 Raft 的一个重要差别：Raft 的少数派一侧无法写入，所以不会接受新任务；我们的两侧都能继续工作。对于“无人机编队被临时分成两组”的场景，两侧都能继续工作可能反而是更好的行为。

## 7 任务输入

### 7.1 要解决的问题

如果每块板卡只读自己无人机的相机（`<ns>/camera/image`），会有两个问题：

1. **任务迁移后输入变了**：任务主节点挂了，任务迁到另一块板卡，处理的就是另一架无人机的画面。对 PKCT 来说，原来的目标框在新画面里没有意义。
2. **冗余模式无法保证同一份输入**：每个参与者各读各的相机，做的根本不是同一件事。

### 7.2 数据源地址

任务的输入用一个地址描述（`CreateTask.input`，代码 `core/input_source.py`）：

| 地址                            | 含义                             | 位置属性                                    |
| ------------------------------- | -------------------------------- | ------------------------------------------- |
| 空                              | 执行节点自己的默认相机           | 绑定到执行节点                              |
| `airsim://<vehicle>/<camera>` | AirSim 中某架无人机的某个相机    | **共享**：任何节点都能通过 RPC 直接取 |
| `ros://<node>/<topic>`        | 某个节点上的 topic（真实传感器） | **绑定到该节点**                      |

核心原则：**请求里只放地址，不放数据**。把数据打包进服务请求的做法有三个问题：大块数据走服务调用，每个参与者都要传一份；迁移时数据要重新传；而且服务请求没有压缩。改成地址后，大块数据只通过 topic 传输，发布一次可以有多个订阅者，并且压缩后再发。小数据（参数、bbox、几 KB 以内的协同载荷）仍然可以直接放进请求。

仿真和真机走同一套机制：仿真时用 `airsim://`，真机时用 `ros://` 或空地址，平台的其他部分完全一样。

### 7.3 每个参与者怎么拿到数据

`plan_input()` 根据地址、本节点名、角色、任务主节点、AirSim 取图模式，决定订阅哪个 topic、是否压缩、是否自己取图：

| 地址             | 本节点是…… | `each` 模式（默认）                                       | `relay` 模式                                                         |
| ---------------- | ------------ | ----------------------------------------------------------- | ---------------------------------------------------------------------- |
| 空               | 任意         | 订阅本节点的 `camera/image`（或规格中的 `image_topic`） | 同左                                                                   |
| `airsim://v/c` | 任务主节点   | 自己取图，订阅 `input/airsim/v/cam_c`                     | 同左                                                                   |
| `airsim://v/c` | 辅助节点     | 自己取图，订阅本节点的 `input/airsim/v/cam_c`             | 不取图，订阅**任务主节点**的 `input/airsim/v/cam_c/compressed` |
| `ros://n/t`    | 节点 n 本身  | 订阅本地的 `t`                                            | 同左                                                                   |
| `ros://n/t`    | 其他节点     | 订阅 `/<n 的命名空间>/t/compressed`                       | 同左                                                                   |

`each` 和 `relay` 的取舍：

- `each`：每个参与者独立向 AirSim 取图，不经过无线网络，但 AirSim 的 RPC 负载随参与者数量增加，可能拖慢 UE 的帧率。
- `relay`：只有任务主节点取图，辅助节点通过无线网络收压缩流，AirSim 负载最小。
- 用 `AIRSIM_FETCH_MODE` 切换，代码不用改。哪种更好需要实测 AirSim 多客户端的负载。

### 7.4 AirSim 按需取图

`airsim_feeds.py`：

- 只有当某个任务使用 `airsim://<v>/<c>` 时，才为这个相机启动取图线程；多个任务共用一个相机时引用计数，最后一个任务结束时停止线程。
- 取图频率由 `airsim_fps` 控制（默认 10），发布到 `<ns>/input/airsim/<vehicle>/cam_<camera>`。
- 节点没有设置 `AIRSIM_HOST` 时，不能执行 `airsim://` 任务：执行器返回 `NOT_READY`，集群主节点换一个节点。

### 7.5 压缩转发

`relay.py`：

- 本节点对外提供的 topic（执行器参数 `relay_topics`，默认 `camera/image`；AirSim 取图的 topic 自动加入）会额外提供一个 `<topic>/compressed`（JPEG，质量 80）。
- **只有在有其他节点订阅时才编码**：没人订阅时，不解码也不编码，不占 CPU。
- 接收方（`images.py`）收到 `CompressedImage` 后用 PIL 解码，再交给推理。

### 7.6 带宽估算

| 数据                         | 大小               | 10 fps 时                |
| ---------------------------- | ------------------ | ------------------------ |
| 640×480 原始 RGB 帧         | 约 920 KB          | 约 74 Mbps               |
| 同一帧 JPEG（质量 80）       | 约 30～60 KB       | 约 2.4～4.8 Mbps         |
| `TaskResult`（含协同载荷） | 约 1～2 KB         | 约 0.1 Mbps              |
| `NodeStatus`（全集群）     | 每条 1～4 KB × 12 | 约 0.1～0.4 Mbps（1 Hz） |

所以禁止跨节点逐帧传输原始图像，跨节点的图像一律走压缩流。JPEG 大小随画面内容变化很大，以上是估算值。

### 7.7 与调度的联动

- **绑定到节点的数据源**（`ros://n/...`）：调度器给节点 n 加 15 分（`input_locality_bonus`），优先让任务主节点在数据所在的地方读本地数据；节点 n 离线时任务无法放置，返回 `NO_FEASIBLE_NODE`。
- 网络评分以数据所在节点为参照点（`input_node`），选出离数据近的辅助节点。
- **共享数据源**（`airsim://`）：任何节点都行，迁移后输入不变。

### 7.8 新增数据类型

平台不关心数据是什么，只关心它在哪里。新增一种数据类型（例如点云）时，由算法声明自己需要的消息类型，平台的取数逻辑（地址解析、订阅、转发）不用改。目前只实现了图像（`Image` 和 `CompressedImage`）。

## 8 调度

### 8.1 流程

调度器（`core/scheduler.py`）采用“过滤 + 评分”两阶段选节点。调用一次 `schedule()` 的流程：

```
数据源绑定到某节点且该节点离线？ ──是──► NO_FEASIBLE_NODE
        │否
指定了 target_nodes？ ──是──► 只检查硬性条件，按指定的顺序放置（第一个是任务主节点）
        │否
指定了 request_node？ ──是──► 任务主节点固定；不需要辅助节点就到此为止
        │                    需要辅助节点的话，辅助节点仍按评分选
        ▼
对每个在线节点：过滤（硬性条件 + 资源条件） → 评分 → 排序
        ▼
可用节点数 < 需要的参与者数？ ──是──► NO_FEASIBLE_NODE（附带每个节点被拒的原因）
        ▼
第 1 名是任务主节点，接下来 helper_count 名是辅助节点
```

### 8.2 过滤条件

| 条件                                                | 拒绝原因                  | 对指定节点也生效？ |
| --------------------------------------------------- | ------------------------- | ------------------ |
| 协议版本不同                                        | `protocol_mismatch`     | 是                 |
| 推理未就绪                                          | `not_ready`             | 是                 |
| 节点不支持该任务类型                                | `algorithm_unavailable` | 是                 |
| 最近 60 秒内启动这个任务失败过                      | `recently_failed`       | 否                 |
| 已分配任务数 ≥ 4                                   | `busy`                  | 否                 |
| 电量 < 20%                                          | `battery_low`           | 否                 |
| 需要 GPU 但没有                                     | `gpu_unavailable`       | 否                 |
| 空闲 CPU 核数不足                                   | `cpu_insufficient`      | 否                 |
| 空闲内存不足（共享内存 GPU 的显存需求也算在内存里） | `mem_insufficient`      | 否                 |
| 独立显卡的空闲显存不足                              | `gpu_mem_insufficient`  | 否                 |

“已分配任务数”来自任务表，而不是节点上报的 CPU 使用率。原因是：任务启动后几秒，CPU 使用率才会反映出来，这期间如果只看 CPU，所有决策都会选同一个节点。

### 8.3 评分

```
得分 = w_lrs × LRS + w_brs × BRS + w_net × NET
       − 5 × 该节点已分配的任务数
       − 10（如果是集群主节点自己）
       + 15（如果数据绑定在这个节点上）
```

推理任务的默认权重是 `(0.3, 0.3, 0.4)`，可以按任务类型配置。

| 分项                   | 含义                                   | 计算（0～100）                                                                                                                                                                            |
| ---------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LRS** 最少资源 | 放上这个任务后剩余资源越多越好         | CPU、内存（使用 GPU 时再加 GPU）剩余比例的平均值 × 100。已用量 = 上报的使用率 + 预留（CPU 10%、内存 20%）                                                                                |
| **BRS** 资源均衡 | 放上这个任务后各维度的使用率越均衡越好 | 比较放置前后各维度使用比例的标准差：50 + (50 + 放置后的均衡度 − 放置前的均衡度) / 2                                                                                                      |
| **NET** 网络     | 到参照节点的链路越好越好               | 从 100 开始扣：RTT 超过 50 ms 每 50 ms 扣 10（最多 40）；抖动超过 10 ms 每 10 ms 扣 5（最多 30）；丢包超过 1% 每 1% 扣 5（最多 50）；三项都乘以任务的 `latency_sensitivity`（默认 0.5） |

NET 的参照节点：任务规格有 `input_node`（数据所在节点）时用它，否则用集群主节点。链路测量值优先取参照节点对候选节点的测量，没有就取反方向的，都没有就用默认值（RTT 30 ms、抖动 5 ms、丢包 0.5%）。

**一个例子**：两个候选节点资源相同，LRS=60、BRS=80；edge-03 到参照节点 RTT 20 ms，NET=100；edge-05 RTT 150 ms，`latency_sensitivity`=1，NET=100−20=80。edge-03 得分 0.3×60+0.3×80+0.4×100=82；edge-05 得分 74。如果 edge-03 上已经有 2 个任务，它就要扣 10 分，变成 72，任务会被派给 edge-05。

### 8.4 链路测量

`core/link_estimator.py` 只用 `NodeStatus` 流量测量链路，不额外发包，也不依赖时钟同步：

- **RTT**（类似 RTCP 接收报告）：节点 B 在自己的 `NodeStatus` 里，对每个对端 A 回显“我最后收到的 A 的 seq”和“我收到它之后过了多久”。A 收到后，用“自己发出那条 seq 至今的时间”减去 B 的持有时间，就是 RTT。两端都只读自己的单调时钟。
- **平滑**：RTT 用 1/8 增益（同 TCP SRTT），抖动用 1/16 增益（同 RTP）。
- **丢包**：接收方根据对端 `seq` 的空洞计算，按时间窗口统计。
- **对端重启**（`incarnation` 变化）：清空这个对端的测量。

精度受 1 Hz 的发布频率限制：持有时间最长 1 秒，回显本身也有调度抖动。这对调度用的“好/中/差”判断足够了，但不能当作精确的网络测量。

### 8.5 几个取舍

| 做法                                                                   | 原因                                                                |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 网络评分用实测的链路，而不是固定值                                     | 自组网中不同节点对之间的链路差异很大                                |
| 不做带宽评分                                                           | 链路测量只有 RTT、抖动、丢包，没有测带宽                            |
| 时延、抖动、丢包共用一个敏感度 `latency_sensitivity`                 | `CreateTask` 只有一个敏感度字段，调用方不需要理解三个参数         |
| GPU 维度用节点上报的显存使用率；均衡评分的显存维度加的是任务的显存需求 | 每个维度都用同一种单位的量，评分才可比                              |
| 按已分配任务数做容量过滤，每个任务再扣 5 分                            | 见第 8.2 节：CPU 使用率滞后于任务分配                               |
| 集群主节点给自己扣 10 分                                               | 减少任务随集群主节点一起丢失的情况（第 6.2 节）；也给控制面留出 CPU |
| Jetson 的 `gpu_mem_total_mb` 填 0                                    | 让调度器区分独立显卡和共享内存的 GPU：后者的显存需求算进内存        |

### 8.6 调参建议

- 权重、扣分、加分都需要在真实负载下调整。建议先记录每次调度的候选列表和各项得分（`ScheduleResult.candidates` 已经有这些数据），再根据实际放置效果调整。
- `max_tasks_per_node=4` 与 PKCT 的 `MAX_TRACKERS` 一致。如果以后某种任务很轻，可以改成按资源而不是按个数限制。

## 9 设计决策记录

每条记录的格式：**决定**、**理由**、**代价**、**什么情况下应该重新考虑**。

### D1 用单一集群主节点，而不是完全无主

- **决定**：任何时刻由一个节点集中做调度和任务管理。
- **理由**：调度需要全局视图和互斥，集中决策是最简单的互斥方式（第 5.1 节）。需求里也明确说“一段时间内由一个节点充当集群主节点”。
- **代价**：需要选主；换主期间（约 10 秒）不能创建任务。
- **重新考虑**：节点规模大到集群主节点成为瓶颈（远超 12 个）时。

### D2 不用 Raft

这是影响最大的一个决定。我们完整实现并实测过一个基于 Raft 的版本，最后没有采用。

**Raft 的吸引力**：任务表复制到多数派节点上，换主后不丢任何信息；理论上可以做到“任务不重复”。实现用的是 PySyncObj（纯 Python 的 Raft 库），转 C++ 时换 NuRaft。

**Raft 版本的实测**（12 个节点在 localhost 上）：

| 项目                               | 结果                                              |
| ---------------------------------- | ------------------------------------------------- |
| 换主耗时                           | 中位数 3.3 秒，最长 4.2 秒                        |
| 一次提交的延迟                     | 约 316 ms（PySyncObj 把命令攒到下一次心跳发送）   |
| 创建一个任务                       | 3 次提交（Submit、Assign、ReportStatus），约 1 秒 |
| 新集群主节点刚当选时查已提交的任务 | 5 次中 1 次查不到，必须先提交一条 Barrier         |

**为什么去掉**：

1. **Raft 不能消除执行层的重复**。Raft 保证的是任务表一致，但“下发 StartTask”和“执行器真的启动”发生在 Raft 日志之外。旧集群主节点在被罢免前发出的下发请求、执行器重启、回复丢失……这些情况下，仍然需要 term 栅栏和对账来清理。也就是说，**有了 Raft，第 5.6 节的那套机制一样不能少**。
2. **Raft 实际多保住的东西不多**。对比第 3.7 节：Raft 能多保住的，只有“排队中/下发途中的任务”和“历史记录”。前者用“没跑起来就如实回复失败 + 幂等重试”可以弥补，后者可以由 UE 保存。
3. **Raft 对自组网的要求高**。每次提交需要 7 个节点（12 个中的多数）确认；PySyncObj 要求节点之间两两建立 TCP 连接、配置静态成员表（`cluster.yaml`）；要处理持久化（全集群重启后任务表该恢复还是清空？）。这些都是额外的部署和运维负担。
4. **PySyncObj 没有 PreVote**，节点短暂断网再恢复会引发不必要的换主。
5. **团队只有 3 个人**。Raft 库是一个需要专人理解、调试的黑盒，转 C++ 时还要换一个库（NuRaft），两个库的行为差异又是一层风险。

**采用的做法**：广播选主（第 5 章）+ 执行者是事实来源（D4）。三人讨论后确定接受“故障时可能短暂重复，几秒内自动清理”。

- **代价**：见第 1.4 节的“不保证”一列。
- **重新考虑**：如果业务要求“集群主节点挂掉时排队中的任务也不能丢”或“任何时刻都不能重复”，而且无法由调用方重试来满足。

### D3 任务表只放在集群主节点内存里

- **决定**：不复制、不持久化；换主后从执行者的上报重建。
- **理由**：复制需要共识（D2）；持久化在全集群重启时反而带来“该恢复还是清空”的问题。任务表里真正重要的部分（正在运行的任务）已经由执行者持有。
- **代价**：第 3.7 节列出的信息会丢失。
- **重新考虑**：同 D2。

### D4 执行者是事实来源

- **决定**：“实际在跑什么”只以执行者的上报为准；集群主节点的任务表是期望状态，靠对账让两者一致。新集群主节点不知道的运行中任务，一律**接收**而不是停掉。
- **理由**：执行者持有的信息是最可靠的，因为任务就在它那里跑。这个思路和 Kubernetes 的控制器一样：期望状态 + 实际状态 + 持续对账，任何一方出了问题都会被下一轮对账纠正。
- **代价**：执行者需要上报完整的任务规格（`spec_json`），`NodeStatus` 变大（第 3.2 节）。
- **细节**：同一任务有多个副本时，接收 epoch 最大的；epoch 相同时优先取任务主节点上的；再相同取节点名最小的。只剩辅助节点副本时也接收，下一轮发现任务主节点离线再重新调度。这些规则保证迁移途中换主也不会丢任务。

### D5 只有跑起来才算创建成功

- **决定**：网关只在任务进入 Running 后回复成功；否则回复失败并附带 task_id，调用方用同一个幂等键重试。
- **理由**：让“成功”有一个可以兑现的含义：成功的任务一定在某个执行者上，因此一定能在换主后被接收。“写进任务表就算成功”在没有复制的任务表上是兑现不了的。
- **代价**：调用方必须正确实现重试和幂等键；创建请求最长阻塞 10 秒。
- **重新考虑**：如果有调用方无法实现重试。

### D6 task_id 用 UUID

- **决定**：集群主节点生成 UUID 字符串。
- **理由**：没有复制的计数器（D3），换主后无法保证整数 ID 不重复。
- **代价**：UE 接口的 task_id 是字符串而不是整数，UE 侧要按字符串处理。

### D7 term 和 epoch 两道栅栏

- **决定**：执行器检查 term（拒绝旧集群主节点），任务表和汇总方检查 epoch（拒绝旧执行会话）。
- **理由**：两者防的是不同的东西（第 3.8 节）。只有 term 的话，同一个集群主节点任期内的迁移无法区分新旧会话；只有 epoch 的话，旧集群主节点可以用“看起来合法”的 epoch 停掉任务。
- **代价**：执行器需要记住最大 term；重启后归零（已知限制）。

### D8 服务名唯一，转发只转一次

- **决定**：服务都放在 `<ns>` 下；公开入口 `api/*` 转发到 `leader/*`，`leader/*` 不再转发。
- **理由**：同名服务有多个服务端时，请求会被每个服务端执行一遍（第 2.5 节）；转发多次可能形成环路。
- **代价**：网关需要知道集群主节点的名字（来自选主状态），换主瞬间可能转发给旧集群主节点，此时返回 `NO_LEADER`，调用方重试。

### D9 下发用 Service，不用 Action

- **决定**：`StartTask`/`StopTask` 是普通服务，启动后立即返回；长时间运行的状态通过 `NodeStatus` 和 `TaskReport` 传递。
- **理由**：ROS 2 Action 的 goal 由发起它的客户端持有，换主后新集群主节点接管不了旧集群主节点发起的 goal；Action 自带的状态机（accepted/executing/succeeded…）和我们的任务状态机重复，两套状态容易不一致；Action 的反馈是点对点的，而我们需要所有节点（任何一个可能成为新集群主节点）都能看到任务状态。
- **代价**：需要自己定义 `TaskReport` 和对账。

### D10 本地直接调用，跨节点低频用 Service，逐帧用 Topic

- **决定**：执行器和推理引擎在同一进程，直接调用函数（`LocalBackend`）；跨节点的命令用 Service；跨节点的逐帧数据用 Topic。
- **理由**：同一进程内走 ROS 服务要序列化、过 DDS、再反序列化，对 640×480 的图像来说是纯开销。跨节点的 Service 适合低频、需要明确结果的命令。逐帧数据用 Topic，因为可以多个订阅者、可以丢帧、不需要逐条确认。
- **代价**：执行器和推理引擎必须在同一进程（数据面进程）；推理崩溃会带走执行器。保留 `RosServiceBackend` 作为退路（`INFERENCE_BACKEND=ros`）。

### D11 任务输入用地址描述，请求里不放数据

- **决定**：见第 7 章。
- **理由**：迁移后输入不变；冗余模式下各参与者处理同一份输入；大块数据只传一次、可以压缩、可以多播。
- **代价**：`ros://` 输入绑定到节点，那个节点挂了任务就无法继续（这是物理事实，不是设计缺陷）。

### D12 不用合同网（招标—投标）方式分配任务

- **决定**：由集群主节点集中调度，不采用合同网方式（发布任务 → 各节点投标 → 选中标者）。
- **理由**：招标需要额外一轮广播和等待投标的时间；多个招标同时进行时，一个节点可能同时中标多个任务，又需要额外的确认机制；而集群主节点本来就从 `NodeStatus` 掌握了所有节点的资源和链路，不需要再问一遍。
- **代价**：调度结果依赖 `NodeStatus` 的新鲜度（最多 1 秒的延迟）。
- **重新考虑**：如果节点的“意愿”包含 `NodeStatus` 表达不了的信息（例如飞行任务的优先级）。

### D13 每个节点 3 个进程

- 见第 2.4 节。理由是控制进程必须轻、数据面受 GIL 影响、DDS 参与者数量。

### D14 核心逻辑不依赖 ROS

- 见第 2.3 节。理由是测试和转 C++。

### D15 可重试的错误在 HTTP 上返回 503

- **决定**：`NO_LEADER`、`BUSY`、`NOT_READY`、`TIMEOUT` 一律返回 503。
- **理由**：HTTP 客户端普遍把 4xx 理解为“请求错了，不要重试”，把 503 理解为“稍后重试”。换主期间返回 400 会让 UE 错误地放弃。

### 10.3 后续工作

### 10.4 任务状态恢复：方案草案

迁移后任务是否需要恢复执行状态，取决于具体任务：

| 任务                               | 状态                     | 迁移后需要什么                                  |
| ---------------------------------- | ------------------------ | ----------------------------------------------- |
| PKCI 逐帧分类                      | 无                       | 什么都不需要                                    |
| PKCT 跟踪                          | 目标当前的位置和外观特征 | 用最近的位置重新初始化跟踪器，而不是最初的 bbox |
| 以后的累积型任务（例如计数、建图） | 累积量                   | 从最近的检查点继续                              |

通用机制（草案，尚未实现）：

1. 算法在 `TaskResult` 中可选地附带一个**检查点**（几 KB 以内的 JSON 或字节，例如 PKCT 的最新 bbox）。
2. 执行器把最近一次检查点放进 `TaskState`（随 `NodeStatus` 广播），这样集群主节点和其他节点都能看到。
3. 重新调度时，集群主节点把最近的检查点放进 `StartTask` 的规格里；新执行者用它初始化。
4. 检查点和 epoch 绑定：只接受当前 epoch 的检查点。

这样平台只负责“搬运”检查点，检查点的内容由算法定义。代价是 `NodeStatus` 变大；如果检查点较大，可以只放摘要，内容走 topic。
